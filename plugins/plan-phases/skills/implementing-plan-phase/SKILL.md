# 計画の 1 フェーズを実装する

引数: `$ARGUMENTS`（計画書のパス）

計画書と同じディレクトリが**計画のディレクトリ**、その `README.md` が**計画の README** になる。判断の要らない操作は共通のスクリプト `${CLAUDE_SKILL_DIR}/../plan-phases-shared/scripts/plan-phases` で行う。出力は JSON で、`ok` が false なら `problems` か `error` を読む。スクリプトはリポジトリのルートで実行する（計画のディレクトリが Git の外にあるので、そこに cd すると git と gh が動かない）。

利用者への報告と結果ファイルは日本語で書く。

## 守ること

決まりに反する git と gh の操作は、frontmatter のフック（`plan-phases-shared/scripts/guard.py`）が止める。止められたら、回り込まずに理由を読み、止まる。

- 人には聞かない。誰も答えないところで動く（`plan-phases run` は `claude -p` で起動する）
- 計画書が決めるのは、約束（後のフェーズや外が頼る名前・形・エラー・文言・表）、従う決まり、作り方、テストのケースと期待する結果、完了の条件まで。関数の分け方、問い合わせの組み立て、内部の名前、export、テストの準備の値、見た目の細部は、CLAUDE.md と既存のコードの形に合わせて自分で決める。計画書との違いは書き残さない（計画書は使い捨て）
- 止まるのは次のときだけ。止まるときは手順 7 の結果ファイルを `--status stopped` で書いて終える
  - 計画書の「変えてはいけないこと」を変えないと進めない
  - データを失う、または本番に影響する操作が要る
  - 計画書が矛盾していて、どちらにしても目的を果たせない
  - 同じ問題で 2 回直して失敗した（3 回目を試す前に、前提と原因の仮説を書いて止まる）
- 計画書の「変更するファイル」は目安にする。目的を果たすのに要るファイルは変えてよい（「対象外」と「変えてはいけないこと」は守る）
- 計画書の「約束」は、そのとおりに作る。既存のコードや検査と合わずに変えたときは、変えた約束と理由を結果ファイルの `--summary` に書く（後のフェーズのワーカーはコードを読む）
- コミットメッセージ、コードのコメント、テストの名前に、計画書と要件定義書にだけある番号・記号・名前（「規則 B」「決めたこと 2」「要件の #28」、作業名、計画書のファイル名、「フェーズ 3」）を書かない。中身を言葉で書く。計画書はリポジトリの外にあって使い捨てなので、マージの後は誰も読めない（`commit-check` が止める）
- 計画書と計画の README は読むだけにする。進捗やチェックボックスを書き換えない（進み具合の正はコミットと機能の PR）
- git と gh の操作は、`{{機能ブランチ}}` へのコミットと push、機能の PR の作成と本文の更新に限る
- main への直接のコミットと push、ブランチの作成、ほかの PR の作成、PR のマージ、force push、タグ、履歴の書き換え（rebase、`reset --hard`、push 済みのコミットの amend）はしない
- デプロイはしない（本番とプレビュー環境は GitHub Actions が行う）
- `{{許可するコマンド}}` に書かれたコマンドは実行してよい。1 回の Bash で単独で実行し、ほかのコマンドと（`&&`・`;`・`|` で）つながない。指揮役が渡す許可ルールはつないだ全体には効かず、auto mode の分類器に回って拒否されることがある。権限が足りずに拒否された操作は繰り返さず、できなかったこととして記録する

## 値を読む

```bash
${CLAUDE_SKILL_DIR}/../plan-phases-shared/scripts/plan-phases values <計画のディレクトリ> --require 計画名 機能ブランチ インストール 静的解析 テスト テストの範囲 "UI の方針" "PR の決まり" 許可するコマンド "PR のタイトル"
```

`values` の値を、以下の `{{…}}` に使う。「なし」の欄は null になる。表に無い欄があると失敗するので、推測で埋めずに止まる（無い欄を `stopped_reason` に書く）。作業名は計画書の冒頭に書いてある（`<計画名>-p<番号>`）。

## 手順

```txt
- [ ] 1. 始める前の確認
- [ ] 2. 実装
- [ ] 3. 前の push を確かめる
- [ ] 4. 完了の前の確認
- [ ] 5. コミット
- [ ] 6. push と PR の更新
- [ ] 7. 結果ファイルを書いて報告する
```

### 1. 始める前の確認

- `plan-phases preflight <計画のディレクトリ>` を実行する（機能ブランチで、origin と同じで、未コミットの変更が無い）。`ok` が false なら、触らずに止まる（他の作業が混ざるため）
- このフェーズの目的、解く問題、予想する最小の変更を、自分の言葉で 3 行にまとめて示す
- 計画書の「テスト」のケース（Test List）を書く。ケースの分け方と準備の値は自分で決める。やめたケースがあれば、理由を結果ファイルの `--summary` に書く
- `{{テスト}}` を実行し、既に落ちているテストがあれば記録する

### 2. 実装

- ステップバイステップで確実に実装する。使うツールやライブラリのベストプラクティスに従い、仕様は必要に応じて Web Search や context7 で最新の情報を確かめる
- `{{テストの範囲}}` と `{{UI の方針}}` に従う
- 計画書の「従う決まり」に従う。CLAUDE.md や既存のコードと食い違ったら、CLAUDE.md と既存の形に合わせ、食い違いを結果ファイルの `--summary` に書く（計画のスキルを直す材料になる）
- 案を比べて決めたことは、その場で、比べた案・選んだ理由・根拠と出典（実測なら日付とコマンド、製品の制約なら公式のドキュメントの URL）をメモしておき、コミットメッセージの「決めたこと」に書く。決定と学びの記録が、ADR にするかを決める材料にする（後からは理由を作らない）。比べた案の無い細部は書かない
- バグの修正は、再現する失敗テストを先に書いてから直す
- E2E のテストは、`{{テストの範囲}}` に従って足し・直すだけにし、流さない（プレビューはまだ前の push の状態にある。最後の push に流して記録をコミットするのは仕上げ）
- コードコメントは原則書かない。コードでは表せない Why と Why not だけを残す
- コミットするのはコードとテストだけにし、計画書の内容をリポジトリに書き写さない

### 3. 前の push を確かめる

前の手順は、push の後に CI を待たずに終えている。前の push の CI と、1 つ前のフェーズの「push の後の確認」を、ここで確かめる。CI は同じ PR への次の push で取り消されるので、自分の push より前に確かめる。

```bash
${CLAUDE_SKILL_DIR}/../plan-phases-shared/scripts/plan-phases previous <計画のディレクトリ> <作業名>
```

- 前景で実行し、終わるまで待つ（バックグラウンドや Monitor にしない）。`ci` が `pending` なら、もう一度実行する。3 回続けて `pending` なら待たずに進み、報告に書く
- `ci` が `none` なら、機能の PR がまだ無い（最初のフェーズ）か、CI が走っていない。後者なら報告に書く
- `ci` が `fail` なら、落ちたチェックのログを `gh run view <run_id> --log-failed` で読み、原因を直す。バグは、再現する失敗テストを先に書いてから直す。直した変更はこのフェーズのコミットに含め、コミットメッセージの「確認したこと」に、落ちたチェック、原因、直し方を 1 行で書く
- 手元で再現せず、原因がコードに無さそうな失敗（デプロイ先の一時的な失敗、不安定なテスト）は、直さずに進む。落ちたチェックと、そう判断した理由を結果ファイルの `--summary` に書く。次の push の CI がもう一度確かめる
- `previous.post_push`（1 つ前のフェーズの「push の後の確認」）があれば、`ci` が `pass` のときに、`{{許可するコマンド}}` の範囲で確かめられるものを確かめる（プレビュー環境の件数、API の応答など）。プレビュー環境は、まだ前の push の状態にある。ラベルを貼るなどで新しいチェックが走ったら、`previous` をもう一度実行して待つ。見つかった問題は、CI の失敗と同じく直す
- 確かめた `post_push` は結果ファイルの `--summary` に、確かめられなかったもの（`ci` が `pass` でなかったときはすべて）は 1 つずつ `--manual-step` に、頭に前のフェーズの作業名を付けて書く（仕上げが確かめ直し、PR の「マージの前に行う確認」に集める）

### 4. 完了の前の確認

- `{{静的解析}}` と `{{テスト}}` を通す
- 影響範囲を確かめ、どれが当てはまったかを書く: 入口（画面、API、CLI、設定、ジョブ）、逆の操作（追加と削除、有効と無効など）、権限、既存のドキュメントの正確さ
- 計画書の「完了の条件」を 1 つずつ確かめる。実行したコマンドとその結果を示す。「はず」「おそらく」で完了としない
- 「完了の条件」は push の前に確かめられるものだけのはず。push の後にしか確かめられない条件（プレビュー環境の画面など）が「完了の条件」に混ざっていたら、それは「push の後の確認」と同じに、次のフェーズ（最後のフェーズなら仕上げ）が確かめる。その条件を 1 つずつ、結果ファイルの `--post-push` に書く（次のフェーズの `plan-phases previous` と仕上げが読む）

### 5. コミット

変更を 1 つのコミットにまとめる（作業の途中ではコミットしない）。

1. 下書きを出す

   ```bash
   ${CLAUDE_SKILL_DIR}/../plan-phases-shared/scripts/plan-phases commit-skeleton phase <計画書のパス>
   ```

2. `<…>` の置き換える場所を埋める。各項目の書き方は [references/commit-message.md](references/commit-message.md) にある
3. コミットするファイル（コードとテストだけ）を `git add` する。続けて次の 1 回の Bash で、書く・確かめる・コミットする。`commit-check` は、メッセージと `git add` した変更に計画書と要件定義書にだけある番号・記号・名前が無いかも見る。`problems` を出したらコミットされないので、直してもう一度実行する

   ```bash
   msg="$(git rev-parse --git-path plan-phases-message.txt)"
   cat > "$msg" <<'EOF'
   <埋めたコミットメッセージの全文>
   EOF
   ${CLAUDE_SKILL_DIR}/../plan-phases-shared/scripts/plan-phases commit-check phase "$msg" --plan <計画書のパス> && git commit -F "$msg"
   ```

### 6. push と PR の更新

1. `git push` で `origin/{{機能ブランチ}}` に push する
2. 機能の PR が無ければ作る（最初のフェーズ）。有れば何もせずに URL を返す。タイトルと本文は計画の README から取る: `plan-phases pr-create <計画のディレクトリ>`
3. 機能の PR の本文の進捗で、このフェーズの行にチェックを入れ、コミットの短いハッシュを書き足す: `plan-phases pr-check-off <計画のディレクトリ> <作業名> <短いハッシュ>`
4. この push の CI と、このフェーズの「push の後の確認」は待たない。次のフェーズのワーカーが自分の push の前に確かめ、最後のフェーズの分は仕上げが確かめる。CI を待つコマンド（`plan-phases ci`、`gh pr checks --watch`、Monitor）は使わずに 7 に進む

### 7. 結果ファイルを書いて報告する

止まったときも書く（`--status stopped --stopped-reason "<止めた理由と、人に決めてほしいこと>"`）。

```bash
${CLAUDE_SKILL_DIR}/../plan-phases-shared/scripts/plan-phases result <計画のディレクトリ> --name <作業名> --skill implementing-plan-phase --status done --commit <短いハッシュ> --pr <機能の PR の URL> --previous-ci <pass|fail|pending|none> --summary "<何をしたか、前の push の CI とその扱い、確かめた push の後の確認を 1〜3 行で。変えた約束、やめたテストのケース、従う決まりと CLAUDE.md の食い違いがあれば、それも>" --post-push "<push の後にしか確かめられなかった完了の条件>" --manual-step "<人が手で行う確認や作業>"
```

`--post-push` と `--manual-step` は数だけ繰り返し、無ければ付けない。結果ファイルは自己申告なので、事実（ハッシュ、URL、前の push の CI の結果）だけを書く。指揮役（`plan-phases run`）は、これと git・PR・手元を照らして確かめる。

そのうえで、コミットのハッシュ、機能の PR の URL、前の push の CI の結果と扱いを、終わったことの報告として示す。
