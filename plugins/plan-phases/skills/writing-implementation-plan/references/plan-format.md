# 計画の形

`plan-phases check-plan`、指揮役（`plan-phases run`）、ワーカーのスキルが読む形。見出しの文字は変えない（番号は付けてよい）。`check-plan` は、ここに反するものを `problems`（直すまで指揮役が動かない）か `warnings` に出す。

## フォルダの配置

```txt
<プロジェクトのフォルダ>/
├── <リポジトリ>/
└── plans/                     ← 計画の置き場所（リポジトリの外・Git の管理外。マージの後も残す）
    └── <計画名>/              ← 計画のディレクトリ
        ├── requirements.md    ← 要件定義書（defining-requirements が書く。計画書としては読まない）
        ├── README.md          ← 計画の README
        ├── phase-01-<短い名前>.md
        ├── phase-02-<短い名前>.md
        ├── .scratch/          ← 使い捨ての試作とスクリプト
        └── .runs/             ← 指揮役とワーカーの記録（指揮役が作る）
```

要件定義書の形は `defining-requirements/references/requirements-format.md` にある。何を、なぜ、どこまで作るかの正は要件定義書で、計画の README はそれを写さずに指す。

## 計画の README

節をこの順に置く。（任意）と書いたもの以外は必ず置く。

1. タイトルと概要（`# <計画名>：<1 行の要約>` の下に、要件定義書の目的と範囲の 1〜3 行の要約、要件定義書（`requirements.md`）を指す 1 文、機能ブランチ）
2. `## 用語`（任意。要件定義書の用語に加えて、この計画で使うコードの言葉の意味の表）
3. この計画で守る規則（任意。複数のフェーズが従う画面や API の約束など。見出しは自由。規則には中身の分かる短い名前を付け、記号や番号（規則 A、規則 1）で名づけない。ワーカーがその記号をコードのコメントに写し、マージの後は誰も読めなくなる）
4. `## 領域の変更`（任意。領域の設計の決まりを当てて、サブドメイン、用語とコードの名前、コンテキストとつなぎ方、作り方、集約、置き場所のどれかが変わるとき。書き方は `references/design/domain.md` の「計画に書くこと」。決定と学びの記録がこれを読んで `docs/domain/` を直す）
5. `## フェーズ表`
6. `## 開始前に人がすること`
7. `## プロンプトに入れる値`
8. `## 決めたこと`
9. `## 機能の PR の本文`
10. `## 計画書の一覧`（任意。ファイルとフェーズの表）

### フェーズ表

表の順が実装の順になる。作業名は `<計画名>-p<番号>` で、1 から順に付ける。指揮役は README の表に出てくる作業名を上から読むので、フェーズ表より前の表には作業名を書かない。

```md
## フェーズ表

表の順に 1 つずつ実装する。1 フェーズが機能ブランチの 1 コミットになる。

| フェーズ | 作業名 | 要約 |
| --- | --- | --- |
| フェーズ 1 | `<計画名>-p1` | <1 行の要約> |
| フェーズ 2 | `<計画名>-p2` | <1 行の要約> |
```

### 開始前に人がすること

人にしかできない前提の作業（秘密の値の登録、契約やアカウントの作成、外部の承認など）の箇条書き。無ければ「なし。」とだけ書く。指揮役は始める前に一度だけ、済んだかを端末で聞く。

## プロンプトに入れる値

表（欄、値）に、次の欄をすべて書く。無い値は「なし」と書く（「なし（理由）」でもよい）。値を 1 つのコードの書式（`` `…` ``）で囲むと、スクリプトは中身だけを読む。値の中の `|` は `\|` と書く。

| 欄 | 内容 | 探す場所 |
| --- | --- | --- |
| `{{計画の置き場所}}` | 計画をまとめて置くフォルダー | |
| `{{計画名}}` | 英小文字・数字・ハイフンだけ。計画のディレクトリの名前と同じ。作業名の頭にも付く | |
| `{{機能ブランチ}}` | `feature/<計画名>` | |
| `{{PR のタイトル}}` | 機能の PR のタイトル。平易な Conventional Commits（後方互換の無い変更なら `!` を付ける）。先頭の `WIP:` はスクリプトが付け外しするので書かない | 前の計画、`git log --oneline` |
| `{{インストール}}` | 依存を入れるコマンド | CI の設定、前の計画 |
| `{{静的解析}}` | 静的解析のコマンド（なしにできない） | `package.json` などのスクリプト、CI の設定 |
| `{{テスト}}` | テストのコマンド（なしにできない） | 同上 |
| `{{テストの範囲}}` | 書く・書かないテスト（単体だけ、E2E は書かない、など） | `TESTING.md`、CLAUDE.md、利用者 |
| `{{UI の方針}}` | UI の部品の方針。UI が無ければ「なし」 | CLAUDE.md、ディレクトリの規則、利用者 |
| `{{PR の決まり}}` | コミットメッセージと機能の PR の本文の追加の決まり。無ければ「なし」 | CLAUDE.md、前の計画 |
| `{{ADR のディレクトリ}}` | リポジトリの中の ADR の置き場所 | `docs/adr/` など |
| `{{許可するコマンド}}` | ワーカーに追加で許すコマンドを文章で。無ければ「なし」 | 計画の手順で使うコマンド |
| `{{許可するコマンドのルール}}` | `{{許可するコマンド}}` を Claude Code の許可ルールにしたもの（任意。無ければ「なし」） | |
| `{{E2E}}` | E2E を流すコマンド、流す前に要ること（プレビューのラベルとデプロイ、モデルの中継、手元の設定ファイルなど）、コミットする記録の置き場所。仕上げのワーカーが最後の push に流し、変わった記録を読んでからコミットする。E2E が無ければ「なし」 | CLAUDE.md、`docs/` の E2E の手順、`package.json` のスクリプト |

`{{許可するコマンドのルール}}` は、指揮役がワーカーに `--settings` で渡す。auto mode の分類器は文章の `{{許可するコマンド}}` を許可として読まないので、外部に書き込むコマンド（PR のラベルなど）はここに書かないと拒否されうる。

- ルールを 1 つずつコードの書式で書き、「、」で並べる（例: `` `Bash(gh pr edit * --add-label preview)`、`Bash(gh pr view *)` ``）
- `*` はサブコマンドの後に置く。プログラム全体を許すルール（`Bash(gh *)`）や、何にでも付けられるコマンドのルール（`Bash(echo *)`）は書かない。`*` は `$(…)` で埋め込んだコマンドまで通すことがある。指揮役は広すぎるルールを見つけると、ワーカーを起動しない
- 計画書の手順では、許可したコマンドを単独で実行させる（`&&`・`;`・`|` でつなぐと、ルールが効かずに分類器に回る）

```md
## プロンプトに入れる値

| 欄 | 値 |
| --- | --- |
| `{{計画の置き場所}}` | `~/Documents/<プロジェクト>/plans` |
| `{{計画名}}` | `<計画名>` |
| `{{機能ブランチ}}` | `feature/<計画名>` |
| `{{PR のタイトル}}` | `feat(<範囲>): <平易な要約>` |
| `{{インストール}}` | `pnpm install --frozen-lockfile --prefer-offline` |
| `{{静的解析}}` | `pnpm check && pnpm check-types` |
| `{{テスト}}` | `pnpm test` |
| `{{テストの範囲}}` | 単体テストだけを書く（E2E は書かない） |
| `{{UI の方針}}` | なし |
| `{{PR の決まり}}` | なし |
| `{{ADR のディレクトリ}}` | `docs/adr/` |
| `{{許可するコマンド}}` | 機能の PR に `gh pr edit <番号> --add-label preview` でラベルを貼ってよい。`gh pr view`・`gh pr checks`・`gh run view` を許可する |
| `{{許可するコマンドのルール}}` | `Bash(gh pr edit * --add-label preview)`、`Bash(gh pr view *)`、`Bash(gh pr checks *)`、`Bash(gh run view *)` |
| `{{E2E}}` | なし |
```

E2E があるリポジトリの例（プレビューに手元から流し、記録をコミットする）。

```md
| `{{テストの範囲}}` | 単体テストと統合テストを書く。E2E は `apps/e2e/tests/dashboard-pages.e2e.ts` の表に行を足すだけにする（流して記録をコミットするのは仕上げ） |
| `{{許可するコマンド}}` | 機能の PR に `gh pr edit <番号> --add-label preview` でラベルを貼ってよい。`pnpm test:e2e <PR 番号>` で E2E を流してよい |
| `{{許可するコマンドのルール}}` | `Bash(gh pr edit * --add-label preview)`、`Bash(gh pr view *)`、`Bash(gh pr checks *)`、`Bash(gh run view *)`、`Bash(pnpm test:e2e *)` |
| `{{E2E}}` | `pnpm test:e2e <PR 番号>`（PR に `preview` ラベルを貼り、デプロイが終わってから流す。AI のモデルは手元の中継を通す。記録は `apps/e2e/.e2e/cache/` にコミットする。手順は `docs/e2e-testing.md`） |
```

計画書の本文で値を指すときは `{{静的解析}}` のように書いてよい（ワーカーが表の値で読む）。表に無い欄（`{{目的}}` など）は残さない。

## 決めたこと

この計画で、どう作るかについて案を 2 つ以上比べて決めたことを 1 行ずつ書く。無ければ「なし」と書く。製品の判断（何を作るか）は要件定義書の「決めたこと」にあるので、ここに写さない（決定と学びの記録が両方を読む）。ADR にするかどうかはここでは決めない。

```md
## 決めたこと

ADR にするかどうかは、ここでは決めない（全フェーズの後の「決定と学びの記録」で決める）。

| # | 決定 | 比べた案と採らなかった理由 | 選んだ理由 | 根拠と出典 | 関係するフェーズ |
| --- | --- | --- | --- | --- | --- |
| 1 | <「〜する」で言い切る> | **<案>**：<採らなかった理由> | 技術：<…>。業務：<…> | <実測（日付・環境・コマンド）、公式のドキュメントの URL、利用者の判断（日付）、または「見立て」> | 1・3 |
```

- 選んだ理由は、技術と業務の両方を書く（片方が無ければ「業務：—」）
- 測っていない予想は「見立て」と書く。`check-plan` は見立ての決定を `assumptions` に並べる

`````md

フェーズ 1 の push の後に、機能の PR（`feature/<計画名>` → `main`）を作るとき、そのまま本文に使う。

## マージの後に行うこと

- <要件定義書の完了の条件のうち、マージの前に確かめられないもの（同じ文で）>

- <機能全体で壊してはいけない既存の挙動>

## マージの方法

マージコミットでマージする。
````
`````

- 「マージの後に行うこと」は、マージの後にしかできないことだけにする（PR の本文にそのまま写り、人がマージの後に読む）。マージの前の確認は、計画書の「push の後の確認」か仕上げが受け持つ。`check-plan` は、「マージの前」を含む行を `warnings` に出す
- 要件定義書の完了の条件は、すべて「機能の完了の条件」か「マージの後に行うこと」に同じ文で写す（文末の句点の有無と空白の違いは見ない。後ろに確かめ方を書き足すのはよい）。`check-plan` は、写していない条件を `problems` に出す。要件を変えるときは、利用者に聞いてから要件定義書の側も直す
- 先頭の注意の「まだマージしない」は消さない（指揮役がこの文で、仕上げ前の PR を見分ける）
- 「進捗」には、作業名ごとにちょうど 1 行と、最後に固定の行 `- [ ] 決定と学びの記録` を置く。ワーカーがこの行にチェックを入れる
- チェックボックスは「進捗」だけに使う。GitHub は本文のチェックボックスをすべて数えて、PR の一覧に「n of m tasks」と出す。「機能の完了の条件」は箇条書きにする

## フェーズの計画書

1 フェーズに 1 ファイル。ファイル名は `phase-<2 桁の番号>-<英小文字とハイフンの短い名前>.md`。冒頭に作業名を書く（指揮役とスクリプトはこの行で計画書を見つける）。

### 計画が決めること、ワーカーが決めること

計画書が決めるのは、人の判断が要ることと、フェーズをまたいで合わせることだけにする。ワーカーは CLAUDE.md と既存のコードを読み、残りを自分で決める。

| 計画書が決める | ワーカーが決める（書かない） |
| --- | --- |
| 約束: 後のフェーズや外（画面・API の使い手・DB・外部サービス）が頼る名前、型と形、エラーの種類と返し方、利用者に見える文言、表と列と制約、イベント・Cron・キューの名前 | 関数の分け方と中身、内部の名前、export するか |
| 作り方: 案を比べて決めたこと、壊れやすい手順（マイグレーションの順、退避と戻し方）、権限の確かめと入力の検査の置き場所 | 問い合わせの組み立て（JOIN、batch の分け方）、SQL と DDL の文 |
| テスト: ケースの名前と期待する結果（返す値の形、エラーの種類、残る状態、送る中身）、境界の値 | テストの準備の値（日時、件数、ID）、ケースの分け方、補助の関数 |
| 完了の条件と確かめのコマンド | 見た目の細部（CSS、部品の組み立て） |

細部を書いても、合わないときにワーカーが直すだけになる。ある製品の 4 つの計画（2026-11-08〜10）では、計画書の 7 割が実装とテストの細部で、46 フェーズのすべてでワーカーが平均 10 か所を直した（SQL の順、export、テストの値など）。細部を計画に書くと、書く時間、点検が読む時間、ワーカーが直す時間がかかる。

```md
# フェーズ 1：<要約>

- 作業名：`<計画名>-p1`
- 依存：<前のフェーズで作るもの。無ければ「なし」>

## 目的

<このフェーズで解く問題と、終わったときに何ができるか>

## 前提

- <ワーカーが知らないと誤る、確かめた事実と根拠（ファイル:行、コマンドの出力、ドキュメントの URL）>

## 変更するファイル

- `<パス>`：<何を変えるか>

## 約束

- <後のフェーズや外が頼るもの（上の表）。名前と形を、そのまま使える具体さで>

## 従う決まり

- <このフェーズで守る設計の決まりを、今のリポジトリの名前で具体的に（例: 通知先の更新は `version` を条件に入れ、更新した行数が 0 なら `conflict` を返す）。無ければ節ごと省く>

## 作り方

- <比べて決めた作り方のうちこのフェーズで効くものと、壊れやすい手順。無ければ節ごと省く>

## テスト

- `<テストのファイル>`（<層>: <対象>）
  - <ケースの名前> → <期待する結果>

## 完了の条件

- [ ] <push の前に手元で確かめられる文。確かめのコマンドと、期待する出力>
- [ ] <実物で観察できる結果を少なくとも 1 つ>
- [ ] `{{静的解析}}` が通る
- [ ] `{{テスト}}` が通る

## push の後の確認

- <プレビュー環境や CI の後でしか確かめられないこと。無ければ節ごと省く>

## 変えてはいけないこと

- <このフェーズで壊してはいけない既存の挙動。無ければ「なし」>

## 対象外

- <このフェーズでやらないこと。無ければ「なし」>
```

- 「約束」は、後のフェーズの計画書がその名前と形をそのまま使う。外に見える振る舞い（API の応答、画面の文言、表）は、要件定義書の振る舞いと同じ言葉で書く
- 「従う決まり」は、計画のスキルが設計の決まり（`references/design/`）から、このフェーズに当てはまるものを写したもの。ワーカーは設計の決まりのファイルを読まないので、ここに無い決まりは届かない。リポジトリの CLAUDE.md に既にある決まりは書かない
- 「変更するファイル」は目安。ワーカーは、目的に要るファイル（型や import でつながったものなど）を足してよい
- 「テスト」のケースは振る舞いの水準で書く。境界の値は、要件定義書や約束にある数（上限が 20 文字なら 20 文字と 21 文字）を書き、準備の値は書かない
- 「完了の条件」「変えてはいけないこと」「対象外」は空にしない（無ければ「なし」）。「変えてはいけないこと」と「対象外」は、仕上げが機能の PR の本文に集める
- 「完了の条件」は `- [ ]` のチェックボックスにする。ワーカーは 1 つずつ確かめてから commit する。push の後にしか確かめられないものを混ぜない
- 「push の後の確認」は、そのフェーズのワーカーではなく、次のフェーズのワーカーが自分の push の前に確かめる（ワーカーは push の後に CI を待たない）。最後のフェーズの分は仕上げが確かめる。プレビュー環境はそのとき、まだ前のフェーズの push の状態にある
- E2E を流すことと記録することは、ここにも「完了の条件」にも書かない。仕上げのワーカーが、最後の push に `{{E2E}}` を 1 回流す
- 確かめのコマンドは、計画を書くときに手元で流して、意図した出力が出ることを確かめたものにする
