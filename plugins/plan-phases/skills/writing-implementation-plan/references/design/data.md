## 決めること・決めないこと

- 決める: 正本と派生データ、同時に動いたときの書き込み、重複と再試行、時刻と順序、互換性を保つ変更の手順、バッチと取り込みの形、個人データの保持と削除。
- 決めない: 品質特性の選び方（領域）。Result・ポート・境界の検査の書き方（コード）。表と列の形、索引、作り直しの手順（テーブル）。製品の上限（技術の既定値。公式のドキュメントで確かめる）。送り先の記録（セキュリティ）。通知（観測）。

## 1. 非機能要件の数字

- 操作ごとの応答時間（p50 / p95 / p99）、可用性、失ってよいデータ、止まってよい時間、許容する遅れ、負荷を依頼主と数字で決め、領域の文書に書く。数字ごとに確かめ方（Traces、死活監視、復元の試験、照合のジョブ）を決める。
- 厳しい数字は要る機能だけに付ける。止まってよい時間は、基盤と自動の再試行で戻る範囲か、人が営業時間内に直せる範囲にする。
- D1 は 1 件ずつ処理するので、1 リクエストで D1 を呼ぶ回数を減らす（N+1 は `batch()` か結合）。

## 2. データの地図

- 正本は 1 つにし、ほかは作り直せる派生データにする。保存先を足すたびに、データの地図（例: `docs/domain/data-map.md`）に、正本か派生か、出どころ、更新の経路、作り直す手順、削除の伝わり方を書く。
- 派生データ（Vectorize、AI Search、KV、集計表）はリクエストの中で直接書かず、outbox を通す。更新の経路は 1 つにする。作り直しでメールなどの副作用を繰り返さない。
- 非正規化した値は、正本と同じ `batch()` で更新する。
- 業務で見せる AI の出力（文字起こし、要約、分類）は正本として、モデルとその版、プロンプトの版、元の文書の ID と一緒に保存する。検索の埋め込みは派生でよく、モデルを変えるときは並べて作ってから切り替える。

## 3. 同時に動いても正しくする

D1 は 1 文か 1 回の `batch()` の中だけが直列化可能。呼び出しを分けた「読む → 判断する → 書く」は守られない。

1. 書き換えうる行は、読んだ `version` を条件に書き（`WHERE id = ? AND version = ?`、`version = version + 1`）、`meta.changes` が 0 なら競合のエラーを返す。
2. 加算は DB の中で行う（`SET n = n + 1`）。
3. 「まだ無いこと」の判断（予約枠、残高、ユーザー名）は、一意制約か `INSERT … SELECT … WHERE NOT EXISTS` の 1 文にする。複雑なら対象ごとの DO の `transactionSync` にする。
4. 条件付きの書き込みが 0 件でも batch は進む。同じ batch の outbox や監査の INSERT にも同じ条件（`WHERE EXISTS (… AND version = ?)`）を付け、UPDATE より前に置く。
5. DO では判断と書き込みを同期の区間に閉じ、外部への `fetch` の await をまたいで前提を持ち越さない。
6. 一意性、割り当て、採番、取り出し、ただ 1 つであること（セッション、ロック）は、D1 の primary か対象ごとの DO で決める。複製、KV、キャッシュ、2 つのストアにまたがる判断では決めない。外部への送信と課金の前は厳密に守り、ほかで後から補償するかは業務が決める。
7. 判断に使う読み取りは primary から行う（Sessions API の `first-primary`。Hyperdrive はキャッシュを切る）。書いた直後の画面は、応答の bookmark を次のリクエストで送らせる。書いてから Queue などで知らせるときは、bookmark を載せるか、受け手が primary を読む。
8. PostgreSQL では、複数行の不変条件を `SERIALIZABLE` と再試行か `FOR UPDATE` で守る。

## 4. 重複と再試行

- 入口（Queues、Workflows のステップ、DO の alarm、Cron、webhook、利用者の再送信）は、すべて「少なくとも 1 回」届く前提にする。
- 処理済みのキーの INSERT（例: `processed_messages`、主キー `(consumer, key)`）を、効果と同じ `batch()` に入れる。一意制約の違反は処理済みとして ack する。
- キー: Queue と outbox は event_id、webhook は相手のイベント ID、alarm は予定した処理の ID、ステップはインスタンス ID とステップ名、Cron は予定時刻（使えるかは公式のドキュメントで確かめる）。
- 利用者の送信: 画面がフォームを開いたときに request ID を作る。API はそれを状態と同じ batch で記録し、重複なら前回の結果を返す。同じ ID を外部への冪等キーまで引き継ぐ。
- Queues の consumer は、書き込みが成功してからメッセージごとに `ack()` し、失敗は `retry()` する。失敗を握りつぶして正常に返さない。
- outbox は状態と同じ `batch()`（DO は `transactionSync`）で書く。順序は保証されないので、イベントに集約の version を持たせ、受け手は `WHERE version < ?` で古い更新を捨てる。未配信の最も古い行の経過時間を監視し、DLQ は 1 件で通知する。DLQ は原因を直してから元の冪等キーで送り直す。
- 外部への副作用（送信、決済）は、相手の冪等キー（例: 決済の API の冪等キー）を使う。無いなら「多くとも 1 回」（送信済みを先に条件付きで記録してから送る）か「少なくとも 1 回」かを業務と決める。
- webhook は、署名を検証 → 原文を R2 か D1 に保存 → すぐに 200 → Queue で処理、の順にする。双方向の同期では、値が変わらない更新を外に出さず、自分が書いた版と同じ webhook を捨てる。

## 5. 障害と時間

- タイムアウトは「結果不明」という独立した失敗にする。自動で再試行するのは、冪等な呼び出しか冪等キー付きの呼び出しだけ。ほかは相手に照会して突き合わせるか、人に回す。
- 再試行には上限とゆらぎ付きの指数の間隔を付け、恒久的なエラーは再試行しない。タイムアウトは `AbortSignal.timeout` で書く。Workers の `Date.now()` は I/O まで進まないので計測に使わない。
- 外部の I/O、Queue、Workflow をまたぐ書き込みは、読んだ version を条件にする。拒否されたら読み直すか止める。ロックの表やリースは自作しない（R2 は `onlyIf`）。
- 前後は version で決め、到着順や送り手の時刻で上書きしない。端末で作るデータは、一意なキーで追記するだけにする。
- 時刻はサーバーの UTC（epoch ミリ秒）で記録する。端末の出来事は、発生・送信・受信の 3 つの時刻を残す。イベントは `occurredAt` と `recordedAt` を持ち、集計は `occurredAt` で行う。営業日と、その時点の税率などの値は、書き込みのときに決めて保存する。
- 主キーは UUIDv7 にし、ID の並びで前後を判断しない。autoincrement を外に出さない。2^53 を超えうる外部の ID は文字列にする。業務の連番は、D1 の 1 文（`COALESCE(MAX(no), 0) + 1` と一意制約）か DO のカウンタで振る。

## 6. 変更と互換性

- 開いたままのタブ、古いメッセージと DLQ、実行中の Workflow、DO ごとに版の違う SQLite、古い形の行は、新しいコードと共存する前提にする。
- API とイベントに足してよいのは、省略できる項目だけ。名前は変えず、新しい名前を足して両方に書き、読み手が無くなってから古い方を消す。消した名前は使い直さない。列挙に値を足すときは、古い読み手の逃げ道を先に出す。公開 API（例: `/api/v1`、MCP）は、版を並べて出す期間と終え方を決める。
- リクエストは厳しく検証してよい。レスポンスとイベントは寛容に読む（知らない項目は無視し、知らない `kind` には逃げ道を出す）。zod の `z.object` は知らないキーを捨てるので、JSON の列は部分的に更新するか、知らない項目を保つ。JSON の列は `v` を持つか足す項目を省略できる形にし、読み手が過去の形をすべて受ける。
- 公開するイベントと Queue のメッセージには、型の名前と `version` を持たせる。
- DB の変更は、広げる（NULL 可か既定値のある列、新しい表）→ 両方に書く → 埋める（小分けに、業務時間外に Workflow で）→ 新しい形だけを読む → 縮める（古いタブ、メッセージ、Workflow が無くなってから）の順にする。段ごとに本番へのデプロイが要る。機能の PR のマージは 1 回のデプロイなので、縮めるは別の計画にする。
- マイグレーションは SQL を手で書き、コミットした後は書き換えない。

表を作り直すとき（`ALTER TABLE` でできない変更だけ）

1. `ADD COLUMN`（`CHECK` 付きも可）で済まないかを先に確かめる。`ADD CONSTRAINT` は D1 で使えない前提にし、使えるかは公式のドキュメントか実測で確かめる。
2. 参照される表は「退避の表に写す → 消す → 同じ名前で作る → 戻す」の順にする（新しい表に写して名前を変える順は、子の行があると確定のときに失敗する）。
3. D1 では `PRAGMA foreign_keys = OFF` が効かず、`defer_foreign_keys` は CASCADE を止めない。親を消すと `ON DELETE CASCADE` の子の行がエラー無しに消えるので、子も退避するか、CASCADE を使わない。
4. `INSERT … SELECT` は両側の列を明示する（古い表に無い列の名前は文字列として入る）。
5. トリガーとビューを作り直す。子の行の入った DB で流し、前後の件数を比べる。

Workflows を変えるとき

- 副作用は `step.do` の中だけで起こす。時刻、ID、乱数はステップの戻り値にする。外部への冪等キーは、インスタンス ID とステップ名から作る。
- 実行中のインスタンスがあるあいだは、ステップの名前と順序を変えない。変えるなら別の名前の Workflow を出す（実行中のインスタンスが新しいコードで再開するかは、公式のドキュメントか実測で確かめる）。

## 7. 派生データ・バッチ・取り込み

- 射影を作り直す元（outbox をイベントの表として残すか、正本から計算し直すか）を決める。新しい射影は並べて作ってから切り替える。書いた直後の画面は、コマンドの戻り値で描く。
- バッチは、日付で固定したスナップショット（例: 夜間に D1 から R2 へ書き出したもの）を入力にした `(snapshot, asOf, params) => output` にする。出力は実行の ID を付けて別に書き、manifest かポインタで切り替える。D1 に戻すときは Queue で量を絞り、業務時間外に行う。
- 分析は R2 か BigQuery に分け、日付の区切りごとに上書きして冪等にする。外部の利用者に任意の SQL を許さない。
- 照合: Cron から Workflow で、射影と正本の差、派生ストアの件数と ID、未配信の outbox と DLQ、外部の記録、復元の試験、バッチの件数と合計を確かめ、差はまず通知だけにする。誤りは打ち消しの記録で直す。
- 取り込みは、段ごとに入力と出力の型を決め、I/O は最初と最後だけにし、途中は純粋な関数（変換 `(a: A) => B`、検査 `(a: A) => Result<A, E>`）にする。行ごとの冪等キー（ファイルの ID と行の番号）を効果と同じ batch で記録し、そこから再開する。元のファイルを R2 に残す。大きなファイルは区切る。

## 8. 個人データと AI

- データの種類ごとに利用目的と保持期間を決め、過ぎたら Cron で消す。データの地図の「削除の伝わり方」には、写しの場所（D1、outbox・Queue・DLQ、R2、Vectorize、KV、Logs、AI Gateway、Workflow の状態、Time Travel）を含める。製品の保持期間は公式のドキュメントで確かめる。
- Queue、outbox、ログには ID だけを載せる。消せない場所に個人データを置くなら、鍵を消す方法（crypto-shredding）を最初から設計する。
- 利用者に見せた AI の回答を記録する。人に関わる判定は人が確かめる。外部のモデルに送る範囲を最小にし、学習に使われない設定かを確かめる。AI Gateway には本番で本文を記録させない（`cf-aig-collect-log-payload: false`）。モデルかプロンプトを変える前に、個人情報を含まない試験用の入力で前の結果と比べる。

## 計画に書くこと

- 「従う決まり」: このフェーズに当たる決まりを、今のリポジトリの名前で写す（例: `orders` の更新は `version` を条件にし、`meta.changes` が 0 なら `OrderConflict` を返す。outbox の INSERT は同じ条件で UPDATE の前に置く）。
- 「約束」: イベントの名前と version、変えない Workflow のステップの名前。
- 「作り方」: 書き込みごとの条件と 0 件のときの返し方、入口ごとの重複を除くキーと記録する表、外部への冪等キーとタイムアウトの後の扱い、データの地図に足す行、DB の変更のどの段を出すか、作り直す表の手順と退避する子の表、取り込みの段と再開の位置。
- 「テスト」: 古い version の書き込みが競合になる。同じキーを 2 回処理しても効果が 1 回。条件が外れたら outbox が増えない。古い形の行とメッセージを読める。子の行の入った DB で、マイグレーションの前後の件数が同じ。取り込みを止めて再開しても二重に入らない。
- 依頼主と決める事項が要件定義書に無ければ、推測で決めず、利用者に聞いて要件定義書を直す。

## 依頼主に確かめること

- 応答時間、可用性、止まってよい時間（人が対応する時間帯）、失ってよいデータ、画面ごとに許容する遅れ。
- 厳密に守るか、後から補償するか（在庫の超過、予約の重なり）。
- 遅れて届く記録を捨てるか、過去の日を計算し直すか。
- 冪等キーの無い外部への送信を、「多くとも 1 回」にするか「少なくとも 1 回」にするか。
- 取り込みで、ファイル全体を拒むか、正しい行だけ取り込んで誤りを返すか。
- 個人データの利用目的と保持期間、要配慮個人情報の同意、外部のモデルに送ってよい範囲。
- 業務の連番の欠番を許すか。公開 API の古い版を出し続ける期間。

## CLAUDE.md に足す候補

- 書き換えうる行は `version` を条件に書き、更新した行数が 0 なら競合を返す。
- 少なくとも 1 回届く入口は、処理済みのキーを効果と同じ `batch()` で記録する。
- 外部 API のタイムアウトは結果不明として扱い、冪等キーが無ければ自動で再試行しない。
- マイグレーションは SQL を手で書き、コミットした後は書き換えない。Queue・outbox・ログには ID だけを載せる。

## 確認の問い

- 計画が変える書き込みのそれぞれに、条件（version）と 0 件のときの返し方が書いてあるか。
- 同じ batch で、条件付きの UPDATE の後ろに条件の無い INSERT を置いていないか。
- 一意性や採番の判断が、複製、KV、キャッシュ、2 つのストアにまたがっていないか。
- 新しい入口のそれぞれに、重複を除くキーと、それを記録する batch が決まっているか。
- 外部への副作用に、冪等キーか「多くとも 1 回 / 少なくとも 1 回」の決定と、タイムアウトの後の扱いがあるか。
- 派生データをリクエストの中で直接書いていないか。新しい保存先がデータの地図にあるか。
- 列や項目を消す・名前を変える変更が、1 回のデプロイで済む形になっていないか。
- 表の作り直しで、CASCADE の子の行と前後の件数の確かめ方が計画にあるか。
- 実行中の Workflow のステップの名前や順序を変えていないか。
- 取り込みの失敗の扱いと再開の位置が決まっているか。
- 依頼主と決める事項（失ってよいデータ、許容する遅れ、遅れて届く記録、副作用の重複、取り込みの失敗、保持期間）に、要件定義書の答えがあるか。
- 個人データを Queue、outbox、ログに載せていないか。
