# テストの設計の決まり

フェーズにテストを書かせるとき（ほぼすべての変更）と、テストの層・道具・設定に触れるときに読む。

## 決めること・決めないこと

- 決める: 層と置き場所、テストダブルを使う所、Test List の導き方、期待値の出どころ、E2E・AI の機能・受け入れ前の確認の扱い、ワーカーに写すテストの決まり
- 決めない: 判断の切り出し方とポートの形（コード）、実装パターン（領域）、冪等・版・移行の仕組み（データ）、権限と脅威への対策（セキュリティ）、通知のイベント（観測）、道具の選定と版（技術の既定値）

## 層の選び方

| 確かめること | 層（ファイル名、動く場所） | 差し替えるもの |
| --- | --- | --- |
| `parse`、判断、`evolve`、plug-in、金額・日付・営業日の計算、権限の判定、行からの変換 | 単体（`*.test.ts`、Node） | なし |
| ブランド、遷移元の制限、網羅 | 型（`*.type-test.ts`、`tsc`） | — |
| ユースケース、API の手続き、Queue の consumer、Workflow、DO、Cron | 統合（`*.integration.test.ts`、workerd） | 外部サービスだけ |
| 画面の振る舞い | 画面（`*.test.tsx`、jsdom） | API の client（contract から作る） |
| 画面と API をつないだ主な道筋 | E2E（プレビュー） | — |
| AI の出力の質 | 評価（手元の別の project） | — |

- 自分たちの D1、R2、KV、DO、Queues、Workflows は本物を使い、最後の状態を確かめる（流した SQL や呼んだ順番は確かめない）。Queues と Workflows は受け手まで動かす
- テストダブルは外部サービス（メッセージの送信、決済、AI、メール、外部への webhook）だけ。送る命令は送った中身（冪等キーを含む）と件数を確かめ、問い合わせは決まった応答を返すだけで、呼んだかは確かめない
- 同じ場合を複数の層で確かめない。下の層で確かめられるなら下に置き、単体で確かめた分岐は統合では代表 1 つにする
- 重心はサブドメインのパターンで決める。event-sourced と domain model は単体を厚く、統合は最も長い成功の道筋と判断で決まらない端だけ。active record と transaction script は統合を厚く（入口から成功と主な失敗、SQL の端）。E2E はどれも主な道筋 1〜3 本
- お金、テナントの分離と権限、個人情報、外部からの重複した入力、データを失う処理（削除、移行、取り込み）は、パターンを問わず境界の値まで確かめる
- 書かない: 型が保証すること、ライブラリの振る舞い、自明なもの（精査の無い zod の形、定数の表）、画面の静的な見た目、調査用のログ（通知や SLO が頼るイベントは確かめる）、テストのために公開した関数

## 置き場所と実行

- テストは対象の隣に置く。純粋な package には単体と型のテストだけを置き、統合テストはアプリに置く。フェイクと固定値は `src/test-support/` に置き、本番のコードから import しない
- Vitest は projects で単体・画面・統合を分け、`cloudflareTest()` は統合の project にだけ置く。`expect.requireAssertions` と `sequence.shuffle` を有効にし、`retry` は 0 のまま
- 統合の設定で外部の資格情報をすべてテスト用の値で上書きし、`outboundService` で外への通信を失敗させる（保険。外部への通信は注入した `fetch` で確かめる）
- D1 はファイルごとにマイグレーションを当て、各テストの前に表を空にする（マスタはマイグレーションで入れて残す）。`reset()` を使わない
- 時間の目安（単体 ＋ 画面 20 秒、統合 2 分）を超えたら、テストを消さずに層を下げる

## テストケースの決め方

計画を書く Claude がこの手順で Test List を導く。

1. 業務の規則、入力と今の状態、出力（Ok の形と Err の `kind` の一覧）、入力ごとの範囲・単位・作り手を書き出す
2. 入力ごと、縛り合う入力の組、出力ごとに区分を作る。Err の `kind` と Ok の形に少なくとも 1 ケース。要件定義書の振る舞いの例は 1 ケースずつにし、その言葉をテストの名前にする
3. 境界は on と off（等号は 3 つ）。on の値は仕様の数字
4. 例外の区分は 1 回だけ確かめ、組み合わせない。多すぎるなら関数を分ける
5. 不正な入力は `parse` でだけ確かめる

| 入力 | 境界と落とし穴 |
| --- | --- |
| 時刻と暦 | 締めの時刻の 1 ミリ秒前 / ちょうど、`14:59:59.999Z` / `15:00:00.000Z`、月末、2/29、年末、締め日、連休、振替休日 |
| 金額と税 | 0 / 1、上限 / 上限 + 1、閾値の前後（税込か税抜か）、端数がちょうど 0.5、軽減税率の混在、行ごとか請求書・税率ごとか |
| 文字 | 全角の数字と記号、空白だけ（全角を含む）、似た文字（`〜` と `～`、`−` と `ー`）、文字数 N / N + 1 と数える単位 |
| 省略可能な項目 | キーが無い、`null`、`""`、空白だけ。「無い」にそろえる境界で 1 回 |
| 状態の遷移 | 許されない遷移は今の状態ごとに 1 ケース。同じ命令の繰り返しは冪等 |
| 一覧とテナント | 0 件、1 件、重複、1 ページの件数 + 1。他のテナントの実在する ID は見つからない（ID を受け取るユースケースごと） |

## 期待値の出どころ

- 期待値は要件定義書から導く。コードを読んで作らず、今の出力や本番の関数で作らない
- 導けなければ利用者に聞く。業務の判断なら「依頼主に確かめること」として返し、要件定義書を直してから計画に書く。お金、権限、個人情報、テナントと domain model の期待値は必ず確かめる
- 決めずに進めると利用者が決めたものは、Test List に `test.todo("要確認: <問い>")` と書き、その振る舞いをフェーズと機能の PR の本文の「対象外」に書く。仮の値で実装させない
- 今の振る舞いを固定するテストは名前に「[現状]」を付ける。お金と権限では人が確かめた値だけを使う

## 単体テスト

- 返り値の全体を `toEqual` で比べる。受け付ける表と拒む表を分け、拒む表は `satisfies Record<E["kind"], …>` にして `kind` の書き忘れを型検査で止める
- 固定値は本物の `parse` で作り（`as` を使わない）、Object Mother は既定値を持つ関数にし、時刻は値で渡す（`Date.now()` を使わない）
- 性質ベースは、往復、按分、営業日の計算、状態の多い core の集約に足す。値は `parse` を通して作り、有効と不正は別の性質にし、反例は例の表に残す
- plug-in は、登録したすべてに同じ契約の表を流す

## 統合テスト

- ユースケースごとに、すべての書き込みと外部への送信を通る最も長い成功の道筋 1 本と、判断では決まらない端（他のテナント、古い version の衝突、同じメッセージや webhook の 2 回目、署名の誤り、外部の 429・500・タイムアウトの後の状態）を確かめる
- 組み立ては本番と同じ関数で、差し替えるのは時刻、ID、外部への `fetch` だけ（ID と時刻は固定の値。SQL の既定値の現在時刻に頼らず、時刻はアプリから渡す）。準備は本番の書き込みの経路で行い、結果は本番の読み取りの経路で読み直す（DO は新しい stub から）
- 外部への送信は記録する `fetch` を注入し、記録の全体を 1 つの `toEqual` で比べる。応答の固定値は相手の文書か実際の応答から写す。HTTP でない外部は自分たちの薄いアダプタのフェイクにする。MSW を使わない
- 失敗の経路は、本物のバインディングを包んで指定の操作だけを失敗させて確かめる。アダプタを直接テストするのは、割り込ませにくい並行の SQL と大事な読み取りだけ
- Queues は同じメッセージを 2 回渡し、前の版の形のメッセージも処理できることを確かめる。Workflows は `await using` で片付け、Cron の「今」は `scheduledTime` から取り、`waitUntil` は時間で待たない
- 入力の数でバインド変数が増える SQL は上限 + 1 件以上で試し、複合の SELECT の数と LIKE のパターンの長さの上限もテストで守る（上限は公式のドキュメントで確かめる）。大事な問い合わせは `meta.rows_read` を予算で確かめ、`EXPLAIN QUERY PLAN` は性質だけを見る

## データの正しさ

状態を作ってから 1 手ずつ進め、時間差で競争させない。

| 仕組み | テスト |
| --- | --- |
| 条件付きの書き込み | 同じ version を読んだ 2 つの更新の 2 回目が衝突し、outbox と監査の行が増えない（batch でも） |
| 一意性、取り出し | 同じ値の 2 回目が「登録済み」。取り出しの 2 回目は別の行か何も無い |
| 処理済みのキー、request ID | 2 回目は効果が無い。request ID なら前回の結果を返す |
| 外部への副作用 | 冪等キーを送る。記録を確定してから送る。タイムアウトは「結果不明」で、自動で再試行しない |
| webhook、順序 | 署名の誤りは保存しない。同じイベント ID は効果なし。古い版や古い `attempt` は何も変えない |
| DB の変更 | 古い形の行を入れてから新しいマイグレーションを当て、今の `parse` で読める。作り直しは親と子に行がある状態で当てる。マイグレーションの SQL の形を文字列で検査する。知らない項目を持つ JSON の列は、書き戻しても残る |
| 取り込み | 誤りの一覧を返し、2 回で重複しない。BOM 付き、Shift_JIS、先頭の 0 が落ちた値 |

## API の境界

- 手続きは HTTP を通さずに呼び、ミドルウェアやヘッダーを確かめるときだけ入口全体を呼ぶ
- 権限とテナントは「手続き × 役割 × テナント」の表で網羅する（未ログインは 401、権限なしは 403、他のテナントの ID は見つからない）。表に無い手続きがあれば落ちるテストを置き、MCP のツール、キューや Workflow の入口も表に入れる
- 外に出すエラーに内部の `kind`、例外のメッセージ、個人情報が出ないことと、セキュリティのヘッダーと Cookie の属性を確かめる
- ログイン済みの状態は、テストの環境だけの認証の仕組みで作る。webhook は本物の署名で呼び、署名の確認を飛ばす分岐を本番に書かない

## 画面

- 確かめる: 権限で出る操作、検証の表示、楽観的な更新の巻き戻し、IME の変換中の Enter、日時の表示（`Asia/Tokyo`）、サーバーに送る中身、入口のリンクの行き先と今いる画面の選ばれた状態、部品が置き換わったときのフォーカスの移り先、読み上げの名前、色に添えた文字。見た目と文言は確かめず、表示の計算は純粋な関数に出す
- Testing Library で役割とラベルを使って操作する。API の client は Context から受け、テストでは contract から作った router を渡す。偽のタイマーは画面のテストだけで使う

## E2E

- この開発フローでは、フェーズは E2E のテストを足し・直すだけで、流さない。流して記録をコミットするのは仕上げのワーカーで、最後の push に 1 回だけ。E2E を流すことと記録することを、フェーズの「完了の条件」「push の後の確認」と、機能の PR の「マージの後に行うこと」に書かない
- 主な道筋だけにし、読み取りを中心にする。書き込む E2E はテストごとに自分のデータを作る。ページを足すなら、すべてのページが開く表に行を足す
- AI が操作する手順（例: `agent.act`）の後は必ずコードで確かめ、確かめに AI を使わない。期待値は直接書き、アプリのコードを import しない
- E2E の利用者はテスト専用の値（`example.invalid`）にし、本物の資格情報を使わない。テストの名前、場所、指示文を変えると記録し直しになる

## AI の機能

- AI はポートの裏に置き、単体と統合では決まった出力のフェイクにする。壊れた出力（崩れた JSON、項目の欠け、空）が Err になり、利用者にどう見えるかを確かめる
- 評価は CI の関門にしない別の project にし、個人情報を含まない試験用の入力（プロンプトインジェクションを含む）を機能ごとに置く。LLM-as-judge を関門にしない。モデルかプロンプトを変えるときは、評価を流して前の結果と比べることを最後のフェーズの「push の後の確認」に書く

## 受け入れ前の確認

- 計画の段階で次を設計とテストに入れる: 二度押しと「戻る」での再送信、2 人で同じ記録を直す、セッション切れの後の送信、月末・締め日・日本時間の 0 時、異体字・絵文字・長い社名、重複した・順番の入れ替わった webhook
- 認証、テナント、個人情報、webhook、決済、AI への入力に関わる機能では、STRIDE で脅威を 15 分ほど洗い出し、残した脅威を「悪意のある利用者は〜できない」テストにする
- 人が行う確認は、最後のフェーズの「push の後の確認」に書く: 機能ごとに 30〜60 分・1 観点の探索（目的を「〈機能〉を、〈役割〉で、〈方法〉で探り、〈危険〉を見つける」の 1 行で）、利用者向けの画面の実機（iPhone の Safari、アプリの中のブラウザ、Android）、キーボードだけの操作と 200% の拡大。見つけて受け入れたものは最も下の層のテストにする

## ワーカーに写す決まり

ワーカーは計画書と CLAUDE.md だけを読む。CLAUDE.md に無いものを、各フェーズの「従う決まり」に写す。

1. Test List のケースを書く。ケースの分け方と準備の値は自分で決める。やめたケースは、理由を結果ファイルの `--summary` に書く
2. 新しいテストは一度失敗させてから通す（不具合の修正は失敗するテストを先に書く）
3. 既存のテストは読み取りだけにする。期待値を変えるのは、このフェーズで振る舞いを変えたときだけにする。変えたファイルの通っていない分岐は、テストを足すか、足さない理由を結果ファイルの `--summary` に書く
4. 緑にするために、テストを消す・skip・todo にする、確かめを緩める、出力を期待値に写す、時間の上限・再試行・`as`・`any`・`biome-ignore`・スナップショットを足す、をしない。不安定なテストは直さずに報告する。3 回続けて緑にできなければ止まる
5. 期待値が分からなければ、想像で埋めずに `test.todo("要確認: …")` を置く
6. `vi.mock`・`vi.fn`・`vi.spyOn`・スナップショットを使わない。テストに分岐、繰り返し、`try`、計算を書かず、期待値を直接書く。`beforeEach` で状態を共有しない（D1 の片付けは除く）
7. 名前は業務の言葉の事実にする（「停止中の顧客は注文できず、注文は保存されない」）。準備・実行・確認を空行で分け、エラーは `kind` で比べる

## 測る・機械で守る

- カバレッジを目標にしない。下限は純粋な層にだけ置き、測った値との差が 5 ポイントを超えたら上げる。ミューテーションテストは純粋な層に週 1 回流し、PR の関門にしない
- 不安定なテストは再試行で隠さず、再現してから直すか、期限付きで隔離する。本番の不具合は、最も下の層で失敗するテストにする
- Biome（テストのルールと、モック・スナップショット・単体での偽のタイマーを禁じるプラグイン）と dependency-cruiser（本番から `test-support/` を、E2E からアプリのコードを import させない）で守る

## 既存のリポジトリの決まりと違うとき

- リポジトリの CLAUDE.md（や `TESTING.md`）にテストの決まりがあれば、それに合わせる。違う所は計画の README の「決めたこと」に 1 行で書き、決まりの無い所にだけこの決まりを当てる
- 機能の計画では CLAUDE.md を変えない。既存のテストや道具の移行も機能の計画に混ぜない（別の計画にし、1 つの PR で全部を変えない）。大きく作り直す前に統合テストで包む

## 計画に書くこと

- 計画の README: `{{テストの範囲}}` に書く層と書かない層（E2E は「表に行を足すだけ。流して記録をコミットするのは仕上げ」）。「決めたこと」に、リポジトリの決まりと違えたこと
- 「作り方」: テストのために要る形（`fetch` の注入、時刻と ID の差し替え、判断を純粋な関数に出す）
- 「テスト」: Test List。ファイルごとに層と対象、ケースの名前と期待する結果、E2E、確かめないもの、変える既存のテストと理由。準備の値（日時、件数、ID）は書かない（ワーカーが決める）。境界の値は要件定義書や約束にある数を書く

```md
- `<…>/order.test.ts`（単体: `decideCancel`）
  - 発送済みの注文は取り消せない → Err `OrderAlreadyShipped`（発送の時刻を含む）
- `<…>/cancel-order.integration.test.ts`（統合: `cancelOrder` の手続き）
  - 古い version では衝突を返し、何も書かない
  - `test.todo("要確認: 発送準備中の注文は取り消せるか")`
- E2E: なし（注文の一覧の道筋に含まれる）
- 確かめない: 取り消しの理由の文言
```

- 「従う決まり」: 「ワーカーに写す決まり」のうち、CLAUDE.md に無いもの
- 「完了の条件」: 新しいテストに絞り、名前が出るコマンド（例: `pnpm vitest run <ファイル> --reporter=verbose`）。計画を書くときに同じ形で流して確かめる
- 最後のフェーズの「push の後の確認」: 人が行う受け入れ前の確認と、AI の評価の比較

## CLAUDE.md に足す候補

「ワーカーに写す決まり」の 2〜7。計画のスキルが最後の報告に並べ、足すかは利用者が別に決める。

## 依頼主に確かめること

- 仕様から期待値の決まらない業務の規則（端数の丸め方、行ごとか請求書ごとか、閾値が税込か税抜か）
- 営業日の暦、締めの時刻、締め日
- 文字数の上限と数える単位
- 取り込みに誤りがあったとき、正しい行だけ取り込むか全体を拒むか
- 利用者が使う端末とブラウザ、AI の出力で許せる誤り

## 確認の問い

- ケースごとに層と期待値（Ok の形、Err の `kind`、残る状態、送る中身）が Test List にあるか
- 要件定義書から導けない期待値を、推測で埋めていないか
