# テーブルの設計の決まり

変更が表・列・制約・索引・トリガー・マイグレーション、または問い合わせの形（集計、ページ送り、検索）に触れるときに読む。既定は D1（SQLite）。PostgreSQL を使うプロダクトで違う所は「PostgreSQL では」と書く。

## 目次

- 前提: 決めること・決めないこと、既存のリポジトリに合わせる
- 列と制約: 名前と型、主キーと ID、外部キーとテナント、NULL、選択肢の値
- 表の形: 1 つの列に 1 つの値、種類で形が違うもの、木構造、期間と時間枠、状態・履歴・削除、ファイルと検索
- 読み方と変え方: 索引とクエリ、表を変える、スキーマを守る
- 計画: 計画に書くこと、CLAUDE.md に足す候補、依頼主に確かめること、確認の問い

## 決めること・決めないこと

- 決める: 表と列の名前と型、キーと制約、NULL、選択肢の置き場所、木・期間・状態・削除の持ち方、テナントの持ち方、索引、問い合わせの形、表の変え方、列の辞書とスキーマの検査
- 任せる: データ（version、重複と冪等、互換性と段階的な変更、派生データの更新、保存期間と個人データの削除、照合の仕組み）、領域（集約の境界と用語。表と列の名前は用語集の英語にそろえる）、コード（行の `parse`、金額の割り算と丸め）、技術の既定値（SQL の書き方、D1 か PostgreSQL か、テナントごとに D1 を分けるか）、セキュリティ（テナントの分離の検査、監査の記録）

## 既存のリポジトリに合わせる

- ORM（例: Drizzle）でスキーマを書いているリポジトリでは、機能の計画は今の形（スキーマの定義、生成するマイグレーション、名前、ID の形、時刻の型）に合わせる。この文書の既定値と違う所は、計画の README の「決めたこと」に書く。
- 機能のためだけに既存の表を既定値へ寄せない（STRICT や名前のためだけに作り直さない）。
- ORM でも外部キー、子の索引、業務の一意、テナントの複合外部キー、選択肢の CHECK は DB に出す。ORM が出すとは限らない（例: Drizzle の `text({ enum })` は CHECK を出さない）ので、生成された SQL を読んで確かめる。ORM で書けないもの（トリガー、部分索引）は手書きの SQL のマイグレーションにする。
- ORM が生成した作り直しの SQL は「表を変える」の手順と照らす（`PRAGMA foreign_keys` は D1 で効かず、写して名前を変える順は子の行があると失敗する）。

## 名前と型

| 値 | 名前 | 型と CHECK |
| --- | --- | --- |
| 表 | 複数形の snake_case。Better Auth の表はそのまま | — |
| 主キー、外部キー | `id`、`<参照先の単数形>_id`、役割があれば `<役割>_<単数形>_id` | `TEXT` |
| 外部のサービスの ID | `<サービス>_<もの>_id` | `TEXT`（数値の ID も） |
| 時点 | `*_at` | `INTEGER`（epoch ミリ秒） |
| 暦日 | `*_on`（日本時間） | `TEXT`、`x GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]' AND date(x) = x` |
| 真偽 | `is_*`、`has_*` | `INTEGER`、`x IN (0, 1)` |
| 金額、量、件数 | `*_yen`、単位を後ろに（`size_bytes`）、`*_count` | `INTEGER`、範囲の CHECK |
| JSON | `*_json` | `TEXT`、`json_valid(x) AND json_type(x) = 'object'` |
| 概数（緯度経度、確からしさ） | — | `REAL`、`-- REAL: <理由>` |
| 制約 | `<表>_<列>_ck`、`_uq`、`_idx`。トリガーは `<表>_<規則>_<insert/update>` | — |

- 新しい表はすべて `STRICT` にする。日付・真偽・選択肢・JSON は CHECK で形を縛る。
- CHECK には名前を付ける（エラーに名前が出て、型付きのエラーに写せる）。CHECK に `date('now')` のような時刻の関数を書かない。表をまたぐ規則はトリガーにする。
- 金額は円の整数にし、`NUMERIC`、`DECIMAL` を使わない（PostgreSQL でも）。円より細かい単位は最小の単位の整数にし、単位を名前に入れる。
- 時点を TEXT の ISO 8601 にしない。日本時間の日付で集計するなら `date(ms / 1000, 'unixepoch', '+9 hours')` の VIRTUAL の生成列と索引にする。営業日は書くときに決めて `*_on` に保存する。
- SQLite のキーワード（`order`、`group`、`key`、`from`、`to`、`begin`、`end`）を名前にしない。TEXT の列には文字列を bind する。
- PostgreSQL では STRICT と型の形の CHECK は要らない。時点と暦日の型は今のリポジトリに合わせる。

## 主キーと ID

- 主キーは `id TEXT PRIMARY KEY` の UUIDv7 にし、アプリで作る（PostgreSQL でも）。Workers の `crypto.randomUUID()` は v4 だけなので、UUIDv7 を作る関数を共有の部品に置く。ID の並びで前後を判断しない。
- 交差テーブルは 2 つの外部キーの複合主キーにし、`id` を足さない。代理キーの表でも、業務で一意なもの（テナントとメール）は `UNIQUE` にする。
- 業務で見える番号（受付番号）は `id` と別の列にし、1 文の `INSERT … SELECT COALESCE(MAX(no), 0) + 1` と `UNIQUE (tenant_id, no)` で振る。番号の付いた記録は消さずに取り消し、欠番を詰めない。
- 連番の主キーを外へ出さない。整数の鍵は FTS5 の外部コンテンツの表だけに使う。
- `WITHOUT ROWID` は、1 行が小さく（約 200 バイト以下）書き込みが多い表（枠の行、交差テーブル）だけに使う。

## 外部キーとテナント

- 参照はすべて外部キーにし、子の列に索引を張る（複合索引の先頭でよい）。外部キーにできない参照（別の D1、Durable Object、R2、外部のサービス）は、許可の一覧に理由と照合の方法を書く。
- 削除の既定は拒む（NO ACTION か RESTRICT）。1 文で木の一部を消すなら NO ACTION にする。CASCADE は 1 つの集約の中の持ち物だけ、SET NULL は NULL を許す任意の参照だけにし、許可の一覧に書く。`ON UPDATE CASCADE` は使わない。
- 変えさせないトリガーで守る列（`created_by_user_id`）への外部キーを SET NULL にしない。利用者を消すときは行を残して個人情報を消す。
- SQLite は誤った外部キー（参照先が主キーでも UNIQUE でもない、列の順番や型が親と違う、NOT NULL の列に SET NULL）を作るときに通し、最初の書き込みで失敗する。
- テナントの表はすべて `tenant_id` を持ち、複合索引の先頭にする（テナントごとに D1 を分けるプロダクトでは要らない）。親に `UNIQUE (tenant_id, id)` を置き、子は `FOREIGN KEY (tenant_id, <親>_id) REFERENCES <親> (tenant_id, id)` にする。テナントごとの一意は `UNIQUE (tenant_id, …)` にする。

## NULL

- NOT NULL を既定にし、NULL を許す列には `-- NULL: <意味>` を書く。「不明」に `''`、`0`、`-1` を使わない。空文字は `CHECK (x IS NULL OR length(trim(x)) > 0)` で拒む。
- NULL が 2 つの意味を持つなら列を分ける。必要になるまで列を足さない。業務の時刻を DB の既定値で埋めない。
- UNIQUE は NULL の重複を許す。NULL を含む組の一意は、NULL の場合とそうでない場合の 2 つの部分一意索引にする（PostgreSQL では `NULLS NOT DISTINCT` でもよい）。
- NULL を含みうる一覧に `NOT IN` を使わず、`NOT EXISTS` にする。

## 選択肢の値

| 種類 | 置き場所 |
| --- | --- |
| 閉じた集合で、コードが値ごとに分岐する（注文の状態） | 名前付きの CHECK（値を足すには表の作り直し） |
| コードが分岐し、増える見込みがある（コメントの出どころ） | `BEFORE INSERT` と `BEFORE UPDATE OF <列>` のトリガー（作り直すだけで値を足せる） |
| 利用者や運用者が画面で編集する（問い合わせの分類） | 一覧の表（`PRIMARY KEY (tenant_id, code)`、変えない `code`、変えてよい `label`、`is_active`）と外部キー |

- 使わなくなった値は消さずに `is_active = 0` にする。
- PostgreSQL では制約を ALTER で変えられるので、増える見込みのある値も CHECK でよい。

## 1 つの列に 1 つの値

- 正規化した形から始める。崩してよいのは、その時点の値（注文や請求の行に商品名、単価、税率を写す）、消して作り直せる集計の表、履歴の最新の写しとしての状態の列だけ。
- 一覧を 1 つの列に入れない（カンマ区切りも JSON の ID の配列も）。交差テーブルにする。件数の上限は 1 文で守る（`INSERT … SELECT … WHERE (SELECT count(*) …) < ?`）。
- 番号違いの列（`phone1`、`phone2`）は従属する表にする。年や月ごとに表や列を増やさず、行にする。
- 大きな列（文字起こし、webhook の原文）は 1 対 1 の表に分ける。

## 種類で形が違うもの

- 種類が少ないなら 1 つの表と、種類ごとに埋める列の CHECK（`CHECK (kind = 'Bug' OR severity IS NULL)`）にする。種類ごとの列が多いなら共通の表と種類ごとの表にし、親の `UNIQUE (id, kind)` を子が `(<親>_id, kind)` で参照する。種類が無制限なら JSON の列にする。
- EAV を作らない。例外は、業務のデータでなく、検索・集計に使わず、丸ごと読み書きするものだけ（多くは JSON の列で足りる）。
- 複数の親を `target_type` と `target_id` で参照しない。親ごとの交差テーブルか、親が 2〜3 個なら親ごとの外部キーと `CHECK ((a_id IS NOT NULL) + (b_id IS NOT NULL) = 1)` にする。例外は監査の記録とジョブの対象だけで、監査の記録を業務の判断に使わない。
- テナントが足す項目は、定義の表と行の JSON の列にする。その項目で絞り込むなら、型ごとの列を持つ値の表 1 つに閉じ込める。
- JSON の列に ID の参照を入れない。中の値で絞り込むなら VIRTUAL の生成列と索引にし、問い合わせに索引と同じ式を書く。SQLite の JSONB は使わない。

## 木構造

- 既定は `parent_id`（NULL は最上位）と再帰の問い合わせ。自分を親にしない CHECK、`(tenant_id, parent_id)` の自己参照の外部キー、同じ親の中の名前の一意（最上位は別の部分一意索引）、付け替えの循環を拒む `AFTER UPDATE OF parent_id` のトリガーを一緒に作る。
- 再帰には深さの上限か `UNION`（`UNION ALL` でない）を付ける。
- 1 つの一覧に混ぜて並べるもの（フォルダとページ）は、並び順の番号を 1 つの系列にする。
- 1 つの節点が複数の木に属するなら閉包テーブルにする。経路列挙と入れ子集合は使わない。

## 期間と時間枠

`start_at`/`end_at` の列を提案する前に、次に答える。

1. 始まりと終わりは、作るときに必ず決まるか。決まるなら期間の列でよい。
2. 終わりが決まらない、取り消しや再開がある、状態に順番があるか。あるなら状態ごとの出来事の表に分ける。期間の表に `canceled_at` を足さない。
3. 有効期間（料金表、税率、割り当て）か。それなら始まりだけを持つ行にする。
4. 終わりを NULL にしたくなったか。それなら 1 に戻る。持つなら `(ends_at IS NULL OR ? < ends_at)` と書き、`UNIQUE (…) WHERE ends_at IS NULL` で今の行を 1 つにする。

- 時点の期間は半開区間 `[starts_at, ends_at)` と `CHECK (starts_at < ends_at)` にする。暦日の期間は両端を含む `first_on`、`last_on` にする。
- 重なりは DB で拒む。既定は AFTER のトリガー（INSERT と `UPDATE OF` の両方）で、`EXISTS` で探さず「新しい `ends_at` より前に始まる最後の 1 件」の `ends_at` だけを比べる。索引は `(tenant_id, resource_id, starts_at)`。決まった刻みなら枠の行（`PRIMARY KEY (tenant_id, resource_id, slot_at)`）を予約と同じ `batch()` で入れる。複数の資源や在庫と組むなら資源ごとの Durable Object にする。
- 取り消した予約は表から出す。
- PostgreSQL では範囲型と `btree_gist` の排他制約にする（使えるかは公式のドキュメントで確かめる）。時間枠のためだけに PostgreSQL を選ばない。

## 状態・履歴・削除

`status` の列を提案する前に、次に答える。

1. 状態の履歴（いつ、誰が、取り消して再開したこと）を業務で読むか。読むなら出来事の表（`<もの>_status_events`）を正本にし、`status` の列は同じ `batch()` で更新する写しにする。
2. 状態ごとに埋める列があるか。あるなら `CHECK (status <> 'Shipped' OR shipped_at IS NOT NULL)` で縛る。

- 履歴の表は追記だけにし、UPDATE をトリガーで拒む。個人情報は消せる表に置く。出来事の時刻と受け付けた時刻を分ける。
- 一律の `deleted_at` を付けない。業務の状態（`Archived`）にするか、物理的に消して ID だけの削除の記録を残す。使うなら、一意の索引をすべて `WHERE deleted_at IS NULL` の部分索引にし、問い合わせにもその条件を文字で書く（bind しない）。

## ファイルと検索

- ファイルは R2 に置き、D1 には `r2_key`（UNIQUE）、`content_type`、`size_bytes`、`sha256`、`purged_at` を置く。消すのは D1 の印が先で、R2 の物は Time Travel で戻せる期間の後に Cron かキューが消す。差し替えは新しい鍵にする。
- 部分一致は、正規化した検索のキーの列に `instr(key, ?) > 0` で行う（D1 の LIKE はパターンの長さに上限がある）。
- 大きな表は FTS5 の `trigram` の外部コンテンツの表にする。元の表に `seq INTEGER PRIMARY KEY`（外へ出さない）と `id TEXT NOT NULL UNIQUE` を明示し、3 つのトリガーで同期し、`tenant_id` で絞る。元の表に `INSERT OR REPLACE` を使わない。3 文字未満の語は `instr` に回す。
- 意味での検索は Vectorize か AI Search にし、テナントで絞る。

## 索引とクエリ

- 索引は問い合わせの一覧から決める。張るもの: 外部キーの子の列、ページ送りの `(tenant_id, 絞り込み, 並び順, id)`、少ない状態だけの部分索引（条件を問い合わせに文字で書く）。主キーや UNIQUE と先頭が同じ索引を足さない。
- ページ送りはカーソルで行い、OFFSET と OR の条件で送らない。
- グループごとの最新の行は `row_number() OVER (… ORDER BY occurred_at DESC, id DESC)` で取り、`GROUP BY` に無い列を選ばない。2 つの「1 対多」を 1 文で結合して数えず、分けて 1 つの `batch()` で送る。
- 列を明示する。`ORDER BY random()` は絞った小さな集合だけに使う。

## 表を変える

- D1 の ALTER でできるのは、列を足す（NOT NULL なら既定値が要る。外部キーの列は既定値が NULL のときだけ）、VIRTUAL の生成列を足す、列を消す（先に索引を消す）、名前を変える、だけ。型、CHECK、NOT NULL、外部キー、UNIQUE を変えるには表の作り直しが要る（PostgreSQL では ALTER でよい）。
- 作り直しの手順は次の 3 つ。
  - A. 参照されない表: 新しい表を作って写し、古い表を消し、名前を変える。
  - B. 参照される表（子が NO ACTION か RESTRICT）: `PRAGMA defer_foreign_keys = ON` → 退避の表に写す → 古い表を消す → 新しい定義で作る → 戻す → 退避の表を消す。
  - C. CASCADE か SET NULL の子がある表: 表を消すと子の行が消える（NULL になる）。子の行も退避して戻すか、先に子の CASCADE をやめてから B にする。
- どれでも、コピーの列を両側で明示し、消えた索引とトリガーを作り直し、前後の行の数が違えば失敗させる（例: `ok CHECK (ok = 1)` の表に比べた結果を入れる）。行の入った workerd の D1 で試す。
- マイグレーションに `PRAGMA foreign_keys`、`ignore_check_constraints`、`writable_schema` を書かない。

## スキーマを守る

- 列の辞書（例: `docs/db/dictionary.md`）に、列の意味、単位（税込・税抜）、NULL を許す理由、個人情報の区分、外部キーの削除の動き、トリガーが守る規則を書く。
- スキーマの写し（例: `packages/db/schema.sql`）を、マイグレーションを当てた後の `sqlite_schema` と比べるテストを置く。
- スキーマの形の検査（`PRAGMA table_list` と、表ごとの `pragma_foreign_key_list(?)`、`pragma_index_list(?)`）で確かめる: すべての表が STRICT、外部キーの最初の列が索引の先頭、CASCADE・SET NULL・外部キーにしない参照が許可の一覧のものだけ、`PRAGMA foreign_key_check` が空、トリガーの名前の一覧が期待どおり。

## 計画に書くこと

- 計画の README の「決めたこと」: 既定値と違う所（PostgreSQL、`deleted_at`、記録の `target_type` など）、期間と状態の問いの答え、選択肢の置き場所と誰が増やすか、重なりの守り方。
- フェーズの計画書の「前提」: 変える表を参照する子の表と `ON DELETE`。索引を足すなら、今の `EXPLAIN QUERY PLAN`。
- 「約束」: 表ごとの一覧。列の名前・型・NULL の可否（許すなら理由）、STRICT、主キー、UNIQUE、CHECK（名前と条件）、外部キーと `ON DELETE`、索引（名前と列）、トリガー（名前と働き）。DDL の文はワーカーが書く（一覧と違う所が無いかは、制約ごとのテストで確かめる）。
- 「作り方」: マイグレーションのファイル名。ORM なら定義の変更と、生成された SQL で確かめる点。作り直しなら手順（A・B・C）、退避する子の表、作り直す索引とトリガーの名前。新しい問い合わせが使う索引の名前。辞書と写しの更新。
- 「テスト」: 業務の規則を表す制約（業務の番号の一意、期間の重なり、変えてはならない列、選択肢の値、テナントをまたぐ参照）ごとに、違反がエラーになるケース（CHECK の名前、`RAISE` の文字列まで）。選択肢は TypeScript の一覧のすべての値と 1 つの不正な値。集計は子の側に 2 行以上、最新の行は同点の 2 行。形の検査の期待値の更新。NOT NULL ごとのテストは書かない。
- 「完了の条件」: 足した索引の `EXPLAIN QUERY PLAN` の期待する出力（`SEARCH <表> USING INDEX <索引>`）、`PRAGMA foreign_key_check` が空、作り直しの前後の行の数が同じ。
- 「従う決まり」: リポジトリの CLAUDE.md に無い決まりのうち、そのフェーズに効くものを表と列の名前で写す（例: 「`order_lines.order_id` は `orders (id)` への外部キーで CASCADE。`order_lines_order_idx` を張る」）。

## CLAUDE.md に足す候補

計画のスキルが最後の報告に並べる。足すかは利用者が決める。

```md
- 新しい表は STRICT。主キーは UUIDv7 の id。交差テーブルは複合主キー。連番を外に出さない。
- 参照はすべて外部キー。子の列に索引。CASCADE は集約の中だけ。テナントの子は (tenant_id, 親_id) で参照する。
- NOT NULL が既定。NULL を許す列には -- NULL: <意味>。'' や 0 や -1 で「不明」を表さない。
- 金額は円の整数（*_yen）、時点は epoch ミリ秒（*_at）、暦日は YYYY-MM-DD（*_on）。
- 表の作り直しは、参照される表なら「退避 → 消す → 作る → 戻す」。索引とトリガーを作り直す。
- マイグレーションと同じ変更で、列の辞書とスキーマの写しを更新する。
```

## 依頼主に確かめること

- 業務で見える番号の範囲（テナント、店舗、年度ごと）と、欠番を見せてよいか
- 選択肢の値を、運用者が画面で増やすか、開発の変更で増やすか
- 期間の終わりは作るときに決まるか。取り消し、再開、状態の順番があるか。暦日の期間は最後の日を含むか
- 状態の履歴を業務で見るか。削除した後に何を残すか
- 金額は税込か税抜か。注文や請求にその時点の値で残す項目
- 同じ資源の予約が重なってよいか。予約は決まった刻みか
- 2 文字以下の語でも探すか
- テナントが項目を足すか。その項目で絞り込むか

## 確認の問い

- ORM のリポジトリで、生成された SQL に CHECK・外部キー・索引が出ることを計画が確かめているか。
- 新しい参照ごとに、外部キー（テナントの子は `(tenant_id, 親_id)`）、子の索引、`ON DELETE` が表の一覧にあるか。
- 業務で一意なもの（番号、メール、名前）すべてに UNIQUE があるか。NULL を含む組の一意が抜けていないか。
- 選択肢の値の置き場所が、誰が増やすかと合っているか。
- 期間の列と `status` の列に、提案する前の問いの答えがあるか。
- 期間の重なりを、アプリでなく DB（トリガー、枠の行、Durable Object）で拒んでいるか。
- 注文や請求の行に、その時点の値（単価、税率）を写しているか。
- 新しい問い合わせごとに使う索引が決まり、ページ送りがカーソルか。
- 型、CHECK、NOT NULL、外部キー、UNIQUE を変える変更に、作り直しの手順があるか。C に当たる子の表を見落としていないか。
- 作り直す表の索引とトリガーが、すべて作り直しの手順にあるか。
- 業務の規則を表す制約ごとに、違反がエラーになるテストがあるか。
