# 要件定義書の形

`plan-phases check-requirements`、点検（`reviewing-requirements`）、計画のスキル（`writing-implementation-plan`）、決定と学びの記録（`recording-plan-decisions`）が読む形。見出しの文字は変えない（番号は付けてよい）。`check-requirements` は、ここに反するものを `problems`（直すまで計画を書かない）か `warnings` に出す。

## 置き場所と寿命

```txt
<計画の置き場所>/                ← 例: リポジトリの隣の plans/
└── <計画名>/                    ← 計画のディレクトリ
    ├── requirements.md          ← 要件定義書（defining-requirements が書く）
    ├── .scratch/                ← 使い捨ての試作と、事実を確かめたスクリプト
    ├── README.md                ← 計画の README（writing-implementation-plan が書く）
    └── phase-01-<短い名前>.md   ← フェーズの計画書
```

Git の管理外で、リポジトリからは読めない（マージの後も、フローの改善の記録として計画と一緒に残すが、正本ではない）。リポジトリに残すべきものは次へ写る。

| 要件定義書の節 | 写る先 | 写す人 |
| --- | --- | --- |
| 目的 | 機能の PR の本文の「なぜ」 | 計画のスキル |
| 完了の条件 | 機能の PR の本文の「機能の完了の条件」（同じ文で。マージの前に確かめられないものは「マージの後に行うこと」） | 計画のスキル（`check-plan` が確かめる） |
| やらないこと | 機能の PR の本文の「対象外」 | 計画のスキル |
| 用語 | `docs/domain/glossary.md` | 決定と学びの記録 |
| 品質特性 | `docs/domain/characteristics.md` | 決定と学びの記録 |
| 権限とデータのセキュリティの段階 | `docs/security.md` | 決定と学びの記録 |
| 決めたこと | 残す価値のあるものだけ ADR | 決定と学びの記録 |

## 節

この順に置く。（任意）と書いたもの以外は必ず置き、空にしない。書くことが無ければ「なし」と書く（「なし（理由）」でもよい）。

| 節 | 書くこと |
| --- | --- |
| タイトル | `# <計画名>：<1 行の要約>`。計画名は計画のディレクトリの名前 |
| `## 目的` | 誰の、どんな場面の、どんな困りごとを解くか。放っておくと何が困るか。終わったら何ができるようになるか。3〜6 行 |
| `## 材料` | 根拠にした議事録・資料・チケット・会話の出典（日付、パス、URL）。利用者と決めたことは「利用者との会話（YYYY-MM-DD）」 |
| `## 範囲` | `### やること`・`### やらないこと`・`### 後に回すこと` の 3 つ。やらないことは、やると思われそうなのにやらないもの。後に回すことには、やり始める条件があれば添える |
| `## 用語` | この機能で新しく使う業務の語と、意味を決めた語の表。コードの名前は書かない（実装の後に決定と学びの記録が書く） |
| `## 振る舞い` | 場面ごとの表。正常な場合に加え、失敗・空・重複・上限・権限の無い人・同時の操作・取り消しの場面を書く |
| `## 完了の条件` | 番号付きの箇条書き。1 つずつ、確かめられる文 |
| `## 品質特性` | この機能で、作り方を変えるほど効く品質特性の表（応答時間、止まってよい時間、失ってよいデータ、新しさ、量、権限の細かさなど）。無ければ「なし（理由）」 |
| `## 権限とデータ` | セキュリティの段階（A・B・C）、誰が何を見られて何をできるか、扱うデータ（個人情報、履歴の要否、消す必要、失ってよいデータ） |
| `## 外部との連携`（任意） | 連携先と、その制約（送れる件数、返るデータ、止まったときの動き）と、確かめた方法 |
| `## 移行と既存データ`（任意） | 既存のデータと利用者の扱い、切り替えの順番、戻し方 |
| `## 決めたこと` | 製品の判断のうち、案を比べて決めたものの表 |
| `## 計画に任せること` | 要件では決めず、計画が決めてよいこと（技術の選択、データの形、画面の部品など） |

## 雛形

```md
# <計画名>：<1 行の要約>

## 目的

<誰の、どんな場面の、どんな困りごとを解くか。放っておくと何が困るか。終わったら何ができるようになるか>

## 材料

- <YYYY-MM-DD の議事録のパス、資料のパス、チケット、URL>
- 利用者との会話（YYYY-MM-DD）

## 範囲

### やること

- <利用者から見てできるようになること>

### やらないこと

- <やると思われそうなのに、この機能ではやらないこと>

### 後に回すこと

- <いずれやるが、この機能には入れないこと。やり始める条件があれば「（〜ができたら）」と添える。無ければ「なし」>

## 用語

| 業務の語 | 意味 | 同義語・使わない言い方 | 出典 |
| --- | --- | --- | --- |
| <語> | <この機能での意味> | <「〜」とは呼ばない> | <議事録の日付と発言者、資料のページ、利用者との会話> |

## 振る舞い

### <場面のまとまり（例: 支払いを確定する）>

| # | 前提 | 操作・きっかけ | 結果 |
| --- | --- | --- | --- |
| 1 | <状態> | <誰が、何をする> | <画面・データ・通知がどうなる。文言が決まっていれば「」で> |
| 2 | <権限の無い人が> | <同じ操作をする> | <どうなるか> |

## 完了の条件

1. <確かめられる文。「〜できる」「〜される」で終え、画面・機能・データを名前で指す。件数・種類・時間は数字で>
2. <…>

## 品質特性

| 品質特性 | 対象 | 数字 | 確かめ方 | 出典 |
| --- | --- | --- | --- | --- |
| <可用性・応答時間・失ってよいデータなど> | <機能・画面> | <p95 で 1 秒以内、など> | <テスト、監視、照合のどれで確かめるか> | <利用者との会話（YYYY-MM-DD）、議事録> |

## 権限とデータ

- セキュリティの段階：<A・B・C>（<docs/security.md の値、または今回決めた理由>）
- <誰が、何を見られ、何をできるか>
- <扱う個人情報、履歴を残すか、消す必要があるか、失ってよいデータ>

## 決めたこと

| # | 決定 | 比べた案と採らなかった理由 | 選んだ理由 | 根拠と出典 |
| --- | --- | --- | --- | --- |
| 1 | <「〜する」で言い切る> | **<案>**：<採らなかった理由> | 技術：<…>。業務：<…> | <利用者の判断（YYYY-MM-DD）、議事録、公式のドキュメントの URL、試作（.scratch/<ファイル>）、または「見立て」> |

## 計画に任せること

- <技術の選択、データの形、画面の部品など、計画が決めてよいこと>
```

## 書き方の決まり

- **何を・なぜを書き、どう作るかは書かない。** 技術の選択、テーブルや API の形、ファイルの置き場所は「計画に任せること」に回す。ただし、利用者が決めた製品の判断（画面の作法、操作の手順、文言）は、どう見えるかとして振る舞いと決めたことに書く
- **完了の条件は、確かめられる文だけにする。** 「〜できる」「〜される」で終え、画面・機能・データを名前で指し、件数・種類・時間は数字で書く。「使いやすい」「速い」のような確かめようのない言葉を使わない。計画のスキルが、この文をそのまま機能の PR に写す（`check-plan` が同じ文かを確かめる）
- **完了の条件は、振る舞いと対応させる。** 振る舞いの場面のうち大事なものは、どれかの完了の条件で確かめられるようにする。完了の条件に、振る舞いに無いことを書かない
- **事実と判断を分けて、出典を付ける。** 今の作りについて書くことは、コードを読んで確かめたこと（ファイル:行）か、材料にあることだけにする。利用者が決めたことは「利用者の判断（日付）」、測っていない予想と、利用者に聞かずに推奨を採ったものは「見立て」と書く。`check-requirements` は見立ての決定を `assumptions` に並べる
- **ほかの計画や機能を、順番の番号で呼ばない。** 「N 本目」「前の計画」ではなく、機能の名前で呼ぶ。要件定義書の言葉は、機能の PR、コード、画面の文言、ADR に写り、計画が捨てられた後は番号の意味が分からなくなる
- **語を作らない。** 材料にない業務の語が要るときは、意味を決めて用語に書き、出典を「利用者との会話（日付）」にする。同じものの別の呼び方や、場面で意味の変わる語は、どれを使うかを決めて「同義語・使わない言い方」に書く
- **数字には確かめ方を付ける。** 確かめ方の無い数字は、決まっていないのと同じ。厳しい数字は、必要な機能にだけ付ける
- **決まっていないことを残さない。** 「TBD」「未定」「要検討」「適切に」を書かない（`check-requirements` が warnings に出す）。決められないことは、利用者に聞いて決めるか、見立てで決めて「見立て」と書く
- 文は平易な日本語で書く。用語の表に書いた語は、本文でも同じ語を使う
