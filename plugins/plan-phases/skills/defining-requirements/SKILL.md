# 要件を定義する

引数: `$ARGUMENTS`（要求。何をしたいか。議事録や資料のパスを含んでよい）

この要件定義書を、別のセッションの計画のスキル（`writing-implementation-plan`）が読んで技術の設計とフェーズを決め、人に聞かないワーカーが実装する。計画のスキルは要件定義書に書いてあることを聞き直さない。ここで決めなかった製品の判断は、誰も決めないまま実装される。何を、なぜ、どこまで作るかは、ここで利用者と詰めて書き切る。どう作るかは決めない。

要件定義書は計画のディレクトリ（リポジトリの外）に置く文書で、コミットしない。形は [references/requirements-format.md](references/requirements-format.md) にある。形の確かめは共通のスクリプト `${CLAUDE_SKILL_DIR}/../plan-phases-shared/scripts/plan-phases` で行う。スクリプトはリポジトリのルートで実行する。

利用者への質問と報告、要件定義書は日本語で書く。

## 守ること

- 確かめられる事実（今のコード、画面、データ、資料に書いてあること、ライブラリや外部サービスの仕様）は自分で確かめ、根拠を控える。利用者に聞くのは、製品の判断（誰のためか、何を作るか、範囲、振る舞い、完了の判断、数字の目標、権限）と好みだけにする。資料で決まっていることは聞き直さない
- 仕様は必要に応じて Web Search や context7 で最新の情報を確かめる
- 不明点は AskUserQuestion で聞き、完全に解消するまでやりとりする。影響の大きいものから聞き、推奨の選択肢を先頭に置いて label の末尾に「（推奨）」を付ける
- どう作るか（技術の選択、テーブルや API の形、ファイルの置き場所）は決めず、出てきたら「計画に任せること」に書く。ただし、利用者が決める見た目、操作の作法、文言は、製品の判断としてここで決める
- 要件定義書に「TBD」「未定」「要検討」「適切に」を残さない。決められないことは、聞いて決めるか、推奨を採って「見立て」と書く
- 語を作らない。資料に無い業務の語が要るときは、意味を利用者と決めて「用語」に書く
- git の操作はしない。リポジトリのファイルも変えない。試作と使い捨てのスクリプトは、計画のディレクトリの `.scratch/` に置く

## 手順

```txt
- [ ] 1. 置き場所と計画名を決める
- [ ] 2. 材料を読み、要求を言い直す
- [ ] 3. 決まっていないことを洗い出す
- [ ] 4. 利用者に聞いて詰める
- [ ] 5. 方向性を比べて決める
- [ ] 6. 決めたことを確かめる
- [ ] 7. 書いて、形を確かめる（check-requirements）
- [ ] 8. 点検させて直す（reviewing-requirements）
- [ ] 9. 報告する
```

### 1. 置き場所と計画名を決める

- リポジトリのルートで動いていることを確かめる（`git rev-parse --show-toplevel`）
- 計画の置き場所は、リポジトリの隣の `plans/`（リポジトリの親のフォルダの `plans/`）。無ければ AskUserQuestion で聞く（推奨: 隣に `plans/` を作る）
- 計画名（英小文字・数字・ハイフン。短く）を決める。計画のディレクトリは `<計画の置き場所>/<計画名>`。機能ブランチは `feature/<計画名>` になるので、既存のブランチ（`git branch -a`）や計画と重ならない名前にする。`requirements.md` が既にあれば、読んでから続きとして直す
- 計画の置き場所がこのセッションの作業フォルダの外なら、書くたびに許可を求められる。利用者に `/add-dir <計画の置き場所>` を打ってもらう
- 計画のディレクトリを作り（`mkdir -p <計画のディレクトリ>`）、この会話を記録する。かかった時間とトークンを、後で `plan-phases usage` が集める（点検のサブエージェントの分も含む）

  ```bash
  ${CLAUDE_SKILL_DIR}/../plan-phases-shared/scripts/plan-phases session <計画のディレクトリ> requirements ${CLAUDE_SESSION_ID}
  ```

### 2. 材料を読み、要求を言い直す

- 引数の要求と、そこに書かれた議事録・資料・チケットを読む。議事録やチャットを読める MCP が使えて、要求がそのプロジェクトのものなら、関係するやりとりも読む
- リポジトリの CLAUDE.md、`docs/domain/`（用語集、品質特性の表など）、`docs/security.md`、ADR（`docs/adr/` など）を読む。同じ置き場所にある前の計画の `requirements.md` も、書き方の手本として読んでよい
- 要求が触る今のコード、画面、データを調べる。広く探すときはサブエージェント（Explore）に任せ、結論とファイルの場所だけを受け取る
- 次を 200〜300 字で示す。要求を自分の言葉で言い直したもの（誰のために、何を、なぜ。分かっている範囲で）。今の作り（ファイル:行）と、この要求が触る範囲。要求が考えていなさそうな制約、食い違い、もっと安い道筋
- 「なぜ（誰の、どんな困りごとか）」が材料から分からなければ、それを最初に、選択肢を付けずに文章で 1 つ聞く。例を添えると答えが例に引きずられるので添えない。答えを待ってから 3 に進む

### 3. 決まっていないことを洗い出す

- [references/viewpoints.md](references/viewpoints.md) の観点で、決まっていないことを洗い出す
- 洗い出したものを「事実（確かめれば分かる）」と「判断（利用者が決める）」に分ける。事実は、コードや資料を読む、使い捨てのスクリプトを流す、ドキュメントを読むなどで確かめ、根拠（ファイル:行、資料の日付とページ、コマンドと出力、URL）を控える
- 規模を見積もる。計画のフェーズが十数を超えそうなら、分けて別の要件定義にする案を、4 の最初の問いにする

### 4. 利用者に聞いて詰める

- 判断を AskUserQuestion で聞く。前提になる判断が決まっていて今聞けるものを、4 つまでまとめて 1 回で聞く。答えで中身が変わる問いは、次の回に回す
- 後から取り返しにくいもの（範囲、データの粒度、権限、履歴を残すか、移行の順番、viewpoints.md の 9）から聞く
- 各問に、分かっていること（資料で誰がいつ何と言ったか、今の作り）、決まっていないこと、選択肢ごとに起きること、推奨とその理由を書く。資料と今の作りが食い違うときは、食い違いを選択肢に 1 行で添えて、どちらに合わせるかを聞く
- 見た目や操作感のように言葉だけでは決めにくいときは、`.scratch/` にブラウザで開ける HTML の試作を作り（案を切り替えて見比べられるようにする）、`open <ファイル>` で開いてから聞く。試作はリポジトリに置かず、リポジトリのコードも使わない（試作が手本にされないように）
- 答えから新しく決まっていないことが出たら、3 と 4 を繰り返す
- 利用者が「任せる」と答えたものは推奨を採り、根拠を「見立て」とする

### 5. 方向性を比べて決める

- 製品の判断を含む解き方（画面の作法、操作の流れ、段階的に出すか一度に出すか）は、構造の違う案を 2〜3 個並べ、それぞれの代償と推奨を示して AskUserQuestion で聞く。名前を変えただけの案は数えない
- 比べた案、採らなかった理由、選んだ理由（技術と業務の両方）、根拠と出典を、「決めたこと」に 1 行ずつ書く。根拠と出典は、利用者が答えたものは「利用者の判断（日付）」、資料にあるものはその出典、試作で決めたものは試作のファイル、測っていない予想と聞かずに推奨を採ったものは「見立て」
- 技術だけの選択（ライブラリ、テーブルの形、API の形）は比べずに「計画に任せること」に書く

### 6. 決めたことを確かめる

聞くことが無くなったら、次を示し、この理解で書いてよいかを AskUserQuestion で確かめてから 7 に進む。直すところがあれば 4 に戻る。

- 目的、やること、やらないこと、後に回すこと
- 完了の条件の案
- 決めたこと（決定と理由。見立てのものは分けて並べる）

### 7. 書いて、形を確かめる

[references/requirements-format.md](references/requirements-format.md) の雛形を写して、`<計画のディレクトリ>/requirements.md` に書く。完了の条件は、計画のスキルがそのまま機能の PR に写すので、確かめられる文で書き切る。

```bash
${CLAUDE_SKILL_DIR}/../plan-phases-shared/scripts/plan-phases check-requirements <計画のディレクトリ>
```

- `problems` が出たら直し、出なくなるまで繰り返す
- `warnings` は 1 つずつ読み、直すか、直さない理由を 9 の報告に書く
- `assumptions`（根拠が見立ての決定）は、9 の報告に並べる

### 8. 点検させて直す

全体の点検は 1 回だけ呼ぶ。重大な指摘を直したときだけ、直した所の確かめを 1 回呼ぶ。それより多くは呼ばない（点検は 1 回に 10 分ほどかかり、呼び直すたびに直していない所からも新しい指摘が出て、終わらなくなる）。

- Skill ツールで `plan-phases:reviewing-requirements` を呼ぶ。引数は計画のディレクトリだけにし、自分の説明や結論は添えない。点検は会話を引き継がないサブエージェントで動き、この文書だけで計画を立てる人の立場で読む。返るのは重大と中の指摘だけ
- 直す前に、点検の結果と、そのときの要件定義書を残す。直した所の確かめが、これを読んで差分を取る

  ```bash
  mkdir -p <計画のディレクトリ>/.scratch/requirements-review-1/before
  cp <計画のディレクトリ>/requirements.md <計画のディレクトリ>/.scratch/requirements-review-1/before/
  ```

  点検の結果は、そのまま `.scratch/requirements-review-1/result.md` に書く
- 返ってきた指摘を 1 つずつ、次のどれかで扱う。扱いは `result.md` の各指摘の末尾に「- 扱い: <どれか>（<書き足した節、または理由>）」と書き足す
  - 会話や材料で答えが出ている: 要件定義書に書き足す
  - 何を作るかが変わらない細かいこと: 自分で決めて書き、根拠を「見立て」とする
  - 利用者にしか決められず、答えで何を作るかが変わる: まとめて 1 回の AskUserQuestion で聞いてから直す
  - 当たらない: 直さず、理由を控える
- 直したら 7 の形の確かめをやり直す
- 重大な指摘を直したときは、`plan-phases:reviewing-requirements` をもう一度呼ぶ。引数は計画のディレクトリと `<計画のディレクトリ>/.scratch/requirements-review-1` の 2 つ。これは直した所の確かめで、前回の指摘が直ったかと、直した所だけを見る。返ってきた指摘は同じように扱い（結果は `.scratch/requirements-review-2/result.md` に残す）、7 をやり直して点検を終える。ここで残った重大な指摘は、9 の報告に書く
- 重大な指摘が無かったときは、中の指摘を直して 7 をやり直し、点検を終える

### 9. 報告する

次を示して終える。

- 要件定義書のパスと、目的・やること・やらないことの要約
- 完了の条件（全件）
- 決めたこと（見立てのものは分けて並べる）
- `check-requirements` の warnings と、それぞれの扱い
- 点検の指摘と、それぞれの扱い（全件。直さなかったものは理由）
- 次にすること。利用者が要件定義書を読み、直したいところがあればこのセッションで伝える。よければ新しいセッションを開き、リポジトリのルートで計画のスキルを動かす

  ```bash
  claude --add-dir <計画の置き場所>
  ```

  ```txt
  /plan-phases:writing-implementation-plan <計画のディレクトリ>
  ```
