# 決定と学びを記録する

引数: `$ARGUMENTS`（計画のディレクトリ）

計画のフェーズではなく、全フェーズが機能ブランチに入った後、仕上げ（`finalizing-feature-pr`）の前に 1 回行う決まった手順。計画書はリポジトリの外にあって、リポジトリからは読めないので、残すべき決定と、繰り返した問題への対策をリポジトリに残す。何を ADR にするか、書き方、状態と置き換え、`docs/` に残す中身の決まりは [references/adr-rules.md](references/adr-rules.md) にある。

ADR にするかどうかは、ここで初めて決める。書く条件の「コード・テスト・コードコメントから読み取れない」と「型・lint・テストで守れない」は、コードができてからでないと判断できないため。決めた時点の文脈（比べた案、選んだ理由、根拠と出典）は、要件定義書（`requirements.md`。製品の判断）と計画の README（どう作るか）の「決めたこと」と、各フェーズのコミットメッセージの「決めたこと」（実装の途中で案を比べて決めたこと。前の版のワーカーのコミットでは「計画から変えた点」）に書いてある。**理由と出典はそこから取り、後から作らない。**

要件定義書はリポジトリの外にあって、リポジトリからは読めないので、業務の知識（用語、品質特性、セキュリティの段階）は、ここでリポジトリの `docs/domain/` と `docs/security.md` に写す（中身の決まりは [references/adr-rules.md](references/adr-rules.md) の 6 章）。用語集の「コードの名前」は、コードができた今だから書ける。 判定は下の規則で決め、人には聞かない。ADR は機能の PR で提案になり、利用者がマージで採用する（[references/adr-rules.md](references/adr-rules.md) の 3 章）。残したくないものは、利用者がマージの前に PR で外させる。

判断の要らない操作は共通のスクリプト `${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack` と、このスキルの `scripts/` で行う。スクリプトはリポジトリのルートで実行する。

利用者への報告と結果ファイルは日本語で書く。

## 守ること

決まりに反する git・gh・wrangler の操作は、frontmatter のフック（`shipstack-shared/scripts/guard.py`）が止める。止められたら、回り込まずに理由を読み、止まる。

- 人には聞かない。止まるのは、既存の ADR と食い違う決定があり、置き換えるか機能の側を直すかを材料から決められないときだけ（手順 8 の結果ファイルを `--status stopped` で書いて終える）
- git と gh の操作は、`{{機能ブランチ}}` へのコミットと push、機能の PR の本文の更新に限る。main への直接のコミットと push、ブランチの作成、PR の作成とマージ、force push、タグ、履歴の書き換え（rebase、`reset --hard`、push 済みのコミットの amend）はしない
- 計画書と要件定義書は削除も書き換えもしない（機能の PR のマージ後に利用者が削除する）
- 仕様や参照先は、必要に応じて Web Search や context7 で最新の情報を確かめる

## 値を読む

```bash
${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack values <計画のディレクトリ> --require 計画名 機能ブランチ "ADR のディレクトリ" 静的解析 テスト "PR の決まり"
```

`values` の値を、以下の `{{…}}` に使う。表に無い欄があると失敗するので、推測で埋めずに止まる。この手順の名前は `{{計画名}}-decisions`（結果ファイルの名前と、コミットメッセージの「手順:」の行に使う）。

## 手順

```txt
- [ ] 1. 始める前の確認
- [ ] 2. 材料を集める（スクリプト）
- [ ] 3. 決定ごとに残し方を判定する
- [ ] 4. 繰り返した問題への対策を決める
- [ ] 5. 書く
- [ ] 6. 確かめる（スクリプト → 自分で）
- [ ] 7. 検査、コミット、push、PR の更新
- [ ] 8. 結果ファイルを書いて報告する
```

### 1. 始める前の確認

次を実行する。機能ブランチで、origin と同じで、未コミットの変更が無く、フェーズ表の作業名がすべてコミットの「フェーズ:」の行にあること（全フェーズが済んでいる）を確かめる。`ok` が false なら止まる。

```bash
${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack preflight <計画のディレクトリ> --require-phases-done
```

### 2. 材料を集める

次の 2 つを実行する。1 つ目は、要件定義書の「決めたこと」「用語」「品質特性」「権限とデータ」の節（要件定義書があるとき）、計画の README の「決めたこと」の節（「領域の変更」の節があれば、それも読む）、各コミットの「決めたこと」を、手を加えずに出す。2 つ目は、この計画でワーカーが止まったり、確かめた結果が合わなかったりした記録を出す。

```bash
${CLAUDE_SKILL_DIR}/scripts/gather-decisions.sh <計画のディレクトリ>
${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack stops <計画のディレクトリ>
```

あわせて、既存の ADR の表題と、`docs/domain/` と `docs/security.md` があれば読む（`grep -h "^# ADR-" {{ADR のディレクトリ}}*.md`）。

### 3. 決定ごとに残し方を判定する

材料の決定（要件定義書と計画の README とコミットの「決めたこと」）を 1 つずつ、機能ブランチのコード・テスト・コードコメントを読んで、次の順に判定する。結果は表（決定、判定、理由、根拠と出典）にする。

1. 次の 3 つをすべて満たすか。満たさなければ「残さない」
   - コード、テスト、コードコメントのどれからも読み取れない
   - 知らないまま将来コードを変えると誤る（採らなかった案とその理由、外部サービスの制約、計測の結果に基づく判断、守るべき前提、作らないと決めたことなど）
   - 実際に比べた案が 2 つ以上あった（材料に記録がある案だけを数える）
2. 型・lint・テストで強制でき、理由がその箇所の 1 行のコメントで足りるか。足りれば「仕組みとコメント」。ただし、強制のために変えるファイルが、計画の README の「機能の PR の本文」かフェーズの計画書の「変えてはいけないこと」に入っているなら、そのファイルを変えない別の手段（テスト）で守る。別の手段が無ければ「ADR」にする
3. 残りは「ADR」。同じ問題の ADR、または食い違う ADR が既にあれば「ADR（ADR-NNNN を置き換え）」

迷ったら「この決定を知らない人や AI が、このコードを素直に直したら何が壊れるか」と問う。答えが「何も壊れない」なら残さない。

### 4. 繰り返した問題への対策を決める

2 の `stops` の記録で、同じ種類の問題が 2 回以上あれば対策を決める。1 回だけのものは対策にしない。

- リポジトリの中で防げるもの（コードの規約、テストの書き方、検査）: CLAUDE.md の 1 行、`.claude/rules/` のルール、lint、テスト、フックのどれかで防ぐ。CLAUDE.md は短く保ち、既存の行と重ねない
- フローや計画の雛形の問題（スキルの手順、計画書の形、指揮役のふるまい）: リポジトリには入れず、`<計画のディレクトリ>/.runs/workflow-feedback.md` に、起きたこと（記録の時刻と作業名）、原因の見立て、直す場所の案を書く。指揮役が最後に利用者へ示す

### 5. 書く

判定が「ADR」「仕組みとコメント」のものと、4 の対策と、業務の知識を書く。

業務の知識は、要件定義書があるときだけ書く。ファイルが無ければ作り、書くことが無ければ作らない。既にあれば、その形に合わせて行を足すか直す（同じ語や品質特性の行を重ねない）。出典には、要件定義書の出典（議事録の日付、「利用者との会話（日付）」など）を写す。要件定義書や計画書を出典に指さない（リポジトリの外にあり、ほかの人とリポジトリからは読めない）。

- `docs/domain/glossary.md`: 要件定義書の「用語」の語を、表（業務の語、コードの名前、意味、同義語・使わない言い方、出典）で書く。コードの名前は、機能ブランチのコードで実際に使っている型・関数・テーブルの名前を `git grep` で確かめて書く（コードに無ければ「—」）。コードを読めば分かることは書かない
- `docs/domain/characteristics.md`: 要件定義書の「品質特性」の行を、表（品質特性、対象、数字、確かめ方、構造への影響、出典）で書く。構造への影響は、計画の README の「決めたこと」とコードから書く（無ければ「—」）。「なし」なら書かない
- `docs/security.md`: 要件定義書の「権限とデータ」のセキュリティの段階を、段階と理由で書く。段階はプロダクト全体のものなので、既にあって要件定義書の段階の方が重いときだけ上げて理由を書き足し、軽いときは下げない（機能の PR で提案になり、利用者がマージで採用する）

- ADR の番号は、1 本書くたびに次のスクリプトで決める。既存のファイル、Git の履歴に残る消した ADR、コードの `ADR-NNNN` の参照を見て、使われていない次の番号を出す。自分で数えない

  ```bash
  ${CLAUDE_SKILL_DIR}/scripts/next-adr-number.sh {{ADR のディレクトリ}}
  ```

- `{{ADR のディレクトリ}}` に `NNNN-<英小文字とハイフンの短い名前>.md` で置き、[references/adr-template.md](references/adr-template.md) の形で書く（既存の ADR の形が違っても）
- 置き換えるときは、新しい ADR に変わらない部分も書き直して全体を置き換え、頭の行に `旧番号`、状況に前の決定と変えた理由を 1〜2 文で書き、古い ADR のファイルを消す（古い本文は Git の履歴に残る）。`git grep -n "ADR-<古い番号>"` で、コードコメント、CLAUDE.md、README、他の ADR の参照を新しい番号に直す
- ADR が守っている箇所のコードコメントに `（ADR-NNNN）` を付ける
- 「仕組みとコメント」は、その型・lint の規則・テストと、理由の 1 行のコメントを足す。4 の対策も含め、「変えてはいけないこと」に入っているファイルは変えない（仕上げが見つけて止まる）

### 6. 確かめる

書いた・変えた ADR を、次のスクリプトで確かめる。ファイル名、表題と番号、頭の行、節の名前と順番、空の節、採らなかった案、代償、計画書を指していないこと、旧番号のファイルと参照が残っていないこと、手元のリンク先を見る。ERROR が出たら直して、出なくなるまで繰り返す。WARN（60 行を超えた、決定が意見の形）は [references/adr-rules.md](references/adr-rules.md) の 2 章に従って見直す。

```bash
${CLAUDE_SKILL_DIR}/scripts/check-adr.sh --plan-dir <計画のディレクトリ> <書いた・変えた ADR のファイル>...
```

そのうえで、スクリプトでは確かめられないことを自分で確かめる。

- 書いた URL をすべて開き、書いたことがその先にある
- 守り方に書いたテスト・lint の規則・CI の検査が実在する
- 決定の 1 文目が「〜する。」で言い切り、理由が技術と業務の両方にある
- 数字に日付と出典があり、測っていない予想は「見立て」と書いてある
- 理由と採らなかった案が、2 の材料にあるものだけでできている
- 業務の知識の用語集のコードの名前が、機能ブランチのコードに実在する。どのファイルも要件定義書・計画書・`plans/` を指していない

### 7. 検査、コミット、push、PR の更新

1. `{{静的解析}}` と `{{テスト}}` を通す
2. 下書きを出し（`shipstack commit-skeleton decisions <計画のディレクトリ>`）、置き換える場所を埋める。「残さなかった決定」には、3 で「残さない」と判定した決定をすべて理由と一緒に書く（仕上げが PR に写し、利用者がマージの前に見る）。各項目の書き方は [references/commit-message.md](references/commit-message.md) にある
3. コミットするファイルを `git add` し、次の 1 回の Bash で、書く・確かめる・コミットする。`commit-check` が `problems` を出したらコミットされないので、直してもう一度実行する

   ```bash
   msg="$(git rev-parse --git-path shipstack-message.txt)"
   cat > "$msg" <<'EOF'
   <埋めたコミットメッセージの全文>
   EOF
   ${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack commit-check decisions "$msg" --plan <計画のディレクトリ> && git commit -F "$msg"
   ```

4. `git push` し、機能の PR の進捗にチェックを入れる: `shipstack pr-check-off <計画のディレクトリ> 決定と学びの記録 <短いハッシュ>`
5. CI は待たない。仕上げ（`finalizing-feature-pr`）が最初に確かめ、落ちていれば直す。CI を待つコマンド（`shipstack ci`、`gh pr checks --watch`、Monitor）は使わない

何も残さないとき（材料に決定が無く、すべて「残さない」と判定し、リポジトリの対策も、書く業務の知識も無い）は、コミットしない。`shipstack pr-check-off <計画のディレクトリ> 決定と学びの記録 なし` で、進捗の行にチェックを入れて「なし」と書く。残さなかった決定は、手順 8 の結果ファイルに `--not-kept "<決定>: <理由>"` で 1 つずつ書く（コミットが無いので、仕上げはここから PR に写す）。

### 8. 結果ファイルを書いて報告する

止まったときも書く（`--status stopped --stopped-reason "<…>"`）。コミットしなかったときは `--commit` を付けない。コミットしなかったときは、残さなかった決定を `--not-kept` で書く。

```bash
${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack result <計画のディレクトリ> --name {{計画名}}-decisions --skill recording-plan-decisions --status done --commit <短いハッシュ> --pr <機能の PR の URL> --summary "<残したもの、残さなかった決定の数、workflow-feedback.md に書いたこと>"
```

そのうえで、残したもの（ADR の番号と表題、足した仕組み、書いた業務の知識）、コミットのハッシュを、終わったことの報告として示す。
