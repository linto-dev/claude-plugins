# ADR とリポジトリに残す知識の決まり

決定と学びの記録で、決定ごとの残し方を判定し、ADR と `docs/domain/`・`docs/security.md` を書くときに読む。手順は SKILL.md、ADR の節は [adr-template.md](adr-template.md)、機械で確かめられる形は `scripts/check-adr.sh` にある。ここには、それらに無い中身の決まりだけを書く。

要件定義書と計画書はリポジトリの外にあり、マージの後も残るが、リポジトリからは読めない。リポジトリで働く人と AI に届くのは、ADR と `docs/` に写したものだけ。だから、どちらも根拠に指さない。

依頼主は、何を作るかを決める人（受託開発なら受託先、自社開発なら事業や業務の担当、個人開発なら自分）を指す。依頼主が利用者本人なら、依頼主に確かめることは利用者に聞く。

## 1. 何を ADR にするか

### 1.1 知識の置き場所

表の ADR 以外の行に当たる知識は、ADR に書かない。

| 知識 | 置き場所 |
| --- | --- |
| 振る舞い、仕様の例 | テスト |
| 1 か所に閉じた理由、外部の癖 | そのコードのコメント（1〜4 行） |
| 機械で確かめられる規則 | 型、lint、テスト（理由は 1 行のコメント） |
| 理由が複数の場所にまたがる決定、置き場所のコードが無い決定、案と根拠と見直す条件が要る決定 | ADR |
| 業務の語の意味、品質特性の数字、セキュリティの段階 | `docs/domain/`、`docs/security.md`（6 章） |
| 人が行う手順（設定、資格情報の入れ替え、障害のときの動き） | README の運用の節 |
| 今の設定値、割り当ての表 | コード |
| AI に毎回守らせる作業の規則 | CLAUDE.md、`.claude/rules/` |
| PR 単位の意図、完了の条件 | PR の本文 |

### 1.2 書く条件に当たりやすい決定

SKILL.md の手順 3 の 3 つの条件を満たしやすいのは、次の決定。

- 構造: 境界、分け方、どこに置くか（例: Worker を分ける、表の持ち主を決める）
- 品質特性に効く技術の選択（数字を満たすために選んだ構造）
- 依存: 新しい外部サービス、SaaS、ライブラリに頼る
- 公開する面: 依頼主の他のシステムや外部に出す API、webhook、MCP、データの形
- 作り方: 基盤、ツール、テストの方針
- 外部の制約や計測に基づく判断
- 作らないと決めたこと、意図的な近道（引き上げる条件つき）
- 依頼主とトレードオフを合意したこと
- 設計の決まりの既定（作り方の選び方、置き場所、つなぎ方、技術の既定）から外れたこと

作らないと決めたことには、コメントを付けるコードが無い。「仕組みとコメント」にはならず、残すなら ADR だけになる。

### 1.3 書かないもの

テンプレートの規則にあるもの（実装の説明、手順、今の設定値）に加えて、次を ADR にしない。

- 既定どおりの選択。理由は既定の側にある
- 入力と保存が中心の部分を、単純な作り方で作ったこと。妥協ではないので、記録は要らない
- 振り返りと教訓。繰り返した問題は、SKILL.md の手順 4 で仕組みかフローへの気づきにする
- 品質特性の数字、業務の語の意味、セキュリティの段階そのもの（6 章に写す）。数字を満たすために選んだ構造と、その代償は ADR になりうる

## 2. 形

テンプレートの節の順に、テンプレートに無い決まりだけを並べる。

- 表題: 問題ではなく決定を書く。良い例「Cron を 1 本にして、中で時刻を見て振り分ける」、悪い例「Cron の構成について」。一覧（`grep -h "^# ADR-"`）で他の ADR と見分けられるよう、業務の語か製品の名前を入れる
- 日付: 書いた日。採用は機能の PR のマージだが、マージの日は書くときに分からないので、ずれても直さない
- 承認: 依頼主の承認が要る決定（依頼主が払う費用、依頼主の業務や他のシステムへの影響、セキュリティと個人情報）で、材料に承認の記録（誰が、いつ、どこで）があるときだけ、そこから写す。記録が無ければ行を作らず、コミットの「確認したこと」に「ADR-NNNN: 依頼主の承認の記録なし」と書く。それ以外の決定は、利用者のマージが承認になる
- 状況
  - なぜ今決める必要があったかを、互いに引っ張り合う事実で書く。評価と結論は決定に回す
  - 範囲（どの機能、どのコンテキスト、どの Worker か）を書く
  - 業務の事情（費用、期間、利用者の満足、依頼主の方針のどれか）を 1 つ入れる
  - 出典の形: 実測は日付・環境・コマンド、製品の制約は公式のドキュメントの URL、依頼主の要求は議事録の日付か「利用者との会話（日付）」
  - 2〜8 行
- 決定
  - 決定を守るのに要る数字は書く（例: 「語は 8 個まで」）。手順は書かない
  - 確かさが低い（測っていない、試していない、根拠が見立て）ときは、そう書き、見直す条件を早めに置く
- 採らなかった案: 「今のまま」も案になる。決め手だけを書き、案ごとの長所と短所の表は作らない
- 影響の守る前提: この決定を保つために、ほかの場所でしてはいけないことを具体的に書く（例: どの表も `WITHOUT ROWID` にしない）
- 守り方
  - 仕組みを名前で書く。テストはファイル名とテストの名前（例: `migration-shape.test.ts` の「WITHOUT ROWID を使っていない」）、lint の規則の名前、CI の検査の名前、型の名前。行番号は書かない。守り方の無い決定と、守っているテストの分からない決定は、次の AI のセッションに破られる
  - 機械で守れないときは「レビューで確かめる」に、見ることを 1 行添える
- 見直す条件
  - 引き金を、観察できる数字か出来事と、それを見る場所で書く（例: 「月の rows_read が <数字> を超えたら（`wrangler d1 insights`）」）。「必要に応じて」「量が増えたら」は条件ではない
  - 前提（料金のプラン、契約、量の見立て）に寄りかかる決定は、前提が満たされたかを確かめる場所も書く
- 全体
  - 大事なことを先に書く。表題と決定の 1 文目だけで要点が分かるようにする
  - 文で書く。箇条書きでも語の羅列にしない
  - ADR だけで読めるようにする。議事録は補足として指すだけにする
  - 識別子（関数名、表名、環境変数）は、検索の目印として要るものだけを書く

## 3. 状態と変更

- main にある ADR は、すべて今の決定にする。状態の行（提案、採用、置き換え済み、廃止）を置かない。提案は機能の PR が担い、マージで採用になる。マージの前なら、機能の PR の中で直してよい
- 却下した案は、採用した ADR の「採らなかった案」に書く。「〜を採らない」こと自体が決定なら、それを表題にした ADR を書く（例: 「CIMD を採らず、開放型 DCR で MCP を公開する」）
- main にある ADR を変えてよいのは、切れたリンクと、意味の変わらない誤字だけ。決定、理由、代償、見直す条件のどれかが変わるなら、後から分かった事実でも、新しい ADR で置き換える。AI は ADR の本文を今の決定として読むので、追記が重なると、どれが今の決定かを読み違える
- 決定を変えない事実は、ADR に書き足さない。手順は README の運用の節、1 か所の理由はコードコメント、規則はテストに置く
- 同じ問題の ADR が 2 本以上あれば、1 本にまとめる。まとめた先も新しい番号（`next-adr-number.sh`）にし、まとめた番号をすべて `旧番号` に並べ、古いファイルをすべて消す
- やめた決定（機能ごと消したなど）は、ADR ごと消す。消した番号と理由をコミットの「残したもの」に書き、`git grep -n "ADR-NNNN"` で参照を消すか直す
- 番号
  - 欠番を詰めず、消した番号も使わない。過去のコミットと PR がその番号を指している
  - 分類のサブフォルダを作らない。番号がリポジトリの中で一意でなくなる
  - 並行する PR と番号がぶつかったら、後からマージする方が振り直す。main を取り込んだ後に `check-adr.sh` が番号の重なりを出したら、機能の側の ADR を `next-adr-number.sh` で振り直し、ファイル名、表題、コードの参照を直す

## 4. AI が書くときに間違えやすいこと

| 間違い | 防ぎ方 |
| --- | --- |
| 状況に評価や結論を混ぜ、決定と同じことを 2 回書く | 状況は事実と出典だけにする |
| 出典に要件定義書の節や番号、計画の README の「決めたこと」、PR のコメントを書く | 材料の出典の欄にある元（議事録の日付、利用者との会話（日付）、URL、コマンド）を写す。`check-adr.sh` は「計画書」の語と計画のディレクトリのパスしか見ない |
| 作らないと決めたことを「壊れるコードが無い」として落とす | 知らずに作り始めると誤る。条件を満たせば ADR にする |
| 見直す条件を観察できない形で書く | 数字か出来事と、見る場所を書く |
| 承認の行を推測で書く | 材料に記録があるときだけ写す |
| 用語集に規則、振る舞いの例、コードを読めば分かること（列の型、関数の引数）を書く | 意味、同義語・使わない言い方、出典だけにする |

## 5. 見つけてもらう工夫

- リポジトリの CLAUDE.md に同じ意味の行が無ければ、次の 3 行を足し、コミットの「残したもの」に書く。`<ADR のディレクトリ>` は計画の値

  ```md
  - 設計にかかわる変更の前に、`<ADR のディレクトリ>` を検索し、そこにある ADR に従う。
  - ADR と食い違う変更が要るときは、変えずに止めて確認する。
  - ADR が守っている箇所のコメントには `（ADR-NNNN）` を付ける。
  ```

- ADR を `@` で CLAUDE.md に取り込まない。毎回のセッションで読み込まれ、CLAUDE.md の長さの目安を食う
- `（ADR-NNNN）` は、決定を守っている箇所すべてのコメントに、理由の 1 行と一緒に付ける。詳しい理由は ADR に任せる。AI はコードの `ADR-NNNN` から ADR にたどり着く
- ADR の一覧（README の表）を作らない。表題が 2 か所に分かれ、片方が古くなる。一覧は `grep -h "^# ADR-"` で作る。既に一覧があるリポジトリでは、その一覧も同じコミットで直す
- ADR のディレクトリと `docs/` を Git の管理から外さない。`git check-ignore` で外れていると分かったら、書いたファイルが入るように `.gitignore` を直し、同じコミットに入れて「残したもの」に書く（採るかは利用者がマージで決める）

## 6. `docs/domain/` と `docs/security.md`

表の列は SKILL.md の手順 5 にある。ここには、列に入れる中身と、ほかのファイルの扱いを書く。

### 6.1 用語集（`docs/domain/glossary.md`）

```md
## 用語集（コンテキスト: 配送）

| 業務の語 | コードの名前 | 意味 | 同義語・使わない言い方 | 出典 |
| --- | --- | --- | --- | --- |
| 便 | Trip | 1 台の車両が 1 回の出発で回る配送のまとまり | 「ルート」とは呼ばない（ルートは道順のこと） | <日付> の打ち合わせ（<発言者>） |
```

- コンテキスト（同じ語が同じ意味で通じる範囲）ごとに表を分ける。コンテキストが 1 つなら見出しは `## 用語集` でよい
- 1 つの語に 1 つの意味。同じ語がコンテキストで意味を変えるなら、それぞれの表に別々に書く。1 行に 2 つの意味を書かない
- 意味は業務の言葉で書く。テーブル、列、関数の名前で説明しない
- 使わない言い方には、使わない理由を括弧で添える
- コードの名前は、その語を表す型（無ければテーブル）の英語の名前
- 既存の語の意味が要件定義書と食い違うときは、要件定義書の意味に直す（要件定義で既存の定義と照らして決めている）。前の意味も使い続けるなら、別の語として行を分ける

### 6.2 品質特性（`docs/domain/characteristics.md`）

```md
| 品質特性 | 対象 | 数字 | 確かめ方 | 構造への影響 | 出典 |
| --- | --- | --- | --- | --- | --- |
| 可用性 | 問い合わせの受付 | 営業時間の 99.9%（月 12 分まで） | 成功したイベントの割合と、外からの死活監視 | 受け付けたら Queue に入れ、後段が止まっても受け付ける | 「受付が止まると取りこぼす」（<日付> の打ち合わせ） |
```

- 1 行は 1 つの品質特性と 1 つの対象の組。同じ組の行があれば数字を直し、行を足さない
- 数字は単位と範囲まで書く（p95、営業時間、月あたり）。可用性の割合には、止まってよい時間を添える
- 確かめ方は、実際に担うテスト・監視・照合の名前を、コードと設定で確かめて書く。要件定義書の「監視」のような種類だけで終えない
- 構造への影響は、数字を満たすために選んだ構造を 1 行で書く。理由が長ければ ADR にして番号で指す
- 依頼主の言葉（「止まったら困る」など）が材料にあれば、出典に添える

### 6.3 セキュリティ（`docs/security.md`）

- 段階は `## 段階` の節に、段階、理由（扱うデータ）、出典を 1 行ずつ書く（例: 「理由: 問い合わせの送り主の氏名と電話番号を扱う。要配慮個人情報は扱わない」）
- 段階はプロダクト全体のもの。要件定義書の段階が今の値より重いときだけ、上げて理由を書き足す。軽いときは下げない（この機能が個人情報に触れないだけで、プロダクトの段階は下がらない）
- 段階のほかの節（受け入れた逸脱、秘密の値の一覧、外部の送り先の表、確かめた結果）は、セキュリティの設計が書く。消さず、書き換えない
- 外部の送り先の表があり、要件定義書が新しい送り先か送る項目を決めているのに表に行が無ければ、結果ファイルの要約に書いて利用者に知らせる

### 6.4 ほかのファイル

- `docs/domain/` に次のファイルが既にあれば、この機能で変わった行だけを、コードと、計画の README の「領域の変更」（あれば）と「決めたこと」から直す。無ければ作らない
  - `subdomains.md`: サブドメイン、種類（core・supporting・generic）、判定の根拠、作り方
  - `context-map.md`: コンテキストの一覧、つなぎ方、表の持ち主
  - `data-map.md`: 保存先ごとに、正本か派生か、更新の経路、作り直す手順、削除の伝わり方
- 振る舞いの例は `docs/` に書かない。テストに残す

## 7. 確かめる問い

- 「残さない」とした決定に、作らないと決めたこと、外部の制約、依頼主と合意したトレードオフが混ざっていないか
- ADR にした決定が、既定どおりの選択、1 か所に閉じた理由、品質特性の数字・語の意味・セキュリティの段階になっていないか
- 同じ問題の既存の ADR があるのに、置き換えずに新しい ADR を足していないか。置き換えとまとめが新しい番号で、`旧番号` にすべての古い番号があるか
- 表題だけで何を決めたかが分かり、一覧で他の ADR と見分けられるか
- 状況に評価が混ざっていないか。範囲と、業務の事情が 1 つあるか
- 確かさが低い決定に、それが書かれ、早めの見直す条件があるか
- 見直す条件が観察できる形か。前提に寄りかかる決定に、前提を確かめる場所があるか
- 守り方が、行番号ではなく仕組みの名前で書かれているか
- 出典が、要件定義書・計画・会話・PR のコメントではなく、議事録の日付、利用者との会話（日付）、URL、コマンドになっているか
- 承認の行が、材料の記録から写したものか
- main にある ADR を書き足しで直していないか。やめた決定の ADR を消し、参照を直したか
- CLAUDE.md に ADR を探す行があり、ADR を `@` で取り込んでいないか
- 用語集で、1 つの語に 2 つの意味が無いか。規則や振る舞いの例を書いていないか
- 品質特性の行が重なっていないか。確かめ方が実在する仕組みの名前か
- セキュリティの段階を下げていないか
- 既にある `docs/domain/` のほかのファイルが、この機能の変更と食い違っていないか
- 書いたファイルが `.gitignore` で Git の管理から外れていないか
