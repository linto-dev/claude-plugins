# ADR の形

```markdown
# ADR-NNNN: <決定を言い切る短い文（「〜にする」「〜しない」）>

- 日付: <YYYY-MM-DD>
- 旧番号: ADR-NNNN（まとめた・置き換えた ADR があるときだけ）
- 承認: <依頼主の承認が要ったときだけ。誰が、いつ、どこで>

## 状況
<なぜ今決める必要があったか。事実だけ>

## 決定
<1 文目で「〜する。」と言い切り、理由を技術と業務の両方で書く>

## 採らなかった案
- <案>: <採らなかった理由>（1 行ずつ）

## 影響
<得るもの、代償を 1 つ以上、守る前提>

## 守り方
<決定を守るテストや lint の規則の名前。なければ「レビューで確かめる」と書く>

## 見直す条件
<観察できる数字か出来事と、それをどこで見るか。なければ「なし」と理由>
```

## 書くときの規則

形（ファイル名、表題と番号、頭の行、節の名前と順番、代償、旧番号の後始末）は `scripts/check-adr.sh` が確かめる。下の規則のうち中身にかかわるものは、書いた本人が確かめる。

- 1 本に 1 つの問題とし（同じ問題への決定は 1 本にまとめる）、60 行以内を目安にする
- 数字には日付と出典（実行したコマンド、公式のドキュメントの URL、議事録の日付）を付け、測っていない予想は「見立て」と書く
- 採らなかった案には、計画の README の「決めたこと」かコミットメッセージに記録がある案だけを書く。比べるためだけの案を作らない
- 理由は「決めたこと」とコミットメッセージ、計測、議事録にあるものだけを使う。もっともらしい理由を後から作らない
- 計画書、会話、PR のコメントを根拠に指さない（計画書はリポジトリの外にあり、リポジトリからは読めない）。書いた参照（URL、ファイル、節）は、すべて開いて実在を確かめる
- コードとテストを読めば分かること（実装の手順、SQL、ファイルの一覧、今の設定値）は書かない
- 人が行う手順は ADR ではなく README の運用の節に書く
