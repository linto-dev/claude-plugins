# 機能の PR を仕上げる

引数: `$ARGUMENTS`（計画のディレクトリ）

レビューの段階は設けないので、ここが実装を確かめる場になる。main へのマージが本番へのデプロイになるので、機能全体の確認はこの PR で行う。判断の要らない操作は共通のスクリプト `${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack` で行う。出力は JSON で、`ok` が false なら `problems` か `error` を読む。スクリプトはリポジトリのルートで実行する。

利用者への報告、PR の本文、結果ファイルは日本語で書く。

## 守ること

決まりに反する git・gh・wrangler の操作は、frontmatter のフック（`shipstack-shared/scripts/guard.py`）が止める。止められたら、回り込まずに理由を読み、止まる。

- 人には聞かない。止まるのは次のときだけ（手順 6 の結果ファイルを `--status stopped` で書いて終える）
  - 満たさない条件を直すのに、計画の README や計画書の「変えてはいけないこと」「対象外」に触れる変更が要る
  - 同じ問題で 2 回直して失敗した
  - CI が手元で再現しない理由で落ちていて直せない
  - E2E が環境の不備で流せない、E2E を通すのにテストの期待を変える必要がある、E2E の記録に秘密の値が入っている（手順 4）
- git と gh の操作は、fetch、機能の PR のタイトルと本文の編集（`shipstack pr-finalize` が行う）、直しの `{{機能ブランチ}}` へのコミットと push に限る
- main への直接のコミットと push、ブランチの作成、PR の作成とマージ、force push、タグ、履歴の書き換え（rebase、`reset --hard`、push 済みのコミットの amend）はしない
- デプロイはしない（main へのマージで GitHub Actions が行う）
- `{{許可するコマンド}}` に書かれたコマンドは実行してよい。1 回の Bash で単独で実行し、ほかのコマンドと（`&&`・`;`・`|` で）つながない。指揮役が渡す許可ルールはつないだ全体には効かず、auto mode の分類器に回って拒否されることがある。権限が足りずに拒否された操作は繰り返さず、PR の「マージの前に行う確認」に回す

## 値を読む

```bash
${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack values <計画のディレクトリ> --require 計画名 機能ブランチ インストール 静的解析 テスト "PR の決まり" 許可するコマンド "PR のタイトル"
```

`values` の値を、以下の `{{…}}` に使う。表に無い欄があると失敗するので、推測で埋めずに止まる。`{{E2E}}` は `--require` に入れない（前に書いた計画には欄が無い）。`values` の出力に無いか null なら、E2E は無い。

## 手順

```txt
- [ ] 1. 始める前の確認
- [ ] 2. 確かめ直す
- [ ] 3. 満たさないものを直す
- [ ] 4. E2E を流す
- [ ] 5. PR のタイトルと本文を仕上げる
- [ ] 6. 結果ファイルを書いて報告する
```

### 1. 始める前の確認

- `shipstack preflight <計画のディレクトリ> --require-phases-done` を実行する（機能ブランチで、origin と同じで、全フェーズのコミットがある）。`ok` が false なら止まる
- `gh pr view {{機能ブランチ}}` で機能の PR があることを確かめる。無ければ止まる
- 決定と学びの記録が済んでいることを確かめる。`git log origin/main..HEAD --format=%B | grep '^手順: {{計画名}}-decisions'` が出るか、機能の PR の本文の進捗の「決定と学びの記録」の行にチェックがあれば済み。どちらも無ければ止まる
- `git merge-base --is-ancestor origin/main HEAD` で、main の変更が取り込まれているかを確かめる。取り込まれていなければ止まる（指揮役が先に `merging-main-into-feature` を動かす）
- `shipstack ci <計画のディレクトリ>` で、最後の push の CI を確かめる。前景で実行し、`pending` ならもう一度実行する。フェーズと決定と学びの記録は push の後に CI を待たずに進むので、最後の push の CI はここで初めて確かめる。`fail` なら 3 で直す

### 2. 確かめ直す

- `{{インストール}}` を実行し、`{{静的解析}}` と `{{テスト}}` を通す
- 計画の README の「機能の完了の条件」と、各フェーズの計画書の「完了の条件」を、機能ブランチの状態でもう一度確かめる。少なくとも 1 つは、実物で観察できる結果にする
- 各フェーズの計画書の「push の後の確認」と、結果ファイル（`.runs/<作業名>.json`）の `post_push`（push の後にしか確かめられなかった完了の条件）と `manual_steps` のうち（最後のフェーズの「push の後の確認」と `post_push` は、まだ誰も確かめていない）、`{{許可するコマンド}}` の範囲で確かめられるものを確かめる。確かめたものは「確認したこと」に、確かめられなかったものは「マージの前に行う確認」に書く
- 実行したコマンドとその結果を示す。「はず」「おそらく」で完了としない

### 3. 満たさないものを直す

- 落ちる検査やテスト、満たさない完了の条件、緑でない CI が見つかったら直す。CI は、落ちたチェックのログを `gh run view <run_id> --log-failed` で読む。バグは、再現する失敗テストを先に書いてから直す。`{{静的解析}}` と `{{テスト}}` を通す
- 手元で再現せず、原因がコードに無さそうな CI の失敗（デプロイ先の一時的な失敗、不安定なテスト）は、直さずに止まる。`--stopped-reason` に、落ちたチェックと、CI を再実行してほしいことを書く（緑でない CI のまま仕上げない）
- 修正は 1 つのコミットにして `{{機能ブランチ}}` に push する。下書きは `shipstack commit-skeleton fix` が出す（満たす条件、なぜ、確認したこと。`{{PR の決まり}}` にも従う）。コミットするファイルを `git add` し、次の 1 回の Bash で、書く・確かめる・コミットする

  ```bash
  msg="$(git rev-parse --git-path shipstack-message.txt)"
  cat > "$msg" <<'EOF'
  <埋めたコミットメッセージの全文>
  EOF
  ${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack commit-check fix "$msg" && git commit -F "$msg"
  ```

- `shipstack ci <計画のディレクトリ>` で CI の結果を確かめ、2 をやり直してから 4 に進む
- 直せなかったもの（環境が無くて確かめられないものなど）は、PR の本文の「完了の条件」でチェックを入れず、理由を書く

### 4. E2E を流す

`{{E2E}}` が無ければ飛ばす。E2E は、プレビュー環境へのデプロイの後でないと流せないことが多いので、フェーズのワーカーは流さず、直しを積み終えた最後の push にここで 1 回だけ流す。記録（リプレイキャッシュやスナップショットなど、コミットするもの）が変わったら、読んでからここでコミットする（作業ツリーに残すと、ほかの作業に混ざるか消える）。

1. `{{E2E}}` に書かれた前提をそろえる。プレビューのラベルが要るなら `{{許可するコマンド}}` の範囲で貼り、走ったデプロイが終わるまで `shipstack ci <計画のディレクトリ>` で待つ
2. `{{E2E}}` のコマンドを前景で実行する（Bash の timeout を 600000 にする。バックグラウンドや Monitor にしない）
3. 結果で分ける
   - 通って、記録が変わらない（`git status --porcelain` が空）: 5 に進む
   - 通って、記録が変わった: 差分を読む（新しいファイルは中身を読む）。足した・書き換えた記録が、テストの期待どおりの画面で終わっていること（押した場所の名前、URL、見出し）、パスワード・トークン・鍵などの秘密の値と、テスト用のアカウント以外の個人の情報が入っていないこと、消えた記録が、名前を変えたか消したテストのものであることを確かめる。問題が無ければ、記録のファイルだけを 1 つのコミットにして push する（下書きは 3 と同じ `commit-skeleton fix`。満たす条件は「E2E が最後の push で通る」、確認したことに、流したコマンド・通った件数・読んだ記録の要点）。秘密が入っていたら、コミットせずに止まる
   - 落ちた: プロジェクトの決まり（CLAUDE.md など）に従って失敗の詳細を読み、3 と同じく実装を直して push し、デプロイを待ってから、もう一度流す。テストや期待値を変えないと通らないなら、仕様の判断なので止まる
   - 流すたびに結果が変わる: 安定させようとせず、落ちたテストと様子を PR の「マージの前に行う確認」に書く
   - 環境の不備で流せない（E2E が呼ぶモデルの中継やブラウザが動かない、手元の設定ファイルが無い、待ってもデプロイが終わらない）: 直さずに止まる。`--stopped-reason` に、何を起動・用意すれば流せるかを書く（用意してから指揮役を打ち直すと、仕上げがもう一度動く）
4. 結果のファイル（動画・トレースなど）はコミットしない。`.gitignore` で除かれずに手元に残るなら、止まって知らせる

### 5. PR のタイトルと本文を仕上げる

1. 下書きを出す。README・計画書・決定と学びの記録のコミット・結果ファイルから写す部分（完了の条件、変えてはいけないこと、対象外、ADR と残さなかった決定、マージの前に行う確認、マージの後に行うこと、マージの方法）は、スクリプトが写す

   ```bash
   ${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack pr-body <計画のディレクトリ>
   ```

2. `<…>` の置き換える場所を埋める。書き方は [references/pr-body.md](references/pr-body.md) にある。写した文は変えない（完了の条件は、行の先頭の `[ ]` と行末の根拠だけを足す）
3. 次の 1 回の Bash で、書く・確かめる・PR に書く。`pr-finalize` が `problems` を出したら PR は変わらないので、直してもう一度実行する。タイトルは README の「PR のタイトル」になり、`WIP:` が外れる

   ```bash
   body="$(git rev-parse --git-path shipstack-pr-body.md)"
   cat > "$body" <<'EOF'
   <仕上げた本文の全文>
   EOF
   ${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack pr-finalize <計画のディレクトリ> "$body"
   ```

### 6. 結果ファイルを書いて報告する

止まったときも書く（`--status stopped --stopped-reason "<…>"`）。修正を積まなかったときは `--commit` を付けない。`--manual-step` には、PR の本文の「マージの前に行う確認」と「マージの後に行うこと」を、行う順に 1 つずつ書く（先頭に「マージの前:」「マージの後:」を付ける）。指揮役は最後にこれを番号付きで示す。

```bash
${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/shipstack result <計画のディレクトリ> --name {{計画名}}-finalize --skill finalizing-feature-pr --status done --pr <機能の PR の URL> --ci <pass|fail|pending|none> --summary "<確かめ直した結果と、直したこと>" --manual-step "マージの前: <確認や作業>" --manual-step "マージの後: <確認や作業>"
```

そのうえで PR の URL を示す。修正を積んだときは、そのコミットのハッシュと CI の結果も示す。最後の報告は、終わったことの報告として書く。
