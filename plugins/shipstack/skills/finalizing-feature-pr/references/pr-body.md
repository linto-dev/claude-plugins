# 仕上げた機能の PR の本文

下書きは `shipstack pr-body <計画のディレクトリ>` が作り、`shipstack pr-finalize` が確かめてから PR に書く（置き換える場所が残っていないこと、節がそろっていること、完了の条件の文が README と同じこと、チェックボックスが「完了の条件」だけにあること）。最初の本文の「まだマージしない」の注意と「進捗」の節は、下書きに入らないので消える。計画書は後で消すので、条件は計画書から写す。フェーズとコミットの一覧、フェーズごとの完了の条件と確認したことは書かない（コミットログと各コミットのメッセージで分かるため）。

| 節 | 写すもの（スクリプト） | 書くこと（Claude） |
| --- | --- | --- |
| なぜ | README の「機能の PR の本文」の「なぜ」 | 無ければ、機能が解く問題を 1〜2 文で |
| 完了の条件 | README の「機能の完了の条件」をチェックボックスにしたもの | 各行の後ろに「 — 」と満たした根拠（実行したコマンドと結果）を書き、満たしたものを `[x]` にする。満たさないものは `[ ]` のまま理由を書く |
| 変えてはいけないこと・対象外 | README と各フェーズの計画書の節 | なし |
| 確認したこと | なし | 手順 2 と 4（E2E）で実行したコマンドと結果、観察できる結果。E2E は、通った件数と、コミットした記録の要点 |
| ADR と残さなかった決定 | 決定と学びの記録のコミットの「残したもの」「残さなかった決定」 | なし |
| マージの前に行う確認 | 各ワーカーの結果ファイルの `manual_steps` | 手順 2 と 4 で確かめたものを除き（E2E を流して記録をコミットする作業は、手順 4 で済んでいるので入れない）、プレビュー環境（無ければ手元）で確かめることを番号付きで並べ直す。コマンドはそのまま貼れる形にする。順番に依存がある作業は、その順に並べる |
| マージの後に行うこと | README の「マージの後に行うこと」 | 必要なら、そのまま貼れるコマンドを添える |
| マージの方法 | README の「マージの方法」（無ければ「マージコミットでマージする」） | なし |

計画の README の `{{PR の決まり}}` が PR の本文に節を求めていれば（例: 「テストの変更」「写したファイルと変えた行」）、それも加える。

GitHub は本文のチェックボックスをすべて数えて PR の一覧に「n of m tasks」と出す。チェックボックスは「完了の条件」だけに使い、手順は番号付きのリストにする。
