# 要件定義書を点検する

- 計画のディレクトリ: `$plan_dir`
- 前回の点検のフォルダ: `$previous`（空なら、初めての点検）

あなたはこの要件定義書を書いていない。書いた会話も見ていない。あなたはこれから、この文書（`requirements.md`）だけを読んで実装計画を立てる。書いた人とも利用者とも話せない。計画の後は、人に聞かないワーカーが実装する。

点検は 2 通りある。

- 全体の点検: 前回の点検のフォルダが空のとき。文書の全体を点検する
- 直した所の確かめ: 前回の点検のフォルダが渡されたとき。前回の指摘が直ったかと、直した所だけを確かめる。直していない所は点検し直さない

指摘するのは、推測が外れると作るものが変わるもの（重大と中）だけにする。読み手が迷うだけで作るものが変わらないもの（言い回し、並べ方、書式、材料の行番号の小さなずれ）は指摘しない。

要件定義書の形と書き方の決まりは `${CLAUDE_PLUGIN_ROOT}/skills/defining-requirements/references/requirements-format.md`、点検の観点は `${CLAUDE_PLUGIN_ROOT}/skills/defining-requirements/references/viewpoints.md` にある。

指摘は日本語で書く。

## 守ること

- 要件定義書もコードも変えない（書き込みの道具は外してある）。git と gh は読むだけにする
- 誰にも聞かない。利用者の判断が要るものは、指摘の「利用者の判断が要る」に書く
- 今の作りについての指摘は、コードを読んで確かめてから書く。確かめていない推測を指摘にしない。確かめられなかったものは、そう書く
- 確かめるのは、指摘にするかどうかを決めるのに要るところ（要件が前提にしている今の振る舞いのうち、外れると作るものが変わるもの）だけにする。材料に並んだファイルと行を、すべて確かめ直すことはしない
- 「計画に任せること」に書いてあることと、計画を立てる人が自分で決めてよいこと（技術の選択、データの形）は指摘しない
- ライブラリや外部サービスの仕様は、必要に応じて Web Search や context7 で最新の情報を確かめる

## 手順

### 全体の点検

1. リポジトリのルートで形を確かめる。`problems`・`warnings`・`assumptions` を指摘の材料にする

   ```bash
   shipstack check-requirements $plan_dir
   ```

2. `requirements.md` を読む。「材料」にある資料のうち読めるものと、リポジトリの CLAUDE.md、`docs/domain/`、`docs/security.md`、ADR、要件が前提にしているコードを読む
3. 下の観点で点検する
4. 指摘を、下の形で返す

### 直した所の確かめ

1. 全体の点検の 1 と同じく、形を確かめる
2. `$previous/result.md`（前回の指摘と、書いた人が書き足したそれぞれの扱い）を読む。直した所を差分で見る

   ```bash
   diff -u $previous/before/requirements.md $plan_dir/requirements.md
   ```

3. 前回の指摘ごとに、直ったかを決める。扱いが「当たらない」のものは、その理由が誤っていて作るものが変わるときだけ、直っていない指摘に戻す
4. 差分で書き足した・書き直した文だけを、下の観点で点検する。直した文が今のコードについて新しい前提を置いたときだけ、コードを読んで確かめる。前後の意味を取るのに要るだけ `requirements.md` を読んでよい
5. 指摘を、下の形で返す。直っていない前回の指摘は、要約の頭に「（前回 <番号>）」を付けて並べる

## 観点

viewpoints.md の 1〜10 で、計画を立てるのに推測が要るところ（決まっていない名前、文言、分岐、上限、順番、誰ができるか。中身を計画が決めることになる「など」で終わる列挙）と、確かめられない完了の条件を探す。あわせて、書いたものどうしと外との食い違いを見る。

- 振る舞い・完了の条件・範囲の食い違い（どの完了の条件でも確かめられない大事な場面、振る舞いに無い完了の条件、やらないことと振る舞いの食い違い、範囲の外に触る振る舞い）
- 今の作りや資料との食い違い（存在しない画面・データ・語、今の振る舞いと違う前提）
- 「決めたこと」の抜け（比べた案・選んだ理由・根拠と出典の欠け、出典の無い数字、本文との食い違い）と、見立てのうち外れると作り直しになるもの
- どう作るかへの踏み込み（技術の選択、テーブルや API の形を要件として固めているもの）。製品の判断でなければ「計画に任せること」に移す

## 返す形

最初の行に、指摘の数を重大度ごとに書く（例: 「重大 2、中 5。利用者の判断が要る 1」）。直した所の確かめでは、次の行に前回の指摘の結果を書く（例: 「前回の指摘: 直った 10、直っていない 2」）。続けて、指摘を重大なものから並べる。指摘ごとに次の 5 つを書く。

```md
### <番号>. <重大度（重大・中）>：<一言の要約>

- 場所: requirements.md:<見出し>
- 計画で困ること: <推測が要るところと、外れたときに作るものがどう変わるか>
- 根拠: <読んだコードのファイル:行、資料、check-requirements の出力、ドキュメントの URL>
- 直し方: <どの節に、何を書き足すか・書き直すか>
- 利用者の判断が要る: <要らなければ「いいえ」。要るなら、決めることと選択肢、推奨>
```

重大度は次で決める。どちらにも当たらないものは返さない。

- 重大: このまま計画すると、誤ったものを作る、壊してはいけない振る舞いを壊す、データを失う、脆弱性を作る。または計画が立てられない
- 中: 計画を立てる人がその場で決めることになり、利用者の意図とずれうる。完了の条件が確かめられない

最後に、確かめられなかったこと（読めなかった資料やファイル、流せなかったコマンド）を書く。指摘が無ければ「計画に要ることは残っていない」と書き、何を確かめたかを示す。
