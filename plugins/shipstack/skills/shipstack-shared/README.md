# shipstack-shared

実装計画を進める指揮役（`shipstack run`）と、ワーカーのスキル 4 つ（`implementing-plan-phase`、`merging-main-into-feature`、`recording-plan-decisions`、`finalizing-feature-pr`）、計画のスキル 2 つ（`writing-implementation-plan`、`reviewing-implementation-plan`。`check-requirements` と `check-plan` だけを使う）、要件定義のスキル 2 つ（`defining-requirements`、`reviewing-requirements`。`check-requirements` だけを使う）が共通で使うスクリプトです。`SKILL.md` を置かないので、スキルとしては出ません。shipstack プラグインの `skills/` に、ほかのスキルと並べて置き、各スキルは `${CLAUDE_SKILL_DIR}/../shipstack-shared/scripts/` から呼びます。

判断の要らない操作は、文章の指示ではなくここで行います。同じ入力なら同じ結果になり、スキルごとに書き方がずれません。

## 中身

| ファイル | 役目 |
| --- | --- |
| `scripts/shipstack` | 指揮役と、決定論的な操作のサブコマンド（下の表） |
| `scripts/guard.py` | 各スキルの「守ること」を止める PreToolUse フック |
| `scripts/guard.sh` | フックの入口。python3 が無いときは git・gh・wrangler だけを止める |
| `tests/test_shared.py` | 試験。`tests/fakes/` の偽の `gh` と `claude` で、指揮役を最後まで回す |

## 指揮役（shipstack run）

リポジトリのルートで、計画のディレクトリを渡して動かします。`<プラグインの場所>` は、プラグインを入れた場所です。計画のスキル（`/shipstack:writing-implementation-plan`）が最後の報告で、この場所を埋めたコマンドを示します。

```bash
<プラグインの場所>/skills/shipstack-shared/scripts/shipstack run <計画のディレクトリ> [--dry-run] [--once] [--yes] [--retry] [--fresh]
```

ワーカーは `/shipstack:<スキル>` で起動します（プラグインの名前は、このスクリプトから見た `../../../.claude-plugin/plugin.json` から読む）。ワーカーには `--plugin-dir` でこのプラグインの根（このスクリプトから見た `../../..`）を渡すので、ワーカーは指揮役と同じ版のスキルで動きます。同じ名前のインストール済みのプラグインは、その会話だけ置き換わり（[公式の説明](https://code.claude.com/docs/en/plugins/loading#name-conflicts)）、ワーカーを動かす設定のフォルダ（`CLAUDE_CONFIG_DIR`）にプラグインを入れていなくても動きます。

1. 計画の形を `check-plan` と同じ規則で確かめる。`problems` があれば、何も起動せずに止まる（`warnings` は件数だけを示す）
2. 計画の README の「開始前に人がすること」があれば、最初に一度だけ済んだかを聞く（端末で y。`--yes` で済んだものとする。答えは `.runs/prerequisites.json` に残り、項目が変わるまで聞かない）
3. 次のことを繰り返す
   1. git・機能の PR から状態を読み、`next` と同じ規則で次に行うことを 1 つ決める
   2. 機能ブランチが origin に無ければ、`origin/main` から作って push する
   3. 手元を機能ブランチの最新にする（未コミットの変更や、push していないコミットがあれば触らずに止まる。途中で切れたワーカーの続きなら、その変更はそのワーカーのものなので止まらない）
   4. ワーカーを `claude -p` で起動する（`--permission-mode auto --permission-prompts none`。人に聞く道具は外れる。`--plugin-dir` でこのプラグインを読ませる。`--effort` で手順ごとのエフォートを渡す（[下](#エフォート)）。`--settings` で決まりのフック（`guard.sh`）と、起動の確かめのフック、`ultracode` と `disableAllHooks` の値、計画に「許可するコマンドのルール」があればそれ（[下](#許可するコマンドのルール)）を渡す。環境変数 `CLAUDE_CODE_RETRY_WATCHDOG=1` を付ける（[下](#途中で切れたとき)）。プロンプトの `/<スキル> <対象>` は標準入力で渡す）。ワーカーの発言の 1 行目、権限で拒否された操作、API の再試行を待っていることを流す
   5. ワーカーが思った設定で始まったかを、モデルを呼ぶ前に確かめる。合わなければワーカーを止め、理由を示して止まる（[下](#起動の確かめ)）
   6. ワーカーが結果ファイルを書かずに終わったら、途中で切れたとみなし、同じ会話を続きから再開する（[下](#途中で切れたとき)）
   7. `verify` と同じ確かめ（結果ファイル、コミット、PR の進捗、手元）をする。CI を待つのは仕上げの後だけ（[下](#ci-を待たない)）。合わなければ、通知して止まる
4. 仕上げまで済んだら、仕上げのワーカーが残した「マージの前・後」の手順を示して終える。マージはしない（計画の README に `{{E2E}}` があれば、仕上げのワーカーが最後の push に E2E を流し、変わった記録を読んでからコミットしている）

止まったら、理由と、ワーカーの会話を開くコマンド（`claude -r <ID>`。`CLAUDE_CONFIG_DIR` で `~/.claude` 以外のアカウントを指定して動かしたときは、頭にその指定が付く）を出します。会話は設定のフォルダごとに保存されるので、ID ではほかのアカウントから開けません（記録ファイルのパスを `-r` に渡せば開ける）。直してから同じコマンドを打ち直すと、状態から続きを決め直します。同じ手順が 2 回続けてうまくいかなかったら、`--retry` を付けない限り 3 回目は起動しません（途中で切れただけの記録と、起動の確かめで止めた記録は数えない）。動きの記録は `.runs/history.jsonl` に 1 行ずつ残ります（渡したエフォートは `effort` に残る。権限で拒否された操作は `denials` に、理由と一緒に残る。動かした設定のフォルダは `config_dir`、API の再試行の回数は `api_retries`、途中で切れたものは `interrupted`、続きから再開した回数は `resumes`、起動の確かめで止めたものは `launch` に残る）。

| 環境変数 | 既定 | 使いどころ |
| --- | --- | --- |
| `CLAUDE_CONFIG_DIR` | — | 2 つ目のアカウントで動かす（`CLAUDE_CONFIG_DIR=~/.claude-b shipstack run …`） |
| `SHIPSTACK_CLAUDE` | `claude` | ワーカーを起動するコマンド（試験では偽物） |
| `SHIPSTACK_PERMISSION_MODE` | `auto` | ワーカーの権限のモード（起動の確かめは、ワーカーがこのモードで始まったかを見る） |
| `SHIPSTACK_MODEL` | — | ワーカーのモデル |
| `CLAUDE_CODE_EFFORT_LEVEL` | — | Claude Code の環境変数。付けて打つと、どのワーカーも手順ごとのエフォートではなくこの値で動く（[下](#エフォート)） |
| `SHIPSTACK_NOTIFY` | `1` | `0` で macOS の通知を出さない |
| `SHIPSTACK_RESUME_PAUSE` | `60` | 途中で切れたワーカーを自動で再開する前に置く秒数 |
| `SHIPSTACK_GUARD` | `scripts/guard.sh` | `--settings` で渡す決まりのフックのコマンド（試験で、呼ばれたことを記録する包みに差し替える） |
| `CLAUDE_CODE_RETRY_WATCHDOG` | `1` | 指揮役がワーカーに付ける。`0` を付けて打つと、ワーカーは既定の 10 回で再試行をやめる |
| `SHIPSTACK_REPO` | — | git と gh を動かすリポジトリ。run がワーカーに渡すので、ワーカーが計画のディレクトリに cd しても動く |

### エフォート

指揮役は、ワーカーに `--effort` でエフォートを渡します。

| 手順 | エフォート |
| --- | --- |
| フェーズ | 計画の README のフェーズ表の「エフォート」（`medium` か `high`。基準は `writing-implementation-plan/references/plan-format.md` の「フェーズ表」）。列の無い前の版の計画は `high` |
| main の取り込み・決定と学びの記録・仕上げ | `medium` |

- **根拠**: 公式の説明（[Claude Code](https://code.claude.com/docs/en/model-config#adjust-effort-level)、[API](https://platform.claude.com/docs/en/build-with-claude/effort)。2026-11-18 に読んだ）。Claude Opus 5.5 の既定は `medium` で、「`medium` から始めて明示し、前のモデルの設定を持ち越さず、自分の課題で水準を比べる。`xhigh` と `max` は差を測った仕事にだけ使う」。`medium` は「新しい機能の実装のような、範囲のはっきりした日々の開発」、`high` は「既存のコードベースのバグを直すような、検証が要り端が出やすい仕事」に当たる。前の版は何も渡さず、設定ファイルの値（ある利用者は `xhigh`）で全手順が動いていた
- **効く順**: `CLAUDE_CODE_EFFORT_LEVEL` ＞ スキルの frontmatter の `effort`（スキルが動いている間）＞ 会話で選んだ水準 ＞ `--effort` ＞ 設定ファイル（`modelSettings`・`effortLevel`）＞ モデルの既定。`--effort` は設定ファイルより強いので、`~/.claude/settings.json` で `xhigh` にしていても、ワーカーは表の値で動く。ワーカーのスキルの frontmatter には `effort` を書かない（書くと `--effort` が効かなくなる）
- **全ワーカーを 1 つの値で動かす**（流し比べなど）: `CLAUDE_CODE_EFFORT_LEVEL=high shipstack run …` と打つ。指揮役は始めにそう知らせ、`history.jsonl` にもその値を残す
- **効いた値を確かめる**: `usage` の「モデル（エフォート）」の列は、会話の記録にある実際の値を出す
- **流し比べ**: 公式は自分の課題で水準を比べるよう勧める。終わった計画から性格の違うフェーズ（新しいものを足すだけ、既存の振る舞いを変える、など）を選び、同じ起点のコミットから水準を変えて流し、`usage` の時間とトークン、完了の条件と検査、止まったか、手戻りを比べる
- 要件定義と計画（`defining-requirements`・`writing-implementation-plan`）と、その点検は `high`（各スキルの frontmatter）。対話のスキルの `effort` は、スキルが動いたターンの終わりまでしか効かない（AskUserQuestion の答えはターンの中）。後から普通のメッセージで頼むと、会話の水準（設定ファイル、無ければ Opus 5.5 の `medium`）に戻る。`allowed-tools` の事前の許可も、次のメッセージで外れる。このため 2 つのスキルは、報告の前の問いをすべて AskUserQuestion で行い、文章で聞いて答えを待たない

### CI を待たない

フェーズ・main の取り込み・決定と学びの記録のワーカーは、push の後に CI を待たずに終え、指揮役も待たずに次の手順を起動します。ある機能の計画（2026-11-07）では、各フェーズが push の後に 7〜10 分（フェーズの時間の約 3 分の 1）CI を待っていました。

- 前の push の CI は、次のフェーズのワーカーが、実装を終えて自分の push をする前に `previous` で確かめる。落ちていれば、そのフェーズで直してそのフェーズのコミットに含める。手元で再現せず原因がコードに無さそうな失敗は、書いて進む（次の push の CI がもう一度確かめる）
- 確かめるのを push の後ではなく前にするのは、同じ PR への次の push で、走っている CI が取り消されるため（GitHub Actions の `concurrency` の `cancel-in-progress`）。次の push の前なら、前の CI はたいてい終わっていて、待つ時間はほとんど無い
- 1 つ前のフェーズの「push の後の確認」も、そのとき確かめる。プレビュー環境は、まだ前の push の状態にある
- 最後のフェーズと決定と学びの記録の push の CI、最後のフェーズの「push の後の確認」は、仕上げのワーカーが確かめて直す。指揮役は仕上げの後に CI を待ち（最長 3600 秒）、通っていなければ止まる。緑でない CI のままマージ待ちにはならない

### 起動の確かめ

ワーカーは誰もいないところで動くので、思った設定で始まらなかったワーカーは、モデルを呼ぶ前に止めます。指揮役は、ワーカーの stream-json の最初の `system/init`（[公式の説明](https://code.claude.com/docs/en/headless#read-session-metadata)）と、それより前に流れるフックの記録を読み、次のどれかに当たれば、ワーカーを止めて理由を示し、止まります。

| 確かめること | 合わないとき |
| --- | --- |
| `permissionMode` が `auto`（`SHIPSTACK_PERMISSION_MODE` の値） | auto mode が使えない（設定の `disableAutoMode`、対応していないモデル、サーバー側で止まっている）と、Claude Code は Manual で始める（[公式の説明](https://code.claude.com/docs/en/permission-modes)）。`--permission-prompts none` と組むと、書き込みがすべて拒否されたまま 1 手順を使い切る |
| `plugins` に shipstack がある | プラグインが読み込めないと、`/shipstack:<スキル>` が展開されない。`plugin_errors` を理由に添える |
| `--settings` の SessionStart のフック（標準エラーに `shipstack-hooks-on` と書くだけ）の `hook_response` が流れた | `--bare`（公式は将来 `-p` の既定にすると予告している）、`CLAUDE_CODE_SIMPLE`、管理者の設定の `disableAllHooks` や `strictPluginOnlyCustomization` では `--settings` のフックが動かず、決まりのフック（`guard.sh`）が効かない |

- 止めたワーカーは何もしていないので、失敗として数えない（`--retry` は要らない）。`history.jsonl` には `launch: true` で残る。新しい会話は捨て、続きから再開しようとした会話は残すので、直してから打ち直すと同じ会話の続きから進む
- 読んだ shipstack の場所が指揮役と違うとき（管理者の設定でプラグインが固定されていると、`--plugin-dir` は使われない）は、止めずに知らせる
- `--settings` には、ほかに `"ultracode": false` と `"disableAllHooks": false` を入れる。コマンドラインの設定はプロジェクトとユーザーの設定より強い（[公式の説明](https://code.claude.com/docs/en/settings#settings-precedence)）ので、利用者の設定に `ultracode` が付いていてもワーカーが手順ごとに dynamic workflow を組まず、リポジトリの設定の `disableAllHooks` で決まりのフックが止まることもない
- 2026-11-18 に 2.1.327 で確かめた: auto mode を設定で止めると `permissionMode` が `default` になる。`--bare` では `--settings` の SessionStart のフックの記録が流れない（`--plugin-dir` のプラグインと `permissionMode` は bare でも変わらないので、フックで見分ける）。`--plugin-dir` のプラグインは `source: "shipstack@inline"` で読まれ、インストール済みのものと置き換わる

### 途中で切れたとき

ワーカーは誰もいないところで動くので、API に届かないときは Claude Code 自身に待たせ、それでも切れたら同じ会話を続きから再開します。ある機能のフェーズ（2026-11-07）は、DNS が引けない状態（`ENOTFOUND`）の約 3 分で既定の再試行 10 回を使い切って終わり、手元に未コミットの変更 19 件を残しました。前の指揮役は、打ち直しても「未コミットの変更があります」で止まり、続けられませんでした。

- **待つ**: ワーカーに `CLAUDE_CODE_RETRY_WATCHDOG=1` を付ける（[公式の説明](https://code.claude.com/docs/en/errors#tune-retry-behavior)）。一時的な失敗（通信が切れた、サーバーの失敗）は 300 回（約 3 時間）まで、`429`・`529` は戻るまで、利用上限は戻る時刻まで再試行する。指揮役は `system/api_retry` を読んで「⏳ API に届かないので再試行を待っています（…、次は 15:45:00）」と流し（1 回目、10 回ごと、理由が変わったとき、10 分以上待つとき。10 分以上なら通知も出す）、戻ったら「↺ API に戻りました」と流す。2026-11-07 に、途中でネットワークを 4 分止めたところ、watchdog 無しは 10 回目（約 3.4 分）で `ECONNREFUSED` で終わり、有りは戻った後に続けて最後まで終えた
- **続きから再開する**: それでもワーカーが結果ファイルを書かずに終わったら（3 時間を超える不通、応答の途切れ、エラー無しで終わったのに結果ファイルが無い、など）、60 秒おいて、同じ会話を `claude -p --resume` で続きから再開する。1 回の run で 2 回まで。その後は通知して止まり、同じコマンドを打ち直すと、同じ会話の続きから再開する。利用上限らしい失敗（`limit`・`上限` を含む）は、すぐには再開せずに止まる
- **Ctrl+C・端末を閉じた**: 起動の前に `.runs/active.json`（手順、会話の ID、設定のフォルダ、始めた時刻）を書き、ワーカーが結果ファイルを書いて終えたら消す。指揮役ごと止まっても、打ち直すとこれを読み、同じ会話の続きから再開する。手元の未コミットの変更と push していないコミットは、そのワーカーのものとして触らない
- **再開のプロンプト**: 最初の指示（`/<スキル> <対象>`）と切れた理由を示し、始める前の確認（`preflight`。未コミットの変更があると止まる）をやり直さず、`git status` と `git log -1` で手元を確かめて、切れた手順から結果ファイルまで進めるように頼む
- **決まりのフック**: 再開した会話（`claude -p --resume`）では、スキルの frontmatter のフックが登録されない（2026-11-07 に 2.1.319 で確かめた。新しい会話では止めたコマンドが、再開した会話ではフックが呼ばれずに通った）。このため指揮役は、どのワーカーにも `--settings` の `hooks` で同じ `guard.sh <役目>` を渡す。新しい会話では 2 回動くが、結果は同じ
- **別のアカウントで続ける**: `--resume` には会話の記録ファイルのパスを渡す。パスなら、別の設定のフォルダ（`CLAUDE_CONFIG_DIR`）からでも同じ会話を続けられ、続きは元のファイルに書き足される（2026-11-07 に確かめた）。利用上限を待たずにアカウントを替えたいときは、Ctrl+C で止め、`CLAUDE_CONFIG_DIR` を替えて打ち直す
- **待つ間に人が続けた**: 打ち直すまでの間に、人が会話を開いて結果ファイルまで書き終えていたら、起動せずに確かめる
- **続けずに捨てる**: 手元の変更を片付けてから `--fresh` を付けて打ち直すと、途中の会話を捨て、新しいワーカーで始める
- 前の指揮役が「ワーカーが失敗で終わりました」と記録したワーカー（`active.json` が無い）も、手元に未コミットの変更があれば、最後の記録の会話を続きから再開する

### 使った時間とトークン（usage）

計画ごとに、要件定義から仕上げまでの手順ごとの時間・モデル・エフォート・トークン・推定費用を残します。フローを直す材料にするためで、計画のディレクトリはマージの後も残します。ある機能の計画（2026-11-07）では、要件定義と計画（点検のサブエージェントを含む）だけで、全体のトークンの約半分を使っていました。

- **数字の正は Claude Code の会話の記録**（`<設定のフォルダ>/projects/<フォルダ>/<会話の ID>.jsonl` と、その `subagents/`）。発言ごとの `message.usage`（入力・キャッシュの読み書き・出力・思考のトークン）、`message.model`、`effort`、ターンごとの `system/turn_duration`、会話の合計の `cost-state`（推定費用と API の時間）を読む。記録は `cleanupPeriodDays`（既定 30 日）で消えるので、読めるうちに `.runs/usage/<会話の ID>.json` に写す。消えた後は写しから出す
- **どの会話を数えるか**: 要件定義と計画のスキルが、自分の会話の ID を `session` で `.runs/sessions.jsonl` に書く（対話の会話は指揮役が起動しないため）。ワーカーは `history.jsonl` の会話。指揮役の外で動いたワーカー（手で起動した、指揮役が記録する前に止まった）は、同じフォルダの会話の最初のコマンド（`/shipstack:implementing-plan-phase <計画書>` など。前の名前の `/plan-phases:…` と、プラグインの名前の無い前の版の形も読む）から見つける
- **時間**: ワーカーは指揮役が測った経過（途中で切れて再開したら足す）。要件定義と計画は、AI が動いた時間（ターンの合計。人が考えている間を除く）。ターンの記録は重なることがあるので（ある計画は、135 分の会話を 204 分と数えていた）、重なった所は 1 回だけ数える
- **数えないもの**: 要件定義と計画の会話で、最初のワーカーが始まった後の発言（同じ会話で別のことを続けたとき）。同じ会話の起動が 2 回あっても、トークンは 1 回だけ数える
- **推定費用**は Claude Code の推定（`cost-state`）で、請求ではない（サブスクリプションでは利用枠から出る）。会話を閉じる前などで推定の無い会話は「—」、一部だけのときは「+」を付ける。トークンは発言の記録から数えるので、Claude Code の補助の呼び出し（会話の題名づけなど）は入らない
- 指揮役は、始めるとき（要件定義と計画の会話）と、各ワーカーの後に写し、仕上げまで済んだら合計を出す

### 許可するコマンドのルール

ワーカーは auto mode で動くので、外部に書き込む操作（`gh pr edit <番号> --add-label preview` など）は分類器が判定します。分類器は利用者の発言を許可として読みますが、計画の README に文章で書いた「許可するコマンド」は、ワーカーがスクリプトの出力として読むだけなので許可になりません。このため、ある計画のフェーズ 1（2026-11-05）では、許可したはずのラベル貼りが「Unrequested Commit in a Connected App」で拒否され、プレビュー環境の確認がすべて人の手に回りました。

計画の README の「プロンプトに入れる値」に、次の欄を足すと、指揮役がワーカーに `--settings '{"permissions":{"allow":[…]}}'` で渡します。欄は任意で、無いか「なし」なら何も渡しません。

```md
| `{{許可するコマンドのルール}}` | `Bash(gh pr edit * --add-label preview)`、`Bash(gh pr view *)`、`Bash(gh pr checks *)`、`Bash(gh run view *)` |
```

- 書き方は Claude Code の[許可ルール](https://code.claude.com/docs/en/permissions)。1 つずつコードの書式で書く。`*` はサブコマンドの後に置く。道具の名前だけ、`Bash(*)`、サブコマンドより前に `*` があるもの（`Bash(gh *)` は `gh pr merge` まで通す）、`Read(**)` のような広いルールは、起動する前に止める
- 許可ルールに合う操作は、分類器を通らずに通る（`--debug` の `permissionDecisionMs` が数 ms。合わないものは分類器に回り数秒かかる。2026-11-05 に Claude Code 2.1.318 で確かめた）
- `&&`・`;`・`|` でつないだコマンドは、つないだ一つ一つがルールに合うか、読み取りだけのコマンドでないと、全体が分類器に回る。`gh pr edit 11 --add-label preview 2>&1; echo "exit=$?"` は分類器に回った。スキルは許可したコマンドを単独で実行させる
- 注意: `*` を含むルールは、`$(…)` やバッククォートで埋め込んだコマンドまで分類器を通さずに通すことがある（`gh pr edit $(<任意のコマンド>) --add-label preview` がルールで通った）。公式の例（`Bash(npm run *)` など）も同じ性質を持つ。ルールは計画に要る最小限にし、`Bash(echo *)` のような、何にでも付けられるコマンドのルールは書かない
- 手で 1 つずつ進めるときは、同じ JSON を `claude --settings '…'` で渡すか、リポジトリの `.claude/settings.local.json` の `permissions.allow` に書く

### 次に行うことの決め方（next）

上から順に見て、最初に当たったものを行います。

1. 機能の PR がマージ済み、または機能ブランチがマージコミットで main に入っている → 何もしない
2. 機能ブランチが origin に無い → 作る
3. main が進んでいる → `merging-main-into-feature`
4. コミットの「フェーズ:」の行に無い作業名のうち、フェーズ表でいちばん上のもの → `implementing-plan-phase`
5. 機能の PR が仕上げ済み（タイトルに `WIP:` が無く、本文に「まだマージしない」が無い） → 何もしない（マージ待ち）
6. 決定と学びの記録が済んでいない（「手順: <計画名>-decisions」のコミットも、PR の進捗のその行のチェックも無い） → `recording-plan-decisions`
7. → `finalizing-feature-pr`

## サブコマンド

`run` は人が読む文を、`commit-skeleton` と `pr-body` は下書きの文を出します。ほかは結果を 1 つの JSON で出します。終了コードは 0 成功、1 確かめた結果が合わない・止まった・失敗（`problems` か `error` に理由）、2 使い方の誤りです。

| サブコマンド | すること |
| --- | --- |
| `run <計画のディレクトリ>` | 指揮役（上） |
| `next <計画のディレクトリ>` | 次に行うことと、状態の要約を出す。何も変えない |
| `verify <計画のディレクトリ> <phase・merge-main・decisions・finalize> [作業名]` | ワーカーの後の確かめ |
| `values <計画のディレクトリ> [--require <欄>...]` | 計画の README の「プロンプトに入れる値」を読む。「なし」は null。`--require` の欄が表に無ければ失敗 |
| `check-requirements <計画のディレクトリ>` | 要件定義書（`requirements.md`）が、計画のスキルと点検の読む形になっているかを確かめる（[下](#要件定義書の形check-requirements)）。`problems` があれば終了コード 1 |
| `check-plan <計画のディレクトリ>` | 計画の README と計画書が、スキルと指揮役の読む形になっているかを確かめる（[下](#計画の形check-plan)）。`problems` があれば終了コード 1 |
| `preflight <計画のディレクトリ> [--require-phases-done]` | `git fetch origin` をして、今のブランチ、origin との差、未コミットの変更、済んだフェーズを確かめる |
| `pr-create <計画のディレクトリ>` | 機能の PR が無ければ、README の「機能の PR の本文」（節の中にコードブロックが 1 つあれば、前後の説明の文と外側の囲みを除いた中身。帰属の行を足す）と、「PR のタイトル」に `WIP:` を付けたタイトルで作る。有れば URL を返すだけ |

| `pr-body <計画のディレクトリ>` | 仕上げた PR の本文の下書き。README・計画書・決定と学びの記録のコミット・結果ファイルから写せる節は、ここで写す |
| `pr-finalize <計画のディレクトリ> <本文のファイル>` | 置き換える場所が残っていないこと、節、写した完了の条件、チェックボックスの置き場所を確かめ、タイトルを「PR のタイトル」にして（`WIP:` が外れる）本文と一緒に書く |
| `ci <計画のディレクトリ>` | CI が終わるまで待つ（最長 540 秒）。`pass`・`fail`・`pending`（時間切れ。呼び直す）・`none`（機能の PR が無いか、チェックが現れない）。落ちたチェックには、ログを読むための `run_id` が付く |
| `previous <計画のディレクトリ> <作業名>` | フェーズのワーカーが push の前に呼ぶ。`ci` と同じく前の push の CI を待ち、`previous` に 1 つ前のフェーズの作業名・計画書・`post_push`（計画書の「push の後の確認」と、そのフェーズが結果ファイルの `post_push` に書いた、push の後にしか確かめられなかった完了の条件。前の版のワーカーがコミットで「（push の後に確かめる）」とした条件も読む）を付けて出す。最初のフェーズでは `previous` が null |
| `result <計画のディレクトリ> --name … --skill … --status …` | 結果ファイルを `.runs/<名前>.json` に書く。`--previous-ci` は、フェーズが push の前に確かめた前の push の CI（指揮役が終わった手順の行に出す）、`--ci` は仕上げが待った CI。`--post-push`（フェーズ: push の後にしか確かめられなかった完了の条件。次のフェーズと仕上げが読む）、`--manual-step`（人が手で行う確認）、`--not-kept`（決定と学びの記録が残さなかった決定。コミットしないときも PR に写す）は繰り返せる |

| `usage <計画のディレクトリ> [--json]` | 計画の会話ごとの時間・モデル・エフォート・トークン・推定費用を集め、`.runs/usage/<会話の ID>.json` に写してから、手順ごとと合計を出す（[下](#使った時間とトークンusage)） |
| `commit-skeleton <phase・decisions・merge-main・fix> …` | コミットメッセージの下書き。指揮役が見分けに使う行（「フェーズ: <作業名>」「手順: <計画名>-decisions」）は、ここで書く。計画書はリポジトリの外にあって使い捨てなので、計画書が無いと読めない中身（計画書の節の写し、計画との差、計画への影響）は下書きに入れない |
| `commit-check <種類> <ファイル> [--plan …]` | タイトル、「フェーズ:」「手順:」の行、項目の有無と順番、置き換える場所が残っていないかを確かめる。フェーズのコミットでは、メッセージと `git add` した変更の足した行に、計画書と要件定義書にだけある番号・記号・名前（「README の規則」「規則 B」「決めたこと 2」「要件の #28」「要件定義書」「計画書」、作業名、計画書のファイル名。メッセージでは「フェーズ 3」「計画どおり」も）が無いかも見る |

## 計画の形（check-plan）

計画の形は `writing-implementation-plan/references/plan-format.md` にあります。`check-plan` は、人の判断の要らないことだけを決まった規則で確かめ、結果を `problems`・`warnings`・`assumptions` に分けて出します。計画のスキルは書いた後に、点検のスキルは点検の最初に、指揮役は始める前に使います。

| 出すもの | 中身 |
| --- | --- |
| `problems` | 指揮役やワーカーが読めない、または途中で止まるもの。README の節（フェーズ表、開始前に人がすること、プロンプトに入れる値、決めたこと、機能の PR の本文）、値の表の欄と「なし」にできない欄、`PR のタイトル`の形、広すぎる許可ルール、作業名の付け方と並び、フェーズ表の「エフォート」の値（列があるとき。low・medium・high・xhigh・max のどれか）、作業名ごとにちょうど 1 つの計画書、計画書の節（完了の条件、変えてはいけないこと、対象外、変更するファイル）と空の節、完了の条件のチェックボックス、PR の本文の「まだマージしない」・節・進捗の行（作業名ごとと「決定と学びの記録」にちょうど 1 行）・進捗の外のチェックボックス、要件定義書の完了の条件のうち、PR の本文の「機能の完了の条件」か「マージの後に行うこと」に同じ文で無いもの（文末の句点と空白の違いは見ない） |
| `warnings` | 直すかどうかを人か Claude が決めるもの。フェーズ表の「エフォート」の列が無い（前に書いた計画を動かせるように problems にしない。無ければフェーズは high で動く）、medium と high 以外のエフォート、実装が一意にならない言葉（TBD、適切に、適宜など）、値の表に無い `{{欄}}`、`{{E2E}}` の欄が無い（前に書いた計画を動かせるように problems にしない。無ければ仕上げは E2E を流さない）、「マージの後に行うこと」の「マージの前」を含む行、push の後にしか確かめられなさそうな完了の条件、Claude ができそうな「開始前に人がすること」、ルールの無い「許可するコマンド」、「決めたこと」の空の列と技術・業務の無い理由、計画のディレクトリと計画名の食い違い、要件定義書（`requirements.md`）の無い計画（要件定義のスキルより前に書いた計画を動かせるように、problems にしない） |
| `assumptions` | 「決めたこと」のうち、根拠と出典が「見立て」のもの。計画のスキルが報告に並べ、利用者が確かめる |

`requirements.md` は計画書として読みません（作業名を探さない）。

## 要件定義書の形（check-requirements）

要件定義書の形は `defining-requirements/references/requirements-format.md` にあります。`check-requirements <計画のディレクトリ>` は、計画のディレクトリの `requirements.md` を読み、`check-plan` と同じく `problems`・`warnings`・`assumptions` と、完了の条件の一覧（`conditions`）を出します。要件定義のスキルは書いた後に、要件定義の点検は点検の最初に、計画のスキルは書き始める前に使います。git を使わないので、リポジトリの外でも動きます。

| 出すもの | 中身 |
| --- | --- |
| `problems` | 計画のスキルが読めないもの。ファイルが無い、計画のディレクトリの名前（計画名）が英小文字・数字・ハイフンでない、タイトルの見出しが無い、節（目的、材料、範囲、用語、振る舞い、完了の条件、品質特性、権限とデータ、決めたこと、計画に任せること）が無いか空、範囲の「やること」「やらないこと」「後に回すこと」が無いか空、完了の条件に箇条書きが無い |
| `warnings` | 一意にならない言葉（TBD、未定、要検討、適切になど）、残った置き換える場所（`{{…}}` と、コードの書式の外の日本語を含む `<…>`）、タイトルと計画名の食い違い、「やること」に箇条書きが無い、セキュリティの段階（A・B・C）が無い、「決めたこと」の列の抜けと空の列と技術・業務の無い理由 |
| `assumptions` | 要件定義書の「決めたこと」のうち、根拠と出典が「見立て」のもの |

## guard.py が止めるもの

各スキルの frontmatter の `hooks` から、役目を引数にして呼ばれます。指揮役（`shipstack run`）は、同じものをワーカーに `--settings` の `hooks` でも渡します（再開した会話ではスキルのフックが登録されないため。[上](#途中で切れたとき)）。止めたら理由を Claude に返します（終了コード 2）。フックが落ちたり時間切れ（30 秒）になったりしたときも、`onFailure: block` でコマンドを止めます（Claude Code の既定では、失敗したフックはコマンドを通す。[公式の説明](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails)）。指揮役はスクリプトなので、フックは通りません。

| 役目 | 使うスキル | 止めるもの（全員に共通のものに加えて） |
| --- | --- | --- |
| すべて | — | force push、main への push とコミット、origin に無いブランチの push、ブランチやタグを消す・送る push、push 済みのコミットの amend と reset、`reset --hard`、rebase、pull、ブランチとタグの作成と削除、worktree の作成と削除、`git clean -f`、`gh pr merge`・`close`、PR の向き先の変更、書き込む `gh api`、`gh workflow run`、秘密の値の書き込み（`gh secret`・`gh variable` の set と delete、wrangler の `secret put`・`delete`・`bulk`、`versions secret`、`secrets-store` の作成・更新・削除、`--secrets-file`） |
| `implement` | implementing-plan-phase | merge |
| `merge-main` | merging-main-into-feature | `origin/<既定のブランチ>` 以外の merge、PR の作成 |
| `decisions` | recording-plan-decisions | merge、PR の作成 |
| `finalize` | finalizing-feature-pr | merge、PR の作成（タイトルの `WIP:` を外せるのはこの役目だけ） |

コマンドは bash と同じ区切りで読み、bash が動かすものはすべて同じ決まりで読みます。

- シェルの予約語の後ろ（`if … then`、`{ …; }`、`for … do`、`!` など）と、前置きの後ろ（`env`・`timeout`・`nice`・`sudo` など。値を取るオプションも読む）
- 別のシェルに渡す文字列（`bash -c`、`sh -c`、`eval`、`env -S`）
- コマンド置換（`$(…)`、`` `…` ``、`<(…)`）。二重引用符の中と、引用符の無い区切りのヒアドキュメント（`<<EOF`）の本文の中でも
- `xargs` と `find -exec` が動かすコマンド。足す引数は読めないので、引数しだいで決まりに反する git（push・commit・reset など）・gh（pr・api など。読むだけの操作は除く）・wrangler（secret など）を、`xargs` と `find -exec` で動かすことも止める

一重引用符の中（コミットメッセージなど）、引用符の付いた区切りのヒアドキュメント（`<<'EOF'`）の本文、コメント、リダイレクト（`2>&1`、`> /dev/null`）は、bash も動かさないので見ません。読めないコマンド（引用符や括弧の対応が取れない、入れ子が 8 段より深い）が git・gh・wrangler を含むなら止めます。

間違いを止めるためのもので、わざと回り込む相手を防ぐものではありません。変数で組み立てたコマンドの名前（`$GIT push`）と、シェルに渡すスクリプトのファイルと標準入力（`bash x.sh`、`… | bash`）は読みません。

試験は、手で書いた例に加えて、本物の bash を正解の役にした確かめを持ちます。禁止の操作をシェルの書き方で包んだコマンドを、固定した種で 400 件作り、引数を記録するだけの偽の `git`・`gh` を置いた bash で動かします。そのうえで、bash が禁止の操作を実際に動かしたコマンドを、guard.py がすべて止めたかを確かめます。生成したコマンドの 4 分の 1 以上が禁止の操作まで届かなければ、確かめが空回りしているとして落ちます（`GuardShellOracleTest`）。

フックのコマンドは `"${CLAUDE_PLUGIN_ROOT}/skills/shipstack-shared/scripts/guard.sh"` です。プラグインのスキルの frontmatter のフックでは `CLAUDE_PLUGIN_ROOT` が使え、`${CLAUDE_SKILL_DIR}` は展開されません（2026-11-13 に Claude Code 2.1.322 で確かめた）。`onFailure: block` も、スキルの frontmatter のフックと `--settings` のフックの両方で効きます（2026-11-18 に 2.1.327 で、落ちるフックを置いて確かめた。無いとコマンドが通り、有ると止まる）。見つからないと、フックの失敗としてすべての Bash が止まるので、置き場所を変えるときは、このパスも直します。`claude -p` でも、スキルの frontmatter のフックは動きます（2026-11-05 に確かめた）。
