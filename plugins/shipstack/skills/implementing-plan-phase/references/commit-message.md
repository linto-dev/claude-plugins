# フェーズのコミットメッセージ

計画書はリポジトリの外にあって使い捨てなので、計画書が無いと読めない中身（計画書の節の写し、計画書との違い、計画書と要件定義書の番号や記号）は書かない。後から履歴を読む人と AI に要る、変えた理由と、案を比べて決めたことだけを書く。

下書きは `shipstack commit-skeleton phase <計画書のパス>` が作り、`shipstack commit-check phase` が確かめる。

## 形

- タイトル: 平易な Conventional Commits（例: `feat(widget): 回答の待ち時間を短くする`）
- 本文: 次の項目をこの順で書く。計画の README の `{{PR の決まり}}` に追加の項目があれば、「確認したこと」の後に足す

```txt
フェーズ: <作業名>

なぜ
<解く問題を 1〜2 文で>

決めたこと
- <案を比べて決めたこと: 決定、比べた案と採らなかった理由、根拠と出典（実測なら日付とコマンド、製品の制約なら公式のドキュメントの URL）。無ければ「なし」>

確認したこと
- <流した検査とテストの結果、観察した結果を 1〜3 行で>
- <前の push の CI が落ちていて直したときは、落ちたチェック、原因、直し方>
```

## 決まり

- 「フェーズ:」の行は、指揮役（shipstack run）がどのフェーズのコミットかを見分けるのに使う。作業名だけを正確に書く（`commit-check` が確かめる）
- 「決めたこと」には、比べた案があるものだけを書く。決定と学びの記録が、ここから ADR にするかを決める。計画書が決めていない細部を自分で決めたこと、計画書と違えたことは書かない
- 「確認したこと」は、完了の条件ごとに書かない。テストの件数や観察した結果を短くまとめる
- 書かないもの: 計画書と要件定義書にだけある番号・記号・名前（「規則 B」「決めたこと 2」「要件の #28」、作業名、計画書のファイル名、「フェーズ 3」）、計画どおりか・計画と違うか。`commit-check` が見つけたら止める
