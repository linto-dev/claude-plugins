# 領域の設計の決まり

変更が、業務の語、サブドメイン、コンテキストの境界、つなぎ方、集約、package とフォルダの配置に触れるときに読む。

## 決めること・決めないこと

- 決める: サブドメインの種類と作り込みの程度、業務の語とコードの名前、コンテキストの境界とつなぎ方、実装パターン、集約の境界、package とフォルダの配置、表の持ち主、境界の検査、`docs/domain/` の中身、ADR の候補。
- 決めない: 業務の知り方と品質特性の聞き出し方（要件定義。計画では要件定義書の品質特性の表と用語を使う）。Result・ブランド型・ポートの書き方（コード）。テストの層と書き方（テスト。パターンごとの重心だけはここ）。並行、重複、互換性、派生データ、個人データ、イベントの版（データ）。表の名前・型・キー・索引（テーブル）。認証と認可の書き方（セキュリティ）。記録と通知（観測）。Worker を分けるか、D1 か別の DB か、Queue・Workflow・Durable Object を使う場面（技術の既定値）。

## 1. 迷ったとき

- 業務の必要で決まるならそれに従い、決まらないなら単純な方、それでも決まらなければあとで変えやすい方を選ぶ。
- 既存の `docs/domain/` と ADR を読み、変わる所だけを見直す。
- 業務の語や規則を発明しない。資料に無い語は「仮の名前」とし、依頼主に確かめる。
- 既存のコードに入るときは書き直さず、まずフォルダの境界をサブドメインに合わせる。新しい要件は新しい境界で作る。

## 2. サブドメインの種類と作り込みの程度

| 種類 | 見分け方 | 作り方 |
| --- | --- | --- |
| core | 切り出してもお金を払う人がいる。複雑な規則・不変条件・アルゴリズム。変わりやすい | 自作。最も作り込む |
| supporting | 優位は無く、入力と保存が中心。自作が既製品より安い | 自作。単純に作る |
| generic | 優位は無いが、複雑で解決済み | 既製品・SaaS・OSS |

- 業務アプリの多くは supporting か generic。事業の優位がソフトウェアの外（目利き、取引先との関係）にあるなら、作るものは supporting。「技術的に難しい所」を core としない。
- 「同じ利用者が、同じ業務上のものについて、密接なデータを扱う」ユースケースの集まりまで分ける。supporting と generic は、分けても設計が変わらなくなったら止める。判定できないものは「未確定」とし、依頼主に確かめる。
- supporting でも core に強く結び付くものは、変わりやすいと見る。種類が変わったら（規則が複雑になり変更が増えた、既製品が出た）、つなぎ方と配置を取り直す。

## 3. 用語

- 要件定義書の用語を出発点に、業務の語ごとにコードの英語名を 1 つ決め、要件・テスト・文書・コードで同じ語を使う。
- 1 語 1 意味。曖昧な語は分けて別の名前にし、同義語は同じ意味かを確かめてからそろえる。接頭辞で区別しない（例: 「請求便」）。要るならコンテキストを分ける。
- 用語集には名詞を書く。規則・不変条件は例（前提・操作・結果）にして、テストの名前と期待値にする。
- 同義語・曖昧な語の候補、出典の無い語、帳票の列名は、勝手に統一せず依頼主に確かめる。

## 4. コンテキストの境界

- 既定は、言葉の衝突が見つかるまでシステム全体を 1 つのコンテキストにし、サブドメインをフォルダで分ける。
- 分ける理由は、言葉の衝突か、リリースの周期・品質特性・規模の変え方の違いだけ。大きさと「チームが別」は理由にしない。
- 同じデータを扱うまとまりのある機能や集約を、2 つのコンテキストに割らない。
- 1 つの変更がいつも複数のコンテキストにまたがる、または呼び合わないと処理が終わらないなら、境界を引き直す。

## 5. つなぎ方

| 相手 | 既定 | 決まり |
| --- | --- | --- |
| 自分たちの別のコンテキスト | partnership | 境界で翻訳し、相手の内部の型を使わない |
| 外部サービス、依頼主の既存システム | ACL | 翻訳を境界の 1 か所に集め、ベンダーの語彙を内側に入れない。相手の概念がそのまま業務の言葉なら conformist |
| 画面、外部の利用者、MCP | OHS（`packages/contract`） | 内部のモデルと別の型。変換は入口で行う |
| 業務の概念の共通部品（金額、営業日） | shared kernel | 変わりにくい概念だけ。一覧に載せる |
| 統合が重複より高くつく | separate ways | core 同士では使わない |

- contract は API の面（画面、リソース）で分け、ドメインのモデルを写さず、他の package に依存させない。内部の `kind` とエラーの文言を出さず、公開用のエラーコードにする。列挙の値は、ずれたら型検査で落ちる形で写す。
- 内部の package 同士の間に写しの DTO を作らない。

非同期でつなぐとき

- 既定は同期。キューで分けても、共有する知識の結び付きは減らない。
- イベントは業務の結果ごとに 1 つにする。受け手のいないイベントを配信しない。
- 受け手が同じ D1 を読めるなら、キーと版の番号だけを運ぶ。元を読めない受け手か、その時点の値に意味があるときはデータを運び、更新では変わった項目の前後の値を入れる。大きな本文は R2 に置き、キーを運ぶ。
- 複数の段の流れ（状態を見せる、再開する、取り消す）は、1 つの Workflow かユースケースが順に命令する。consumer の連鎖は、独立した後始末（通知、射影の更新）だけに使う。業務上の分岐があれば process manager にする。
- outbox は、他のコンテキストや外部が確実に受け取る必要があるときだけ使う。内部のイベントを外へ公開せず、公開用のイベントを別に定義する。

## 6. 実装パターン（判断の木）

サブドメインごとに上から問う。手がかりなので、外れたら理由を「決めたこと」に書く。

1. 金銭の取引を扱う、一貫した監査ログが要る、振る舞いの深い分析が要る → event-sourced domain model（core に限らない。迷ったら、履歴に業務上の価値があるかを依頼主に確かめる）
2. 業務のロジックが複雑（規則・不変条件・アルゴリズムが多い） → domain model
3. 複雑なデータ構造がある → active record
4. どれでもない → transaction script（core には使わない）

| パターン | 形 | テストの重心 |
| --- | --- | --- |
| event-sourced | `decide`（コマンド → イベント）と `evolve`（イベント → 状態）の純粋関数 | 単体 |
| domain model | 状態ごとの型、判断する純粋関数、ポートを受け取るユースケース（読む → 判断する → 書く） | 単体 |
| active record | 型付きのデータ、読み書きの変換関数、サービス関数 | 本物の D1 での統合 |
| transaction script | 入口 → 1 つの関数 → DB。失敗は `Result` で返す | 入口からの統合 |

- パターンはサブドメインごとに選び、1 つのコンテキストに混ぜてよい。すべての機能を同じ層に通さない。
- 読み取り専用の画面や一覧は、ドメインのモデルを通さず、SQL で画面の型を直接返す。
- core なのに transaction script で足りる、supporting なのに domain model が要る、と食い違ったら依頼主に確かめる。
- 入力の検証と、必要な原子性と並行制御は、どのパターンでも省かない。
- パターンは 1 段ずつ移す。event sourcing へは状態ベースの集約を経由する。

## 7. 集約と不変条件

domain model と event sourcing のサブドメインだけで作る。

- 不変条件を書き出し、それを守るために同時に正しくなければならないデータの範囲を集約にする。結果整合で困らないものは外に出す。要件の名詞から作らない。
- 1 トランザクションで変える集約は 1 つ。他の集約は ID で参照する。状態は集約の操作だけで変える。並行して更新されうるなら、版の番号で楽観ロックをかける。
- 集約をまたぐ処理は、(1) いつも同時に変わるなら 1 つの集約に、(2) 同じ DB なら 1 回の原子的な書き込みに、(3) それでも分けるなら結果整合と補償にする。補償が失敗したときの行き先（DLQ の通知、照合、人の作業の一覧）を先に決める。取り消しが利用者に見えるなら、仮押さえで書いて全体の成功後に確定する。
- 規則の出力でなく入力を保存する（「VIP か」でなく判定の材料）。
- event sourcing では、個人情報を消すなら暗号化して鍵を消す形を最初から作る。スナップショットは 1 集約のイベントが 1 万件を超えるまで作らない。ログの表やトリガーで代用しない。

## 8. 配置

デプロイ単位が 1 つのモジュラーモノリスの既定（今のリポジトリに別の形があれば読み替える）。分ける次の段は、D1 を共有したまま Worker を業務ごとに分ける形。

```txt
apps/<app>/src/entry/                  入口と contract との変換
apps/<app>/src/composition.ts          依存の組み立て
apps/<app>/src/<context>/<subdomain>/  transaction script、active record、読み取りの問い合わせ
apps/<app>/src/<context>/adapters/     ポートの実装（DB、外部 API）
packages/<context>/src/<subdomain>/    domain/（状態の型、判断、ポートの型）、application/（ユースケース）、index.ts（公開面）
packages/contract/                     画面や外部に出す API の型
packages/db/                           マイグレーション
packages/<vendor>-client/              外部 API の通信形式
```

- domain model のサブドメインが無ければ `packages/<context>` を作らない。`packages/<context>` は `"types": []` にし、I/O を持たせない。
- package はコンテキストの業務の名前にする（`core`・`domain` は避ける）。`Manager`・`Service`・`Handler` の付く名前と `utils`・`common`・`helpers`・`lib` を作らず、役割か業務の行為で名付ける。責務を 1 文で書けないフォルダは分ける。
- 表の持ち主はコンテキスト。マイグレーションのファイル名と先頭に持ち主を書く（例: `0012_sales_add_order_note.sql` と `-- 持ち主: sales`）。表の SQL と行の変換は持ち主のアダプタに置き、全部の表の型を集めた置き場を作らない。
- 同じ I/O のコードを 2 つのデプロイ単位で使うなら、`packages/<context>-adapters` に移す。認可のように多くのコンテキストが使う確認は 1 か所に置く。
- 同じコンテキストのサブドメイン同士は `index.ts` だけを import する。コンテキストをまたぐときは公開面だけを使い、受け取った値を自分の言葉に変換し、ID は自分の `parse` でブランドを付ける。コンテキストのフォルダを 1 つの package に並べた既存の形でも、公開面以外を import しない。
- 相手が core なら `packages/<context>` 同士で import させない。使う側がポートを宣言し、`apps/` の組み立ての場所でつなぐ。
- 他のコンテキストの表に書き込まない。直接読むのは、上流が supporting か generic のときか、同じ package の中のときだけ。それ以外は公開面の問い合わせか統合用のビューを通す。

## 9. 境界の検査

- package の `exports` と依存の宣言で守る。Turborepo の Boundaries は実験的な機能なので、使う前に公式のドキュメントで今の状態を確かめる。
- フォルダの規則（公開面以外を import しない、純粋な層で I/O を使わない）は、dependency-cruiser か Biome のプラグインで書く。
- `apps/<app>/src/` と `packages/` の直下には、`context-map.md` のコンテキストと決まった場所だけを置き、CI のスクリプトで突き合わせる。
- 規則は実際にある境界のぶんだけ作り、わざと違反を置いて発火を確かめる。

## 10. 置くか分けるか

- 結び付きの強さ: 侵入（他の表に書く、公開面を通さない import）> 機能（同時に成功する、順に呼ぶ、同じ規則を 2 か所に持つ）> モデル（内部の型の共有）> 契約（contract、公開イベント）。問いは「要件が変わったら両方が変わるか」。
- 強いものは近く（同じサブドメインのフォルダ、できれば同じ集約）に置き、契約だけのものは遠くに置いてよい。Worker を分ける線は、契約だけの所に引く。
- 上流が変わりにくければ釣り合わなくても許し、見直す条件を「決めたこと」に書く。
- D1 を共有したまま Worker を分けても、D1 の待ちと障害は共有したまま。
- 同じ業務規則を 2 か所（画面とサーバー、2 つのコンテキスト）に書かない。持ち主を 1 か所に決め、結果を API かイベントで配る。
- 一緒に変わるものは同じフォルダに置く。型検査で見えない結び付きは、型か 1 つの関数にまとめる。

## 11. テナントごとの違い

- 値だけが違うならテナントの設定（表の列）にする。処理が違うなら中心と plug-in に分ける。2 つ目の違いが出るまで作らない。
- 中心はテナントで分岐しない。plug-in は変わり目ごとに型を決めた純粋関数で、DB を読まず、互いに依存しない。対応は組み立ての場所の型付きの表で決める。
- plug-in は `variants/<違いの中身>.ts` に置き、テナントの名前で名付けない。全 plug-in に同じ表のテストを流す。

## 12. 残す成果物

- 決定と学びの記録が、計画の README の `## 領域の変更` を `docs/domain/` に写す。`subdomains.md`（サブドメイン表）、`glossary.md`（用語集）、`context-map.md`（コンテキスト、つなぎ方、表の持ち主、shared kernel）。品質特性は `characteristics.md`、データの地図は `data-map.md`（中身はデータ）。
- `docs/` を `.gitignore` に入れない。
- ADR の候補: 判断の木と違うパターン、この決まりや技術の既定値から外れた配置やつなぎ方、新しい外部サービスへの依存、外部への API・webhook・MCP の公開、依頼主と合意したトレードオフ、shared kernel の追加、釣り合わない結び付きの受け入れ。既定どおりの決定は候補にしない。

## 13. 先に確かめる決定

- 遅らせてよい: コンテキストを細かく分けること、デプロイ単位を分けること、読み取り用のモデルの置き場、製品、画面の細部、索引。
- 先に確かめる: 履歴に業務上の価値があるか。金銭・監査・法令に関わるか。個人情報を消す必要があるか。外部サービスの制約（件数、返るデータ、障害時の振る舞い。試作で確かめる）。同時に操作されたときどうなるべきか。遅れて正しくなるあいだに何が起きてよいか。依頼主の組織の決まり（クラウドの可否、データの置き場所、SSO、作った後の運用を誰が持つか）。
- 要件定義書に答えが無ければ、計画を確定する前に利用者に聞く。答えが出るまで、その部分をフェーズに入れない。
- 影響と起こりやすさを 1〜3 で付けて掛け、6 以上を高いとする。使ったことのない技術、学習の時期より新しい版、ベータの機能は 9 とし、公式のドキュメントか試作で確かめるまで下げない。
- 試作のコードはリポジトリの外（計画の `.scratch/`）に置く。

## 計画に書くこと

- 案は要件定義書の品質特性の上位 3 つで比べ、代償を書く。既定から外れた決定と ADR の候補は「決めたこと」に書く。
- README の `## 領域の変更`（フェーズ表より前。作業名を書かない）に、変わる所だけを短く並べる。変わらない項目は「変更なし」と書く。
  - サブドメイン（種類、根拠の出典）
  - 用語（業務の語、コードの名前、意味、出典）
  - コンテキストとつなぎ方（パターン、翻訳の場所、表の持ち主、shared kernel）
  - 実装パターン（判断の木の答え）
  - 集約と不変条件（domain model の所だけ）
  - 配置（新しいフォルダと、その責務の 1 文）
  - 依頼主に確かめる事項（答えで設計がどう変わるか、点数）。計画を確定する前に利用者に聞き、答えは「決めたこと」に「利用者の判断（日付）」と書く
- フェーズの計画書の「約束」: 業務の語とコードの名前の対応。「作り方」: パターンの形、集約の操作と検査する不変条件、翻訳する場所。
- 「テスト」: パターンの重心に合うテスト、用語集の例を名前と期待値にしたテスト、全 plug-in に流す表のテスト、境界の規則の発火の確かめ。
- 「従う決まり」: このフェーズに当てはまる決まりを、今のリポジトリのパスと名前で写す（例: 「`invoices` 表の持ち主は請求。配送のコードから書き込まない」）。

## 依頼主に確かめること

- 判定できないサブドメインの優位はどこにあるか、切り出して売れるか。種類とパターンが食い違うとき、要求を単純にできるか。
- 同義語・曖昧な語・出典の無い語の意味。帳票の列名が業務の言葉か、昔のシステムの都合か。
- 状態の一覧と終わりの状態、終わった記録をいつ消すか、なぜその状態になったかを後から説明する必要があるか。補償が失敗したとき誰が直すか。
- テナントごとの違いは値だけか、処理まで違うか。
- 13 節の先に確かめる決定のうち、要件定義書に答えの無いもの。

## 確認の問い

- `## 領域の変更` のサブドメインごとに、種類と根拠の出典があるか。
- 新しい業務の語に出典があるか。出典の無い語を依頼主に確かめる事項にしたか。
- コンテキストを分けた理由は、言葉の衝突か、リリースの周期・品質特性の違いか。
- 外部サービスごとに、ACL か conformist かと、翻訳の場所が決まっているか。
- 新しい表に持ち主があり、他のコンテキストの表に書き込むフェーズが無いか。
- 分けた package・Worker・DB の間で、同時に成功すべき更新や同じ規則を共有していないか。
- サブドメインごとに判断の木の答えがあり、種類との食い違いを確かめたか。
- 集約は不変条件から見つけ、1 トランザクションで 1 集約か。
- event sourcing、outbox、非同期、Worker の分割に、この決まりの条件に当たる理由があるか。
- 集約をまたぐ処理で、補償が失敗したときの行き先が決まっているか。
- 新しい境界に、検査の規則と発火の確かめがあるか。
- 先に確かめる決定が、答えの無いまま実装のフェーズに入っていないか。
- 「従う決まり」は、ワーカーがこのファイルを読まずに守れるほど具体的か。

## CLAUDE.md に足す候補
