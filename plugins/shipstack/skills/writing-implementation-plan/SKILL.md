# 実装計画を書く

引数: `$ARGUMENTS`（計画のディレクトリ。要件定義のスキル `defining-requirements` が書いた `requirements.md` がある）

何を、なぜ、どこまで作るかは要件定義書で決まっている。ここでは、どう作るか（技術の設計とフェーズの切り方）を決めて計画に書く。この計画は、人に聞かないワーカーが `shipstack run` で 1 フェーズずつ実装する。実装の間は誰も答えないので、人が判断することはここで詰めて計画に書く。計画はリポジトリの外に置く文書で、コミットしない（マージの後も、フローの改善の記録として残す。正本はコードとテスト、コミット、機能の PR）。形の確かめは `shipstack` コマンド（プラグインの `bin/`。Bash の PATH にある）で行い、リポジトリのルートで実行する。

利用者への質問と報告、計画は日本語で書く。

## 守ること

- 要件の正は `requirements.md`。書いてあることは聞き直さず、変えない。計画が要件と食い違ってはならない
- 確かめられる事実（コードの作り、既存の仕組み、ライブラリの仕様、コマンドの出力）は自分で確かめ、根拠を控える。利用者に聞くのは、技術の判断と好みと、要件の抜け（要件定義書に無く、答えで何を作るかが変わる製品の判断）だけにする
- 要件の抜けを聞いて決めたら、`requirements.md` の該当の節と「決めたこと」に書き足してから計画に使う（要件の正を 1 か所に保つ）
- 仕様は必要に応じて Web Search や context7 で最新の情報を確かめる
- 不明点は AskUserQuestion で聞き、完全に解消するまでやりとりする。影響の大きいものから聞き、推奨の選択肢を先頭に置いて label の末尾に「（推奨）」を付ける
- 計画の形は [references/plan-format.md](references/plan-format.md) に従う。`check-plan`、指揮役、ワーカーのスキルがこの形を読む。計画が決めるのは、人の判断が要ることと、フェーズをまたいで合わせることだけにし、ワーカーが決める細部は書かない（分け方は plan-format.md の「計画が決めること、ワーカーが決めること」）。決めたことに「TBD」「適切に」「エッジケースを処理する」のような、一意にならない言葉を残さない
- git の操作はしない。リポジトリのファイルも変えない（使い捨てのスクリプトは計画のディレクトリの `.scratch/` に置く）
- 設計の決まりは、下の「設計の決まり」の表のファイルにある。変更が触れる分野のファイルだけを読み、決まりを当てて設計する。リポジトリの今の形（CLAUDE.md、既存のコード）と決まりが違うときは、今の形に合わせる（決まりへの移し替えは、この計画に混ぜず別の計画にする）。決まりから外れる設計は、違いと理由を README の「決めたこと」に書く
- ワーカーは決まりのファイルを読まない。フェーズで守る決まりは、そのフェーズの計画書の「従う決まり」に、今のリポジトリの名前（ファイル、関数、型）で具体的に書く。書いていない決まりはワーカーに届かない

## 設計の決まり

どの分野も、既定値、判断の基準、計画に書くこと、依頼主に確かめること、確認の問い（点検が使う）、CLAUDE.md に足す候補を持つ。決まりは、1 人と AI で業務アプリを Cloudflare と TypeScript のモノレポで作る前提の既定値（受託・自社・個人のどの開発でもよい）。依頼主は、何を作るかを決める人（受託開発なら受託先、自社開発なら事業や業務の担当、個人開発なら自分）を指す。依頼主が利用者本人なら、依頼主に確かめることは利用者に聞く。

| 分野 | 読むとき | ファイル |
| --- | --- | --- |
| 領域 | 新しい業務の概念・用語、境界（コンテキスト、package）、集約を作る・またぐとき | [references/design/domain.md](references/design/domain.md) |
| コード | コードを書くフェーズがあるとき（ほぼ常に） | [references/design/code.md](references/design/code.md) |
| データ | 保存・更新の仕方、並行、重複と再試行、外部との連携、取り込み、派生データ、個人データ、互換性（API・イベント・マイグレーション）が変わるとき | [references/design/data.md](references/design/data.md) |
| テーブル | 表・列・索引を足す・変えるとき | [references/design/tables.md](references/design/tables.md) |
| セキュリティ | 入口（API・画面・MCP・webhook）、権限、入力と出力、外への通信、ファイル、秘密の値、AI の機能が変わるとき | [references/design/security.md](references/design/security.md) |

| 画面 | 画面（ページ）・共通のメニュー・パンくず・フォーム・ダイアログ・一覧・日付の表示を足す・変えるとき | [references/design/ui.md](references/design/ui.md) |

## 手順

```txt
- [ ] 1. 要件定義書を読み、値を集める
- [ ] 2. 調べて、決まっていないことを洗い出す（設計の決まりを読む）
- [ ] 3. 利用者に聞いて詰める
- [ ] 4. 設計を比べて決める
- [ ] 5. 書く
- [ ] 6. 形を確かめる（check-plan）
- [ ] 7. 点検させて直す（reviewing-implementation-plan）
- [ ] 8. 報告する
```

### 1. 要件定義書を読み、値を集める

- リポジトリのルートで動いていることを確かめる（`git rev-parse --show-toplevel`）
- `<計画のディレクトリ>/requirements.md` が無ければ、計画を書かずに止まる。利用者に、先に `/shipstack:defining-requirements <要求>` で要件定義書を作るよう伝える
- 要件定義書の形を確かめる。`problems` が出たら計画を書かずに止まり、利用者に `/shipstack:defining-requirements` で直すよう伝える（要件は利用者と決めるもので、ここでは直さない）

  ```bash
  shipstack check-requirements <計画のディレクトリ>
  ```

- 計画名は計画のディレクトリの名前、計画の置き場所はその親のフォルダ。`README.md` が既にあれば、読んでから続きとして直す
- この会話を記録する。かかった時間とトークンを、後で `shipstack usage` が集める（点検のサブエージェントの分も含む）

  ```bash
  shipstack session <計画のディレクトリ> plan ${CLAUDE_SESSION_ID}
  ```

- 計画の置き場所がこのセッションの作業フォルダの外なら、書くたびに許可を求められる。止まらずに続ける（許可はその場で利用者が答える。文章で頼んで答えを待つと、そこでターンが終わり、frontmatter の `effort` と `allowed-tools` が外れる）
- 「プロンプトに入れる値」を集める。同じ置き場所にある前の計画の README の値の表、CLAUDE.md、`package.json` などのスクリプト、CI の設定（`.github/workflows/`）から取る。`{{インストール}}`・`{{静的解析}}`・`{{テスト}}` は今ここで流し、通るか、既に落ちているものがあるかを控える。決められない値だけを 3 で聞く
- E2E があるリポジトリ（CLAUDE.md や `docs/` の E2E の手順、`package.json` の `test:e2e`、`playwright.config.*` など）では、`{{E2E}}` を埋め、そのコマンドを「許可するコマンド」と「許可するコマンドのルール」に足す。手元の前提がそろっているか（設定ファイルがあるか。中身の秘密は読まない）を確かめ、人にしか用意できないものは「開始前に人がすること」に書く。E2E が無ければ「なし」

### 2. 調べて、決まっていないことを洗い出す

- 要件定義書の目的と完了の条件を、自分の言葉で 2〜3 行に言い直して示す
- 関係するコード、テスト、ADR、CLAUDE.md、`docs/domain/` を読む。広く探すときはサブエージェント（Explore）に任せ、結論とファイルの場所だけを受け取る
- 変更が触れる分野を「設計の決まり」の表で選び、そのファイルを読む。各ファイルの「計画に書くこと」を洗い出しに加える。「依頼主に確かめること」のうち要件定義書に無いものは、要件の抜けとして 3 で聞く
- 要件定義書の振る舞いと完了の条件を満たすために、どう作るかで決まっていないことを洗い出す: データの形と移行、モジュールの境界と置き場所、API、画面の部品と状態、失敗したときの扱い、品質特性の数字を満たす作り、セキュリティの作り（認可の置き場所、入力の検査、秘密の値）、テストの層、確かめのコマンド
- 洗い出したものを「事実（確かめれば分かる）」と「判断（利用者が決める）」に分ける。事実は、コードを読む・使い捨てのスクリプトを流すなどで確かめ、根拠（ファイル:行、コマンドと出力、公式のドキュメントの URL）を控える
- 要件定義書に無く、答えで何を作るかが変わる製品の判断が見つかったら、要件の抜けとして 3 で聞く。要件定義書の「計画に任せること」にあるものは、ここで決めてよい

### 3. 利用者に聞いて詰める

- 判断を AskUserQuestion で聞く。前提になる判断が決まっていて今聞けるものを、まとめて 1 回で聞く。答えで中身が変わる問いは、次の回に回す
- 各問に、分かっていること、決まっていないこと、選択肢ごとに起きること、推奨とその理由を書く。要件の抜けを聞くときは、そう書く
- 答えから新しく決まっていないことが出たら、2 と 3 を繰り返す
- 要件の抜けへの答えは、`requirements.md` の該当の節と「決めたこと」（根拠は「利用者の判断（日付）」）に書き足し、`check-requirements` をもう一度通す
- 聞くことが無くなったら、決めたこと（決定と理由）の一覧を示し、この理解で書いてよいかを AskUserQuestion で確かめてから 4 に進む

### 4. 設計を比べて決める

- 新しい構造を作る設計と、モジュールの境界をまたぐ設計は、構造の違う案を 2 つ以上比べて選ぶ（名前を変えただけの案は数えない）。要件定義書の品質特性で比べ、各案の代償を書く。製品の判断を含むなら、3 に戻って聞く
- 比べた案、採らなかった理由、選んだ理由、根拠と出典を、README の「決めたこと」に 1 行ずつ書く（列と出典の書き方は plan-format.md の「決めたこと」）。要件定義書の「決めたこと」にある製品の判断は、README に写さない
- 見立てで決めたもののうち、外れると作り直しになるものは、使い捨てのスクリプトで確かめて実測にするか、3 で利用者に聞く
- ADR にするかどうかはここでは決めない（全フェーズの後に、決定と学びの記録が、できあがったコードを見て決める）

### 5. 書く

[references/plan-format.md](references/plan-format.md) の雛形を写し、そこに書いた決まりに従って埋める。そのうえで、次を守る。

- フェーズは、機能ブランチに積む 1 コミットで閉じる単位にする（大きすぎず小さすぎず）。表の順に 1 つずつ実装する（並列にしない）。前のフェーズに依存するものは後ろに置き、複数のフェーズが使う定数・型は先行するフェーズにまとめる。ADR のためのフェーズと、`docs/domain/` を書くためのフェーズは作らない（決定と学びの記録が書く）
- 要件定義書の振る舞いの場面は、どれかのフェーズのテストか完了の条件で確かめる。用語の表の語は、コードの名前の元にする
- **完了の条件に書いた確かめのコマンドは、今ここで手元で 1 回流す。** まだ無いテストやファイルを確かめるコマンドは、同じ形の既存のもので流し、意図した出力（テストの名前、件数）が出ることを確かめる。要る環境変数や引数（テストの名前を出す reporter、絞り込みの書き方）はコマンドに含める。ある計画では、絞り込めない・名前が出ない・環境変数が無くて止まるコマンドを、ワーカーが 9 回直した
- 同じ確認（件数の控えと照合、マイグレーションの予行など）を 2 つ以上のフェーズで行うなら、最初に使うフェーズでスクリプトにし、後のフェーズはそれを使う
- 計画の要件: 要件定義書の振る舞い、完了の条件、品質特性、権限とデータを満たす。セキュリティの脆弱性が無い。利用者が操作に迷わない UI/UX（新しい画面の入口と戻り道、今の状態と次にすることが分かる。画面の設計の決まり）。使うツールやライブラリのベストプラクティスに従う。既存のアーキテクチャを踏襲する。`{{テストの範囲}}` と `{{UI の方針}}` に従う。本番へのデプロイは、機能の PR を main にマージしたときにだけ GitHub Actions が行う前提にする
- 全体を通して論理的に正しく、要件定義書とも計画書どうしでも矛盾が無いようにする

### 6. 形を確かめる

```bash
shipstack check-plan <計画のディレクトリ>
```

- `problems` が出たら直し、出なくなるまで繰り返す。指揮役は、problems のある計画を動かさない
- `warnings` は 1 つずつ読み、直すか、直さない理由を 8 の報告に書く
- `assumptions`（根拠が見立ての決定）は、8 の報告に並べる

### 7. 点検させて直す

全体の点検は 1 回だけ呼ぶ。重大な指摘を直したときだけ、直した所の確かめを 1 回呼ぶ。それより多くは呼ばない（点検は 1 回に 10 分以上かかり、呼び直すたびに直していない所からも新しい指摘が出て、終わらなくなる）。

- Skill ツールで `shipstack:reviewing-implementation-plan` を呼ぶ。引数は計画のディレクトリだけにし、自分の説明や結論は添えない。点検は会話を引き継がないサブエージェントで動くので、書いた本人ではない立場で読む。返るのは重大と中の指摘だけ
- 直す前に、点検の結果と、そのときの計画のファイル（`.md` のすべて）を残す。直した所の確かめが、これを読んで差分を取る

  ```bash
  mkdir -p <計画のディレクトリ>/.scratch/plan-review-1/before
  cp <計画のディレクトリ>/*.md <計画のディレクトリ>/.scratch/plan-review-1/before/
  ```

  点検の結果は、そのまま `.scratch/plan-review-1/result.md` に書く
- 返ってきた指摘を 1 つずつ、直す・直さない（理由）・利用者の判断が要る（AskUserQuestion で聞いてから直す）のどれかで扱い、扱いを `result.md` の各指摘の末尾に「- 扱い: <どれか>（<直した所、または理由>）」と書き足す。コードとの食い違いの指摘は、コードを読んで確かめてから直す。要件定義書との食い違いは、計画の側を直す（要件を変えるなら、利用者に聞いてから `requirements.md` も直す）
- 直したら 6 をやり直す
- 重大な指摘を直したときは、`shipstack:reviewing-implementation-plan` をもう一度呼ぶ。引数は計画のディレクトリと `<計画のディレクトリ>/.scratch/plan-review-1` の 2 つ。これは直した所の確かめで、前回の指摘が直ったかと、直した所だけを見る。返ってきた指摘は同じように扱い（結果は `.scratch/plan-review-2/result.md` に残す）、6 をやり直して点検を終える。ここで残った重大な指摘は、8 の報告に書く
- 重大な指摘が無かったときは、中の指摘を直して 6 をやり直し、点検を終える

### 8. 報告する

次を示して終える。

- 計画のディレクトリと、フェーズ表（作業名、エフォート、要約）
- 決めたこと（見立てのものは分けて並べる）と、開始前に人がすること
- 要件定義書に書き足したこと（要件の抜けとして聞いたもの）
- `check-plan` の結果（warnings と、それぞれの扱い）
- 読んだ設計の決まりの分野と、リポジトリの今の形が決まりと違う所（「決めたこと」に書いたもの）。読んだ分野の「CLAUDE.md に足す候補」のうち、リポジトリの CLAUDE.md（と `.claude/settings.json`）に無いものを並べ、足すかを利用者に任せる（この計画では足さない）
- 点検の指摘と、それぞれの扱い（全件。直さなかったものは理由）
- 次にすること。利用者が計画を読んで承認し、開始前に人がすることを済ませてから、リポジトリのルートで動かす

  ```bash
  "${CLAUDE_PLUGIN_ROOT}/bin/shipstack" run <計画のディレクトリ> --dry-run
  "${CLAUDE_PLUGIN_ROOT}/bin/shipstack" run <計画のディレクトリ>
  ```
